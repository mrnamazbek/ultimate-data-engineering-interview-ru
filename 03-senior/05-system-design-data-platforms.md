# Системный дизайн платформ данных (Уровень Senior)

Секция **System Design** — ключевой этап собеседования на позиции Senior Data Engineer, Lead и Data Architect. Здесь оценивается умение кандидата спроектировать надежную, масштабируемую и экономически эффективную платформу данных с нуля, учитывая бизнес-требования, объемы, SLA и безопасность.

---

## 1. Фреймворк ответа на интервью по System Design

На интервью кандидату дают открытую задачу: *«Спроектируйте платформу данных для сервиса доставки еды (100 млн заказов в день, аналитика в реальном времени + отчетность для финансистов)»*.

### 6 шагов структурированного ответа:
1. **Сбор требований и ограничений (Clarification & Scope)**:
   - Функциональные требования: какие типы отчетов нужны? (Real-time дэшборды с задержкой < 5 сек или ночной расчет задолженностей).
   - Нефункциональные требования: объем данных (ГБ/ТБ/сутки), пиковые RPS, допустимый процент потерь (для логов — допустимо, для финансовых транзакций — строго Exactly-Once), SLA на восстановление (RPO, RTO).
2. **Оценка объемов (Back-of-the-envelope calculations)**:
   - 100 млн заказов / $86400$ сек $\approx 1200$ заказов/сек (пик до $5000$ RPS).
   - 1 запись заказа $\approx 1$ КБ $\implies 100$ ГБ сырых данных в сутки $\implies 36.5$ ТБ в год без учета логов.
3. **Высокоуровневая архитектура (High-Level Architecture)**.
4. **Выбор технологий хранения и вычислений (Deep Dive)**: обоснование выбора между Kafka, Spark, Flink, Iceberg, ClickHouse.
5. **Масштабирование и отказ нод (Fault Tolerance & Scalability)**.
6. **Data Governance, мониторинг и безопасность (PII, Observability)**.

## 2. Медальонная архитектура (Medallion Architecture: Bronze -> Silver -> Gold)

Отраслевой паттерн организации слоев данных в корпоративных Lakehouse-платформах:

```text
[Источники данных] ──► +---------------------------------------------+
(RDBMS, IoT, Kafka)     |             СЛОЙ BRONZE (СЫРОЙ)             |
                        | - Сырые логи и таблицы как есть (JSON/Avro)|
                        | - Append-only, сохранение полной истории   |
                        +----------------------+----------------------+
                                               |
                                               v Очистка, дедупликация, валидация
                        +---------------------------------------------+
                        |            СЛОЙ SILVER (ОЧИЩЕННЫЙ)          |
                        | - Приведение типов, очистка от мусора       |
                        | - Консолидация сущностей (Users, Orders)    |
                        | - SCD Type 2 таблицы измерений              |
                        +----------------------+----------------------+
                                               |
                                               v Бизнес-агрегации и витрины
                        +---------------------------------------------+
                        |             СЛОЙ GOLD (БИЗНЕС-ВИТРИНЫ)      |
                        | - Схемы «Звезда» для аналитиков и BI        |
                        | - Фичи для ML-моделей                       |
                        | - Максимальная скорость выполнения SQL      |
                        +---------------------------------------------+
```

## 3. Data Mesh (Сетка данных) против Монолитного DWH

Традиционные централизованные команды данных становятся узким местом (bottleneck) в крупных компаниях: аналитики из 20 бизнес-отделов ждут от единственной команды DE доработок месяцами.

### 4 столпа архитектуры Data Mesh (по Жамак Дехгани):
1. **Domain-oriented ownership (Владение по доменам)**: инженерные пайплайны и таблицы принадлежат конкретным бизнес-командам («Команда логистики», «Команда платежей»), а не общей абстрактной команде инженеров данных.
2. **Data as a Product (Данные как продукт)**: команда домена отвечает за свои данные как за публичный API (гарантирует SLA, документацию, стабильность схемы и качество).
3. **Self-serve data platform (Платформа самообслуживания)**: центральная команда инфраструктуры предоставляет удобные инструменты (K8s, Spark, каталоги, шаблоны Airflow) в виде PaaS, чтобы продуктовые команды могли легко создавать свои пайплайны сами.
4. **Federated computational governance (Федеративное управление)**: единые сквозные стандарты компании по безопасности, маскированию данных и политикам доступа, исполняемые автоматически через код.

## 4. Data Governance: Происхождение данных и безопасность PII

Инженер уровня Senior проектирует систему с учетом регулирования (GDPR, HIPAA, ФЗ-152):

### Происхождение данных (Data Lineage)
Возможность визуально проследить весь путь конкретной цифры в отчете вплоть до исходной транзакции в мобильном приложении:
- Автоматический сбор метаданных на базе открытого стандарта **OpenLineage** при выполнении Spark-задач или Airflow DAG.
- Хранение и отображение графа зависимостей в каталогах данных (DataHub, Marquez, Apache Atlas).

### Маскирование персональных данных (PII Masking)
- Паспорта, номера банковских карт, телефоны и email маскируются на границе слоя Bronze -> Silver.
- Для аналитики применяется необратимое соление и хэширование (`SHA256(phone + salt)`), позволяющее соединять таблицы по ID без раскрытия реального телефонного номера.
- Динамическое маскирование на уровне строк/колонок (Row/Column-level Security в Trino / Ranger / BigQuery).
