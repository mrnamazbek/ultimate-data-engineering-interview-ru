# Оптимизация Oracle Database (Oracle Performance Tuning)

Oracle Database — флагманская СУБД в банковском, страховом и телеком-сегменте. Оптимизация Oracle строится вокруг стоимостного оптимизатора (CBO), анализа системных очередей ожидания через AWR-отчеты и гранулярного управления планами выполнения с помощью подсказок (Hints).

---

## 1. Стоимостный оптимизатор (Cost-Based Optimizer — CBO) и статистика

Оптимизатор CBO выбирает путь выполнения запроса на основе статистики распределения данных. Если статистика устарела, CBO строит неоптимальные планы (например, выбирает Full Table Scan вместо Index Range Scan).

### Сбор актуальной статистики через `DBMS_STATS`:
```sql
-- Сбор статистики по таблице и ее индексам с построением гистограмм распределения значений
BEGIN
    DBMS_STATS.GATHER_TABLE_STATS(
        ownname          => 'ANALYTICS',
        tabname          => 'FACT_TRANSACTIONS',
        estimate_percent => DBMS_STATS.AUTO_SAMPLE_SIZE, -- адаптивный размер выборки
        method_opt       => 'FOR ALL COLUMNS SIZE AUTO', -- автоматический расчет гистограмм для колонок с перекосом
        cascade          => TRUE,                        -- собирать статистику и по индексам таблицы
        degree           => 4                            -- параллельность в 4 потока
    );
END;
/
```

### Гистограммы (Histograms)
Если колонка имеет сильный перекос значений (например, 99% клиентов из одного региона и 1% из других), обычный расчет селективности ошибается. Гистограммы (`Frequency`, `Top-Frequency`, `Hybrid`) позволяют CBO знать точное распределение частотности значений и выбирать индекс только для редких значений.

## 2. Подсказки оптимизатора (Optimizer Hints)

Хинты — это специальные комментарии `/*+ ... */` сразу после ключевого слова `SELECT`, принудительно направляющие CBO по определенному пути выполнения, когда автоматика выбирает плохой план.

### 1. Управление методами доступа (Access Paths):
- `/*+ FULL(t) */` — принудительное полное сканирование таблицы `t`.
- `/*+ INDEX(t idx_name) */` — принудительное сканирование по конкретному индексу.
- `/*+ INDEX_FFS(t idx_name) */` — быстрое полное сканирование индекса (Index Fast Full Scan) вместо таблицы.

### 2. Управление порядком и типом соединений:
```sql
SELECT /*+ LEADING(c o) USE_HASH(o) NO_MERGE */
    c.customer_name,
    SUM(o.amount) AS total_amount
FROM customers c
JOIN orders o ON c.customer_id = o.customer_id
GROUP BY c.customer_name;
```
- `LEADING(c o)`: предписывает начать соединение с таблицы `customers`, затем присоединить `orders`.
- `USE_HASH(o)`: указывает соединять таблицу `orders` методом Hash Join.
- `USE_NL(o)`: указывает использовать Nested Loop.

### 3. Параллельное выполнение (Parallel Query):
```sql
-- Разделение тяжелого аналитического запроса на 8 параллельных потоков CPU
SELECT /*+ PARALLEL(f 8) */ 
    COUNT(*), SUM(amount)
FROM fact_large_sales f;
```

## 3. Анализ производительности: Отчеты AWR и события ожидания (Wait Events)

Отчет **AWR (Automatic Workload Repository)** — главный диагностический документ для инженера данных и администратора Oracle.

### Главные события ожидания (Top Wait Events) в отчете:
1. **`db file sequential read`**:
   - Одиночное чтение одного блока данных с диска в память.
   - *Что означает*: выполнение поиска по индексу (`Index Scan`). Если занимает слишком много времени — индекс фрагментирован или запрашивается слишком много строк (выгоднее перейти на Full Table Scan).
2. **`db file scattered read`**:
   - Многоблочное чтение (Multiblock Read).
   - *Что означает*: полное сканирование таблицы (`Full Table Scan`) или быстрое сканирование индекса (`Index Fast Full Scan`). Если занимает 90% времени ожидания — не хватает индексов для фильтрации.
3. **`direct path read / write temp`**:
   - Чтение и запись напрямую во временное табличное пространство (Temporary Tablespace).
   - *Что означает*: операции сортировки (`ORDER BY`, `GROUP BY`, Hash Join) не помещаются в оперативную память процесса (PGA) и сбрасываются на диск. Требуется увеличить параметр `PGA_AGGREGATE_TARGET`.
4. **`log file sync`**:
   - Сессия ожидает, пока процесс LGWR сбросит буфер Redo Log на диск при фиксации транзакции (`COMMIT`).
   - *Что означает*: слишком частые коммиты внутри мелких циклов (`COMMIT` на каждую строку) или медленный диск под журналами повтора.

## 4. Память: Архитектура SGA и PGA

- **SGA (System Global Area)**: общая разделяемая память экземпляра.
  - *Database Buffer Cache*: кэш блоков таблиц и индексов.
  - *Shared Pool*: кэш разобранных SQL-запросов (Library Cache) и системного словаря данных. Параметризация запросов (Bind Variables `:val` вместо жестких литералов) предотвращает жесткий парсинг (Hard Parse) и экономит Shared Pool.
- **PGA (Program Global Area)**: приватная память, выделяемая под каждый серверный процесс для выполнения сортировок и хэш-соединений.

### Формула управления PGA:
```sql
-- Увеличение общего пула для тяжелых ETL-нагрузок
ALTER SYSTEM SET PGA_AGGREGATE_TARGET = 32G SCOPE=BOTH;
```

## 5. Партиционирование таблиц (Partitioning)

Для больших таблиц фактов (сотни гигабайт) партиционирование обязательно:
- **Range Partitioning**: по диапазону дат (`PARTITION BY RANGE (order_date)`). Обеспечивает **Partition Pruning**: при выборке за конкретный месяц дисковые сегменты других месяцев даже не открываются движком.
- **List Partitioning**: по дискретному списку категорий или стран (`PARTITION BY LIST (country_code)`).
- **Composite Partitioning (Композитное)**: двухуровневое разбиение (например, Range по дате + Hash по `user_id` для равномерного распределения внутри каждого месяца).
