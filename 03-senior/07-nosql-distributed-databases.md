# 07. Распределенные NoSQL базы данных: Архитектура Cassandra и DynamoDB

## 1. Введение: Смена парадигмы — от реляционного моделирования к Query-First

Главная ментальная ловушка инженера, переходящего из мира PostgreSQL/MySQL в распределенные NoSQL хранилища (Apache Cassandra, ScyllaDB, Amazon DynamoDB), заключается в попытке нормализовать данные и надеяться на джойны (JOIN).

В распределенных NoSQL системах действует **Золотое правило NoSQL**:
> **"В SQL вы проектируете модель данных, чтобы отвечать на любые запросы в будущем. В распределенном NoSQL вы проектируете модель данных исключительно под заранее известные паттерны доступа (Query-First Modeling)."**

### Сравнительная таблица парадигм

| Параметр | Реляционные СУБД (PostgreSQL, Oracle) | Распределенный NoSQL (Cassandra, DynamoDB) |
| :--- | :--- | :--- |
| **Основной принцип** | Нормализация (3NF), разделение сущностей | Денормализация, дублирование ради быстрого чтения |
| **Операция JOIN** | Выполняется на лету процессором СУБД | Запрещена; данные предрассчитываются при записи |
| **Масштабирование** | Вертикальное (Scale-Up), Read-реплики | Горизонтальное (Scale-Out) без единой точки отказа |
| **Согласованность** | ACID (строгая согласованность) | BASE (Eventual Consistency), настраиваемый кворум |
| **Стоимость хранения** | Экономим диск за счет нормализации | Диск дешев; оптимизируем задержку сети и CPU |

## 2. Физическое распределение данных: Роль ключей

### 2.1. Согласованное хеширование (Consistent Hashing) и кольцо токенов
В Apache Cassandra кластер представляет собой кольцо токенов (от $-2^{63}$ до $2^{63}-1$). Каждый узел (нода) отвечает за определенный диапазон хеш-значений.

Когда клиент отправляет запись, СУБД берет хеш от **Partition Key (Ключа партиционирования)** с помощью алгоритма Murmur3 и точно определяет, на какую физическую ноду и ее реплики положить строку.

### 2.2. Составной первичный ключ (Composite Primary Key)

Первичный ключ в Cassandra и DynamoDB делится на две принципиальные составляющие:

```sql
-- Пример таблицы в Cassandra (CQL)
CREATE TABLE sensor_readings (
    device_id uuid,
    metric_type text,
    reading_timestamp timestamp,
    value double,
    PRIMARY KEY ((device_id, metric_type), reading_timestamp)
) WITH CLUSTERING ORDER BY (reading_timestamp DESC);
```

1. **Partition Key (Ключ партиционирования)**: `(device_id, metric_type)`
   - Определяет, **на каком узле кластера** физически хранятся данные.
   - По нему возможен только поиск по точному равенству (`WHERE device_id = ... AND metric_type = ...`).
2. **Clustering Key / Sort Key (Ключ кластеризации/сортировки)**: `reading_timestamp`
   - Определяет, **в каком физическом порядке** строки записаны на диске внутри одной партиции.
   - Позволяет выполнять высокоэффективные интервальные выборки (`WHERE reading_timestamp >= '2026-09-01'`).

## 3. Проблема горячих разделов (Hot Partitions) и методы решения

### В чем опасность
Если в качестве ключа партиционирования выбрать поле с низкой кардинальностью (например, `status = 'ACTIVE'` или дату `date = '2026-09-20'`), то миллионы записей и тысячи сетевых запросов в секунду полетят на **один единственный сервер** в кластере. Остальные 99 нод будут простаивать, а целевая нода упадет от нехватки CPU/IOPS.

### Инженерные техники борьбы с Hot Partitions

1. **Соление ключа (Key Salting)**:
   К ключу партиции искусственно приписывается случайный суффикс из фиксированного диапазона (например, от 0 до $N-1$):
   ```
   Сырой ключ:    user_actions_2026-09-20
   Засоленный:     user_actions_2026-09-20_salt_3
   ```
   При записи суффикс генерируется как `random(0, 9)`, что равномерно распределяет трафик по 10 узлам. При чтении клиент делает 10 параллельных асинхронных запросов и объединяет результат в памяти.

2. **Составные синтетические ключи**:
   Объединение сущности с бакетом времени, например `device_10492#2026-09-20-14` (почасовые бакеты вместо суточных).

## 4. Паттерн Single-Table Design (в Amazon DynamoDB)

В реляционных СУБД под каждую сущность создается отдельная таблица (`users`, `orders`, `order_items`). В DynamoDB создание нескольких таблиц приводит к необходимости делать несколько последовательных сетевых запросов (Network Roundtrips) от бэкенда к БД.

**Single-Table Design** — это подход, при котором **все разнородные сущности сервиса хранятся в одной физической таблице**.

### Пример таблицы с использованием обобщенных ключей PK и SK:

| PK (Partition Key) | SK (Sort Key) | Type | Attr1 (Name / Status) | Attr2 (Amount / Email) |
| :--- | :--- | :--- | :--- | :--- |
| `ORG#501` | `METADATA` | Organization | Acme Corp | enterprise@acme.com |
| `ORG#501` | `USER#usr_11` | User | Alice Johnson | alice@acme.com |
| `ORG#501` | `USER#usr_12` | User | Bob Smith | bob@acme.com |
| `USER#usr_11`| `PROFILE` | UserProfile | Alice Johnson | Timezone: UTC |
| `USER#usr_11`| `ORDER#2026#901`| Order | COMPLETED | $1,250.00 |
| `USER#usr_11`| `ORDER#2026#902`| Order | PENDING | $340.00 |

### Преимущества:
1. Запрос `WHERE PK = 'USER#usr_11' AND SK begins_with('ORDER#2026')` за **одно обращение к базе данных** возвращает все заказы пользователя за 2026 год, отсортированные по номеру.
2. Запрос `WHERE PK = 'USER#usr_11'` возвращает профиль пользователя и все его заказы вместе (Adjacency List Pattern).

## 5. Архитектура движка хранения: LSM-Tree и Tombstones

В отличие от PostgreSQL, использующего B-Tree со случайной перезаписью страниц на диске, Cassandra и RocksDB построены на базе **LSM-Tree (Log-Structured Merge-tree)**.

### Механизм записи (Append-Only):
1. Запрос на запись попадает в **CommitLog** (последовательный журнал на диске для гарантии долговечности).
2. Данные сохраняются в оперативную память в отсортированную структуру **Memtable**.
3. Запись подтверждается клиенту (задержка записи обычно < 2 мс).
4. При заполнении памяти Memtable сбрасывается на диск в виде неизменяемого файла **SSTable (Sorted String Table)**.

```
[ Client Write ]
      │
      ├──► [ 1. CommitLog (Disk Append) ]
      │
      └──► [ 2. Memtable (RAM) ]
                 │
                 ▼ (Flush)
           [ 3. SSTable (Immutable Disk File) ]
                 │
                 ▼
           [ 4. Compaction (Фоновое слияние) ]
```

### Проблема Tombstones (Надгробных маркеров)
Так как файлы SSTable неизменяемы (immutable), физически удалить строку с диска в момент выполнения `DELETE` невозможно.
Вместо этого Cassandra записывает специальный маркер удаления — **Tombstone** (надгробный камень) с временной меткой.

> **Критическая ошибка эксплуатации**: Если приложение использует Cassandra как очередь задач (постоянно пишет строки и тут же их удаляет), в базе накапливаются миллионы Tombstones. При выполнении запроса на чтение СУБД вынуждена сканировать тысячи надгробных маркеров, что приводит к таймаутам, росту GC паузы в Java и падению ноды (`ReadFailureException: Scanned over 10000 tombstones`). Физическое удаление происходит только во время фоновой процедуры **Compaction** после истечения периода `gc_grace_seconds`.

## 6. Настраиваемая согласованность (Tunable Consistency) и Кворум

В Cassandra и распределенных хранилищах вы управляете балансом между скоростью и строгой согласованностью на уровне каждого отдельного запроса.

### Формула строгого кворума:
$$R + W > N$$
Где:
- $N$ — Фактор репликации (Replication Factor, обычно $N = 3$).
- $W$ — Число узлов, подтвердивших запись (Write Consistency Level).
- $R$ — Число узлов, ответивших при чтении (Read Consistency Level).

Если $R + W > N$, вы гарантированно прочитаете самую свежую версию записи, так как множества узлов записи и чтения пересекаются хотя бы на одном узле.

### Типичные уровни согласованности:
- **`LOCAL_QUORUM` (Рекомендуется для большинства enterprise-систем)**: Требует подтверждения от большинства реплик в локальном дата-центре ($\lfloor N/2 \rfloor + 1$). Защищает от задержек межрегиональной сети.
- **`ONE`**: Ответ возвращается, как только ответила первая попавшаяся реплика. Максимальная скорость, но риск прочитать устаревшие данные (Stale Read).
- **`ALL`**: Требует ответа от всех $N$ узлов. Если хотя бы один сервер в кластере недоступен, запрос падает с ошибкой (нулевая отказоустойчивость при записи).

## 7. Вопросы с Senior собеседований

### Вопрос 1: В каких случаях для Big Data платформы следует выбрать Cassandra вместо HBase или ClickHouse?
**Ответ**:
- **Cassandra** выбирается для транзакционных высоконагруженных OLTP-сценариев с огромным потоком точечной записи по ключу (Point Lookups) и отсутствием единой точки отказа (Masterless Architecture). Примеры: профили пользователей, корзины интернет-магазина, фиче-стор (Feature Store) для ML в реальном времени.
- **ClickHouse** выбирается для аналитики (OLAP), агрегаций по миллиардам строк (`SUM`, `AVG`, `GROUP BY`). Точечные апдейты и транзакции в ClickHouse неэффективны.
- **HBase** исторически выбирался при тесной интеграции с экосистемой Hadoop (HDFS/MapReduce), но имеет архитектурного мастера (NameNode/HMaster) и сложнее в обслуживании.

### Вопрос 2: Как в Cassandra реализовать пагинацию страниц без использования `OFFSET`?
**Ответ**:
В Cassandra нет оператора `OFFSET`, так как смещение на 100 000 строк требовало бы полного сканирования всего кластера. Пагинация реализуется исключительно через **Cursor / Keyset Pagination**:
При выборке первой страницы возвращается последний прочитанный токен (`token(pk)`) или значение ключа сортировки (`sort_key`). Следующий запрос запрашивает строки строго больше полученного маркера:
```sql
SELECT * FROM user_events 
WHERE user_id = ? AND event_time < ? 
LIMIT 20;
```
