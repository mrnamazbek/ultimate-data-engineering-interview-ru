# Оркестрация данных в Apache Airflow (Уровень Middle)

Apache Airflow — отраслевой стандарт для оркестрации и планирования конвейеров данных. На собеседованиях уровня Middle вопросы по Airflow охватывают архитектуру компонентов, выбор исполнителей (Executors), правильную работу с сенсорами и исключение антипаттернов при передаче данных между задачами.

---

## 1. Архитектура Apache Airflow

Airflow состоит из четырех ключевых компонентов, взаимодействующих через метабазу:

```text
       +--------------------+      +--------------------+
       |   Airflow Web UI   |      | Airflow Scheduler  |
       |  (Мониторинг, DAG) |      | (Парсинг, очереди) |
       +---------+----------+      +---------+----------+
                 |                           |
                 +-------------+-------------+
                               |
                   +-----------v-----------+
                   |   Metadata Database   |
                   |  (PostgreSQL / MySQL) |
                   +-----------+-----------+
                               |
                     +---------v---------+
                     | Airflow Executor  |
                     | (Celery / K8s)    |
                     +---------+---------+
                               |
            +------------------+------------------+
            |                                     |
    +-------v-------+                     +-------v-------+
    | Worker Node 1 |                     | Worker Node 2 |
    |  [Task Pod]   |                     |  [Task Pod]   |
    +---------------+                     +---------------+
```

1. **Scheduler (Планировщик)**: периодически парсит DAG-файлы, отслеживает расписание, проверяет зависимости задач и отправляет готовые к запуску таски в очередь Executor-а.
2. **Webserver**: веб-интерфейс для мониторинга статусов, ручного триггера, просмотра логов и управления переменными (Variables) и подключениями (Connections).
3. **Metadata Database (БД метаданных)**: реляционная база (обычно PostgreSQL), где сохраняется состояние всех запусков DAG (`DagRun`), экземпляров задач (`TaskInstance`), учетные записи и переменные.
4. **Executor & Workers**: исполнительный механизм, запускающий физический код задач.

---

## 2. Ключевые абстракции: DAG, Оператор, Таска, TaskInstance

- **DAG (Directed Acyclic Graph)**: граф выполнения задач, в котором нет циклов (задача А не может зависеть от задачи Б, если Б зависит от А).
- **Operator (Оператор)**: шаблон/класс, определяющий, **что именно** нужно сделать:
  - `PythonOperator` — выполнение Python-функции.
  - `BashOperator` — выполнение bash-скрипта.
  - `SQLExecuteQueryOperator` — запуск SQL-запроса в СУБД.
  - `SparkSubmitOperator` — отправка задачи на Spark-кластер.
- **Task (Задача)**: экземпляр оператора, включенный в DAG.
- **TaskInstance (Экземпляр задачи)**: конкретный запуск задачи для определенного момента времени (`logical_date`). Имеет жизненный цикл: `queued` -> `running` -> `success` / `failed` / `up_for_retry`.

## 3. Обмен данными: XCom (Cross-Communication)

### Что это такое
Механизм передачи небольших сообщений и параметров между задачами внутри одного запуска DAG через базу метаданных.

```python
# Задача-источник отправляет метаданные (push)
def extract_data(**context):
    file_path = "s3://bucket/data_2026_09_18.parquet"
    context['ti'].xcom_push(key='landing_path', value=file_path)

# Задача-приемник читает метаданные (pull)
def load_data(**context):
    path = context['ti'].xcom_pull(task_ids='extract_task', key='landing_path')
    print(f"Loading data from {path}")
```

### Главный антипаттерн XCom
Передача через XCom реальных таблиц или больших датасетов (Pandas DataFrame). Поскольку XCom сохраняется в реляционной базе данных Airflow (PostgreSQL), передача данных объемом более нескольких мегабайт приведет к переполнению базы и деградации производительности всего кластера Airflow. 
*Правило*: Через XCom передают **только метаданные** (путь к файлу в S3, количество обработанных строк, ID партиции).

## 4. Сенсоры (Sensors): режим `poke` против `reschedule`

Сенсор — это специальный тип оператора, который ожидает наступления внешнего события (появления файла в S3, завершения другого DAG, появления записи в таблице).

### Разница режимов (Mode):
- `mode='poke'` (по умолчанию): сенсор занимает рабочий слот воркера (`worker slot`) и держит его заблокированным всё время ожидания, периодически опрашивая источник. Если файл задерживается на 4 часа, рабочий поток воркера 4 часа будет простаивать, блокируя другие важные задачи.
- `mode='reschedule'`: сенсор опрашивает источник один раз. Если условие не выполнено, сенсор освобождает слот воркера и переходит в статус `up_for_reschedule`. Планировщик разбудит его снова через заданный интервал (`poke_interval`).

*Рекомендация*: Для любых ожиданий длительностью более 2-3 минут всегда используйте `mode='reschedule'`.

```python
from airflow.sensors.filesystem import FileSensor

wait_for_file = FileSensor(
    task_id='wait_for_incoming_file',
    filepath='/data/inbox/sales.csv',
    poke_interval=60,         # проверять раз в минуту
    timeout=60 * 60 * 3,      # таймаут 3 часа
    mode='reschedule'         # освобождать рабочий слот между проверками!
)
```

## 5. Сравнение Airflow Executors

| Executor | Как работает | Масштабируемость | Сценарий применения |
|---|---|---|---|
| **SequentialExecutor** | Выполняет задачи строго по очереди на SQLite | Нулевая (только для отладки) | Локальная разработка и тестирование |
| **LocalExecutor** | Запускает задачи в отдельных процессах на одной машине | Ограничена ресурсами одного сервера | Небольшие проекты с умеренной нагрузкой |
| **CeleryExecutor** | Распределяет задачи по пулу воркеров через очередь (Redis / RabbitMQ) | Высокая горизонтальная масштабируемость | Традиционный корпоративный продакшн |
| **KubernetesExecutor** | Под каждую таску динамически поднимается изолированный K8s Pod и удаляется после завершения | Идеальная изоляция ресурсов и автомасштабирование | Современный Cloud-Native продакшн |

## 6. Механизм `catchup` и `backfill`

### Параметр `catchup=True/False`
Когда вы активируете DAG с датой начала в прошлом (`start_date = days_ago(30)`):
- При `catchup=True`: Airflow мгновенно создаст 30 последовательных запусков (`DagRun`) за все пропущенные дни. Если пайплайн не готов к такой нагрузке, это может положить базу данных источника или исчерпать ресурсы воркеров.
- При `catchup=False`: Airflow запустит расчет только для самого последнего интервала времени.

### Ручной исторический пересчет (Backfill)
Для контролируемого исторического перерасчета данных за прошлый период используют CLI-команду:
```bash
airflow dags backfill \
    --start-date 2026-01-01 \
    --end-date 2026-01-31 \
    --reset-dagruns \
    my_etl_pipeline
```

## 7. Разработка кастомных плагинов: Hooks, Operators и Sensors

В реальных проектах возможностей стандартных операторов недостаточно. Например, требуется взаимодействовать с внутренней CRM-системой, специфическим API банка или кастомным хранилищем.

### 7.1. Разделение ответственности: Hook против Operator
В архитектуре Airflow действует строгое разделение:
- **Hook (Хук)**: отвечает исключительно за **подключение и низкоуровневый протокол** к внешней системе (управление сетевой сессией, авторизацией, ретраями HTTP/TCP). Хук ничего не знает о графе DAG.
- **Operator (Оператор)**: отвечает за **бизнес-логику шага** (что сделать с данными, куда передать). Оператор внутри себя вызывает соответствующий Hook.

### 7.2. Практический пример: Кастомный Hook и Operator

```python
# plugins/custom_crm_plugin.py
from airflow.hooks.base import BaseHook
from airflow.models import BaseOperator
from airflow.utils.decorators import apply_defaults
import requests

# 1. Кастомный хук для авторизации и обращения к API
class CrmApiHook(BaseHook):
    def __init__(self, crm_conn_id: str = "crm_default"):
        super().__init__()
        self.crm_conn_id = crm_conn_id

    def get_conn(self):
        # Получение хоста, логина и пароля из защищенного хранилища Airflow Connections
        conn = self.get_connection(self.crm_conn_id)
        session = requests.Session()
        session.headers.update({"Authorization": f"Bearer {conn.password}"})
        return conn.host, session

    def fetch_leads(self, target_date: str):
        host, session = self.get_conn()
        response = session.get(f"{host}/api/v1/leads", params={"date": target_date}, timeout=30)
        response.raise_for_status()
        return response.json()

# 2. Кастомный оператор, использующий созданный хук
class CrmToS3Operator(BaseOperator):
    # template_fields указывает поля, в которых работает Jinja-шаблонизация!
    template_fields = ("target_date", "s3_key")

    @apply_defaults
    def __init__(self, target_date: str, s3_key: str, crm_conn_id: str = "crm_default", **kwargs):
        super().__init__(**kwargs)
        self.target_date = target_date
        self.s3_key = s3_key
        self.crm_conn_id = crm_conn_id

    def execute(self, context):
        self.log.info(f"Запуск выгрузки лидов за дату: {self.target_date}")
        hook = CrmApiHook(crm_conn_id=self.crm_conn_id)
        leads_data = hook.fetch_leads(self.target_date)
        self.log.info(f"Успешно получено {len(leads_data)} записей. Сохранение в {self.s3_key}")
        # Сохранение в S3 или возвращение пути через XCom
        return self.s3_key
```

## 8. Архитектура и эксплуатация продакшн-кластера Airflow

Для отказоустойчивой работы под нагрузкой в сотни DAG разворачивается распределенный кластер:

```
                  [ Load Balancer (Nginx / Ingress) ]
                                   │
              ┌────────────────────┴────────────────────┐
              ▼                                         ▼
     [ Webserver Replica 1 ]                   [ Webserver Replica 2 ]
              │                                         │
              └────────────────────┬────────────────────┘
                                   │
                     [ PostgreSQL HA Metastore ] ◄────────┐
                                   │                      │
              ┌────────────────────┴────────────────────┐ │
              ▼                                         ▼ │
     [ Scheduler Leader ]                      [ Scheduler Standby ]
              │                                         │
              └────────────────────┬────────────────────┘
                                   │ (Отправка task_id)
                                   ▼
                       [ Message Broker (Redis) ]
                                   │
              ┌────────────────────┼────────────────────┐
              ▼                    ▼                    ▼
     [ Celery Worker 1 ]  [ Celery Worker 2 ]  [ Celery Worker 3 ]
     (Concurrency: 16)    (Concurrency: 16)    (Concurrency: 16)
              │                    │                    │
              └────────────────────┴────────────────────┘
                                   │
                       (Сброс логов выполнения)
                                   ▼
                       [ Remote Storage: S3 / GCS ]
```

### Ключевые настройки производительности (`airflow.cfg`):
1. **`dag_dir_list_interval`** (по умолчанию 300 сек): как часто планировщик ищет новые файлы DAG.
2. **`min_file_process_interval`** (по умолчанию 30 сек): интервал повторного парсинга одного DAG-файла. Увеличение до 60–120 секунд снижает нагрузку на CPU планировщика на 40-50%.
3. **DAG Serialization**: начиная с Airflow 2.0 веб-сервер больше не исполняет Python-код DAG файлов на диске напрямую, а читает сериализованный JSON-граф из базы метаданных. Это устраняет риск взлома или падения веб-сервера из-за некорректного кода DAG.
4. **Remote Logging**: воркеры в Celery/K8s сбрасывают логи тасок в S3/GCS. Это позволяет безопасно удалять и пересоздавать узлы воркеров без потери логов для отладки.

## 9. Вопросы с собеседований

### Вопрос 1: Что произойдет, если в теле DAG-файла написать подключение к базе данных или тяжелый расчет вне оператора?
**Ответ**:
Это грубейший антипаттерн (Top-Level Python Code). Планировщик Airflow циклически исполняет (парсит) весь файл каждые несколько секунд для построения графа. Если внутри файла вне функций оператора расположен запрос к БД или внешний HTTP-запрос, планировщик будет открывать соединения к базе сотни раз в минуту, что приведет к исчерпанию пула соединений СУБД (Connection Starvation) и зависанию самого Scheduler. Любые подключения и расчеты должны находиться строго внутри метода `execute()` оператора или внутри Python-функции `PythonOperator`.

### Вопрос 2: Как безопасно перезапустить упавшую часть большого DAG без пересчета успешных шагов?
**Ответ**:
В веб-интерфейсе Airflow (или через CLI `airflow tasks clear`) можно очистить состояние конкретной упавшей задачи с флагом `Downstream`. В этом случае все предшествующие успешные задачи останутся в статусе `success`, а упавшая таска и все зависящие от нее downstream-шаги перейдут в статус `queued` и будут корректно пересчитаны.
