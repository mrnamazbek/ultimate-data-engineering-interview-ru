# Потоковая обработка и архитектуры реального времени (Уровень Senior)

Потоковая обработка данных (Stream Processing) требует принципиально иного инженерного мышления по сравнению с пакетной. На уровне Senior интервьюеры уделяют внимание гарантиям доставки сообщений, семантике Exactly-Once, обработке времени событий (Event Time vs Processing Time) и выбору архитектурного паттерна (Lambda против Kappa).

### Сравнение архитектур:
| Критерий | Lambda Architecture | Kappa Architecture |
|---|---|---|
| **Количество конвейеров** | Два независимых конвейера: быстрый (Speed) и точный (Batch) | Один универсальный потоковый конвейер |
| **Кодовая база** | Двойная (одна логика на Java/Flink для потока, вторая на SQL/Spark для батча) | Единая кодовая база для всех вычислений |
| **Сложность поддержки** | Высокая (постоянный рассинхрон бизнес-логики и результатов) | Значительно ниже |

*Современный консенсус*: Индустрия массово мигрирует на архитектуру **Kappa**, используя Apache Flink и Kafka, так как современные потоковые движки обеспечивают точность вычислений, не уступающую батчевым.

## 2. Гарантии доставки: At-Most-Once, At-Least-Once, Exactly-Once

1. **At-Most-Once (Не более одного раза)**:
   - Сообщения могут теряться, но никогда не дублируются. Продюсер отправляет сообщение и не ждет подтверждения (`acks=0`). Оффсет фиксируется до завершения обработки. Применяется для метрик телеметрии и логов, где потеря 0.1% данных не критична.
2. **At-Least-Once (Хотя бы один раз)**:
   - Сообщения гарантированно доставляются, но возможны дубликаты при сбоях сети. Продюсер требует подтверждения (`acks=all`), при сбое делает повторную отправку. Стандарт по умолчанию в большинстве систем.
3. **Exactly-Once (Строго один раз)**:
   - Каждое входящее событие влияет на конечное состояние системы ровно один раз.

### Как физически достигается Exactly-Once в продакшне:
Exactly-Once — это не магия, а комбинация трех инженерных механизмов:
1. **Идемпотентный продюсер Kafka (`enable.idempotence=true`)**: каждому сообщению присваивается порядковый номер `SequenceID`, и брокер отбрасывает дублирующие пакеты при повторной отправке.
2. **Двухфазный коммит (Two-Phase Commit / 2PC)**: координация транзакций между потребителем и приемником (например, между Flink и базой данных).
3. **Идемпотентная запись в приемник**: операции `UPSERT` или дедупликация по уникальному ключу на стороне целевого хранилища.

## 3. Обработка времени: Event Time, Ingestion Time, Processing Time

- **Event Time (Время события)**: момент, когда действие физически произошло на устройстве пользователя (сохраняется в полезной нагрузке события: `timestamp: 1726650000`). Единственное надежное время для бизнес-аналитики.
- **Ingestion Time (Время поступления)**: момент, когда брокер сообщений (Kafka) записал событие в свой топик.
- **Processing Time (Время обработки)**: текущие системные часы сервера, на котором в данный момент работает Spark или Flink воркер.

### Проблема задержки и рассинхрона времени:
Пользователь совершил покупку в поезде без связи в 12:00 (Event Time). Телефон отправил событие на сервер только в 15:00 (Processing Time). Если аналитика сгруппирована по `Processing Time`, покупка неверно попадет в дневной пик продаж вместо полуденного.

## 4. Водяные знаки (Watermarking) и поздние данные

Когда мы группируем поток по окнам на основе **Event Time**, мы не знаем, сколько времени ждать опаздывающие события из-за сетевых задержек.

### Что такое Watermark:
Водяной знак (Watermark) — это монотонно возрастающая временная метка, сигнализирующая движку: *«Мы уверены, что все события с Event Time раньше этой метки уже поступили в систему. Окно можно окончательно закрывать и отправлять результат в DWH»*.

```python
# Пример в PySpark Structured Streaming:
# Watermark = 10 минут. Опоздания до 10 минут будут включены в расчет,
# а события, отставшие более чем на 10 минут, будут отброшены.
streaming_df = spark.readStream \
    .format("kafka") \
    .load() \
    .withWatermark("event_timestamp", "10 minutes") \
    .groupBy(
        window("event_timestamp", "5 minutes"), # окно 5 минут
        "device_id"
    ) \
    .count()
```

## 5. Типы окон (Windowing Strategies)

1. **Tumbling Windows (Перекатывающиеся / Фиксированные окна)**:
   - Непересекающиеся окна фиксированного размера (например, 00:00–00:05, 00:05–00:10). Каждое событие принадлежит ровно одному окну.
2. **Sliding Windows (Скользящие окна)**:
   - Окна фиксированной длины, сдвигающиеся с заданным шагом (например, окно 10 минут с шагом сдвига 1 минута). Окна перекрываются, одно событие может учитываться в нескольких окнах.
3. **Session Windows (Сессионные окна)**:
   - Окна переменной длины, динамически формируемые по периодам активности пользователя. Если в течение заданного интервала неактивности (gap duration, например, 30 минут) новых событий нет — сессия закрывается.
