# 08. Векторные базы данных, алгоритмы ANN и RAG-архитектура

## 1. Введение: Зачем Data Engineer разбираться в векторных базах

С развитием больших языковых моделей (LLM) и поисковых систем изменился характер хранимых данных. Традиционные СУБД оптимизированы для точных скалярных сравнений: равенство чисел, попадание дат в диапазон, префиксы строк. 

Однако неструктурированные данные (тексты документов, аудиозаписи, изображения, логи действий) не поддаются строгому SQL-сравнению. Их преобразуют в **эмбеддинги (векторы чисел высокой размерности, например, 384, 768 или 1536 измерений)** через нейросетевые модели.

Векторная база данных — это специализированная система хранения, оптимизированная для выполнения операций **поиска $K$ ближайших соседей (K-Nearest Neighbors, KNN)** среди миллионов векторов за миллисекунды.

### Наглядно: документ становится единицей поиска

```text
Документ → chunks с устойчивыми ID → embeddings + metadata → search index
Запрос → embedding той же модели → кандидаты → контекст ответа
```

Изменение документа требует обновлять/удалять его чанки. Metadata и ACL — часть продукта, а не необязательное дополнение к вектору.

## 2. Метрики векторного расстояния

Для определения того, насколько два объекта семантически похожи, вычисляется расстояние между их векторными представлениями $u$ и $v$:

| Метрика | Формула | Особенности и применение |
| :--- | :--- | :--- |
| **Косинусное сходство (Cosine Similarity)** | $\cos(\theta) = \frac{u \cdot v}{\|u\| \|v\|}$ | Оценивает угол между векторами независимо от их длины (нормы). Диапазон от -1 до 1. Идеально для текстов разной длины. |
| **Евклидово расстояние ($L2$ Distance)** | $d(u, v) = \sqrt{\sum (u_i - v_i)^2}$ | Геометрическое расстояние между концами векторов в пространстве. Чувствительно к абсолютной величине значений. |
| **Скалярное произведение (Dot Product / Inner Product)** | $u \cdot v = \sum u_i v_i$ | Самая быстрая вычислительная операция. Если векторы предварительно нормализованы к единичной длине ($\|u\| = 1$), скалярное произведение математически эквивалентно косинусному сходству. |

### Наглядно: направление и длина вектора

```text
Query=(1,0), A=(1,0), B=(10,0)
Cosine similarity: A=1, B=1 → одинаковое направление
Dot product: A=1, B=10 → влияет длина
L2 distance: A=0, B=9 → отличается расстояние
```

Если все векторы нормированы, ранжирование метрик тесно связано. Для нулевого вектора cosine требует специальной обработки; метрика должна соответствовать модели и индексу.

## 3. Алгоритмы приближенного поиска (ANN - Approximate Nearest Neighbors)

Точный поиск ближайших соседей (**Flat / Brute-force**) требует сканирования всех $N$ векторов в базе и вычисления расстояния до каждого. При 10 миллионах векторов размерности 1536 такой запрос занимает секунды и требует гигантских вычислительных мощностей.

Для продакшена применяются алгоритмы приближенного поиска (ANN), которые находят 95-99% истинных ближайших соседей за доли миллисекунд.

### 3.1. IVFFlat (Inverted File Flat)

**Идея**: Пространство векторов разбивается на $K$ кластеров с помощью алгоритма $k$-means. 

```
[ Все векторы базы ] ──(k-means)──► [ Вороной-кластер 1 (Центроид C1) ]
                                  [ Вороной-кластер 2 (Центроид C2) ]
                                  [ Вороной-кластер 3 (Центроид C3) ]
```

1. На этапе индексации данные группируются вокруг центроидов.
2. При поиске вектор запроса сравнивается только с центроидами, выбираются $P$ ближайших кластеров (`nprobe`), и поиск идет только среди векторов внутри этих кластеров.
- **Параметры**:
  - `nlist`: количество кластеров при обучении индекса.
  - `nprobe`: количество кластеров, просматриваемых при выполнении запроса (чем выше `nprobe`, тем выше точность Recall, но больше задержка).

### 3.2. HNSW (Hierarchical Navigable Small World)

HNSW является стандартом де-факто в индустрии векторного поиска благодаря наилучшему соотношению задержки (Latency) и точности (Recall).

**Идея**: Векторы организуются в многоуровневый граф (по аналогии со списком с пропусками — Skip List).

```
Уровень 2 (Редкий):    [V1] ───────────────────────────► [V9]
                        │                                  │
Уровень 1 (Средний):   [V1] ────────► [V4] ─────────────► [V9]
                        │              │                   │
Уровень 0 (Плотный):   [V1] ──► [V2] ─► [V4] ──► [V7] ──► [V9]
```

1. Поиск начинается с верхнего слоя с длинными связями (быстрое перемещение в нужный район пространства).
2. Затем алгоритм спускается на нижние слои, выполняя локальную жадную маршрутизацию.
- **Ключевые параметры HNSW**:
  - `m`: Максимальное количество двунаправленных связей у каждого узла (обычно 16-64). Больше связей — выше Recall, но больше расход памяти.
  - `ef_construction`: Размер динамического списка кандидатов при построении индекса. Влияет на время построения индекса.
  - `ef_search`: Размер списка кандидатов при выполнении поискового запроса. Позволяет динамически балансировать между скоростью ответа и качеством выдачи.

### 3.3. Квантование (Product Quantization, PQ & Scalar Quantization, SQ)

Векторы размерности 1536 в формате `float32` требуют 6 КБ памяти на один вектор. 100 миллионов векторов потребуют 600 ГБ оперативной памяти только на сами векторы, без учета графа HNSW.

- **Scalar Quantization (SQ8)**: Сжатие каждого числа из `float32` (4 байта) в `int8` (1 байт). Уменьшает объем RAM в 4 раза с потерей менее 1% точности.
- **Product Quantization (PQ)**: Разделение вектора на подвекторы и замена их индексами из кодовой книги. Уменьшает объем памяти в 8-16 раз.

### Наглядно: IVF, HNSW и квантование

```text
IVFFlat: векторы → кластеры → query ищет несколько ближайших списков
HNSW: верхние уровни графа → грубый маршрут → нижний слой → кандидаты
PQ: части вектора → код ближайшего центра → компактное приближение
```

Больший search budget обычно улучшает recall ценой задержки. Измеряйте на своих запросах; ANN не обещает точный top-k и универсальную O(log N) для каждого набора.

## 4. Архитектура RAG (Retrieval-Augmented Generation) для Data Engineer

Data Engineer в ML/LLM проектах отвечает за надежность и масштабируемость пайплайна подачи знаний в LLM:

```
[ Источники: PDF, Confluence, DB, S3 ]
                   │
                   ▼ (Batch / Streaming Ingestion)
[ 1. Chunking Pipeline: Рекурсивное разбиение с перекрытием (Chunk: 512, Overlap: 64) ]
                   │
                   ▼
[ 2. Embedding Generation (Batch inference через GPU worker или API) ]
                   │
                   ▼
[ 3. Векторное хранилище (pgvector / Qdrant / Milvus) + Метаданные (ACL, tenant, date) ]
                   │
  ┌────────────────┴────────────────────────┐
  ▼                                         ▼
[ Векторный поиск (Dense) ]      [ Полнотекстовый поиск BM25 (Sparse) ]
  │                                         │
  └────────────────┬────────────────────────┘
                   ▼
[ 4. Reciprocal Rank Fusion (RRF) & Reranker (Cross-Encoder) ]
                   │
                   ▼
[ 5. Контекст передан в LLM для генерации ответа ]
```

### Пре-фильтрация (Pre-filtering) vs Пост-фильтрация (Post-filtering)

В корпоративных системах векторный поиск обязательно сопровождается фильтрацией по правам доступа и метаданным (`tenant_id = 'acme' AND department = 'finance'`):
- **Пост-фильтрация (Post-filtering)**: Сначала векторный индекс находит 100 ближайших документов, а затем отбрасываются те, у которых нет прав доступа. **Опасный антипаттерн**: если пользователю доступны только 2 документа из 100 найденных, он получит пустой или неполный ответ.
- **Пре-фильтрация (Pre-filtering)**: Векторный индекс на этапе обхода графа HNSW учитывает скалярный битовый фильтр (Filtered HNSW). Возвращается ровно $K$ релевантных векторов, к которым у пользователя есть доступ.

### Наглядно: фильтр доступа и качество результатов

```text
Dense candidates + sparse/BM25 candidates → объединение → rerank
Metadata/ACL policy → разрешённые документы → контекст → генерация
Post-filter: 10 кандидатов, 9 запрещены → осталось 1 вместо нужных 10
```

Фильтрация должна исключить утечку запрещённого контекста. Pre/post-filter и iterative scan меняют recall, latency и доступность результатов; уточняйте реализацию.

## 5. Практический пример: pgvector в PostgreSQL

Расширение `pgvector` превращает стандартный PostgreSQL в полноценную векторную базу данных для объемов до десятков миллионов векторов.

```sql
-- 1. Подключение расширения
CREATE EXTENSION IF NOT EXISTS vector;

-- 2. Создание таблицы с метаданными и векторным полем (размерность 1536 для OpenAI embeddings)
CREATE TABLE enterprise_documents (
    doc_id bigserial PRIMARY KEY,
    tenant_id text NOT NULL,
    category text NOT NULL,
    chunk_text text NOT NULL,
    created_at timestamptz DEFAULT now(),
    embedding vector(1536) NOT NULL
);

-- 3. Создание HNSW индекса с косинусным расстоянием (vector_cosine_ops)
CREATE INDEX idx_docs_hnsw_cosine ON enterprise_documents 
USING hnsw (embedding vector_cosine_ops)
WITH (m = 24, ef_construction = 128);

-- 4. Создание B-Tree индекса по метаданным для эффективной пре-фильтрации
CREATE INDEX idx_docs_tenant_category ON enterprise_documents (tenant_id, category);

-- 5. Поисковый запрос с пре-фильтрацией и настройкой точности
SET hnsw.ef_search = 64;

SELECT 
    doc_id, 
    chunk_text, 
    1 - (embedding <=> '[0.012, -0.043, 0.089, ...]'::vector) AS cosine_similarity
FROM enterprise_documents
WHERE tenant_id = 'company_corp' 
  AND category = 'contracts'
ORDER BY embedding <=> '[0.012, -0.043, 0.089, ...]'::vector ASC
LIMIT 5;
```

*Операторы pgvector:*
- `<=>` : Косинусное расстояние (Cosine Distance = $1 - \cos(\theta)$).
- `<->` : Евклидово расстояние ($L2$).
- `<#>` : Отрицательное скалярное произведение (Negative Inner Product).

### Наглядно: проверка индекса pgvector

```text
ORDER BY embedding <-> query LIMIT k → L2 поиск
Index operator class должна соответствовать метрике
Exact baseline → измерить recall ANN при тех же фильтрах и k
```

Используйте EXPLAIN и сравнение с точным результатом. При фильтрах ANN может вернуть меньше k; настройки iterative scan зависят от версии pgvector.

## 6. Вопросы с Senior собеседований

### Вопрос 1: В чем разница между специализированной векторной СУБД (Qdrant, Milvus, Pinecone) и pgvector в PostgreSQL?
**Ответ**:
- **pgvector** идеален, если у вас уже есть PostgreSQL, объем векторов не превышает нескольких миллионов, и вам критически важна транзакционная целостность (ACID), объединение (JOIN) с бизнес-таблицами и простота инфраструктуры.
- **Специализированные СУБД (Milvus, Qdrant)** написаны на C++/Rust/Go, поддерживают горизонтальное шардирование на десятки нод, миллиарды векторов, продвинутые механизмы квантования (Product Quantization) и хранение графов на NVMe дисках без полной загрузки в RAM. Они выбираются при экстремальных нагрузках и жестких SLA (< 10 мс).

### Вопрос 2: Почему для качественного поиска часто недостаточно только векторного индекса и требуется Hybrid Search?
**Ответ**:
Векторный поиск (Dense Retrieval) отлично улавливает общий контекст и смысл, но плохо справляется с точным поиском по специфическим идентификаторам, аббревиатурам, артикулам товаров (SKU), фамилиям и кодам ошибок (например, `"ERROR_404_NULL_POINTER"`). Традиционный полнотекстовый поиск (Sparse / BM25) находит точные вхождения слов, но слеп к синонимам. **Гибридный поиск (Dense + Sparse)** объединяет оба подхода через ранжирование RRF (Reciprocal Rank Fusion) и выдает стабильно лучший результат.
