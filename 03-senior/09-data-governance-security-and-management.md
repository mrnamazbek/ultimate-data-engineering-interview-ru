# 09. Управление данными, корпоративная безопасность и PyDeequ (Data Governance & Security)

## 1. Введение: Почему платформе данных недостаточно быть просто быстрой

На начальных этапах развития дата-платформы компании фокусируются на скорости: как быстро перелить терабайты из источников в Data Lake или DWH.

Однако по мере роста возникают критические проблемы:
- Аналитики не могут найти нужные данные и тратят недели на выяснение, в какой таблице лежит «настоящая выручка» (проблема Data Discovery).
- Разработчики не знают, кто использует их таблицы, и случайно ломают финансовые отчеты (отсутствие Data Lineage).
- Утечки конфиденциальных персональных данных (PII) приводят к штрафам регуляторов (отсутствие Data Security).
- В хранилище накапливаются дубли и мусор, искажающие решения топ-менеджмента (деградация Data Quality).

Дисциплины **Data Governance (Руководство данными)** и **Data Security (Безопасность данных)** регламентируют правила владения, каталогизации, защиты и контроля качества информации на уровне всей организации.

## 2. Стандарт DAMA DMBOK и разделение ролей

Международный стандарт DAMA DMBOK (Data Management Body of Knowledge) определяет колесо управления данными из 11 областей, ядром которого является **Data Governance**.

```
                           [ DATA GOVERNANCE ]
                           (Стратегия и правила)
                                     │
    ┌────────────────┬───────────────┼───────────────┬────────────────┐
    ▼                ▼               ▼               ▼                ▼
[Архитектура]   [Качество]     [Безопасность]   [Метаданные]    [Интеграция]
```

### Разделение зон ответственности (Data Roles):
1. **Data Owner (Владелец данных)**:
   - Представитель бизнес-подразделения (например, Директор по маркетингу или Главный бухгалтер).
   - Принимает решения о том, кто имеет право доступа к данным его домена, определяет критичность метрик и утверждает бизнес-правила.
2. **Data Steward (Куратор данных)**:
   - Бизнес-аналитик или дата-аналитик, связующее звено между бизнесом и разработкой.
   - Ведет **Бизнес-глоссарий (Business Glossary)**, следит за единым пониманием терминов (что такое «активный пользователь»), формулирует правила валидации качества данных.
3. **Data Custodian / Data Engineer (Технический хранитель)**:
   - Инженер данных и администратор баз данных.
   - Отвечает за физическое хранение, шифрование, производительность, надежность ETL-пайплайнов и реализацию утвержденных политик доступа в коде.

## 3. Каталоги данных (Data Catalog) и Происхождение данных (Data Lineage)

### 3.1. Зачем нужен Data Catalog
**Data Catalog (Каталог данных)** — это единая поисковая система и метаинформационный портал для всех дата-активов компании (таблицы в Postgres, топики Kafka, бакеты S3, витрины Snowflake, дашборды Tableau).

Популярные корпоративные open-source решения:
- **LinkedIn DataHub**: современный каталог на базе метамоделей графов и событий Kafka.
- **Lyft Amundsen**: поисковый движок на базе Elasticsearch и Neo4j.
- **Apache Atlas**: классический инструмент экосистемы Hadoop с тесной интеграцией с Ranger.

### 3.2. Data Lineage (Происхождение данных)
Data Lineage показывает сквозной граф движения данных от систем-источников до конечных потребителей:

```
[ CRM Postgres ] ──► [ Kafka Topic ] ──► [ Spark (Bronze) ] ──► [ Iceberg (Gold) ] ──► [ Tableau Dashboard ]
```

**Зачем нужен Lineage:**
1. **Root-Cause Analysis (Анализ первопричин сбоя)**: если на дашборде директора пропали данные за вчерашний день, инженер по графу Lineage мгновенно видит, какой конкретно upstream-пайплайн упал 5 шагов назад.
2. **Impact Analysis (Оценка влияния изменений)**: перед тем как удалить или переименовать столбец в таблице, инженер видит полный список downstream-дашбордов и ML-моделей, которые сломаются от этого действия.
3. **OpenLineage**: открытый стандарт трассировки Lineage, поддерживаемый Spark, Airflow, dbt и Great Expectations.

## 4. Информационная безопасность данных (Data Security)

### 4.1. Управление доступом: RBAC против ABAC

| Метод | Принцип работы | Пример правила | Применимость |
| :--- | :--- | :--- | :--- |
| **RBAC (Role-Based Access Control)** | Права назначаются статическим ролям пользователей | Роль `marketing_analyst` имеет `SELECT` на схему `analytics_marketing` | Простые системы с небольшим количеством групп пользователей |
| **ABAC (Attribute-Based Access Control)** | Права вычисляются динамически на основе атрибутов субъекта, объекта и контекста | Разрешить чтение, ЕСЛИ `user.department == data.department AND request.time == work_hours AND request.location == 'office'` | Крупные корпорации со сложными политиками безопасности |

### 4.2. Маскирование и деперсонализация данных (Data Masking)

Для защиты персональных данных (PII: ФИО, паспорта, телефоны, кредитные карты) в средах разработки (Dev/Stage) и аналитических витринах применяются два подхода:

1. **Статическое маскирование (Static Data Masking, SDM)**:
   Применяется при выгрузке данных из продакшна в тестовые контуры. Исходные значения навсегда заменяются сгенерированными синтетическими данными (например, библиотека Faker в Python).
2. **Динамическое маскирование (Dynamic Data Masking, DDM)**:
   Данные хранятся в БД в исходном виде, но при выполнении `SELECT` СУБД (PostgreSQL, Snowflake, ClickHouse) динамически скрывает часть символов в зависимости от роли текущего пользователя:
   - Администратор видит: `+7-999-123-45-67`
   - Аналитик видит: `+7-***-***-**-67`

### 4.3. Токенизация против Шифрования
- **Шифрование (AES-256)**: математическое обратимое преобразование с использованием криптографического ключа. Если ключ скомпрометирован, злоумышленник расшифрует весь массив данных.
- **Токенизация (Tokenization)**: реальное значение (номер кредитной карты) заменяется случайным строковым суррогатом (токеном). Реальная связка хранится в строго изолированном защищенном хранилище (Token Vault). В аналитическое хранилище попадает только нечувствительный токен.

## 5. Распределенный аудит качества данных: AWS Deequ / PyDeequ на Apache Spark

Когда объем данных превышает десятки терабайт, инструменты вроде Great Expectations на одной машине перестают справляться из-за нехватки оперативной памяти.

**Deequ** (разработано инженерами Amazon для внутреннего аудита петабайтных датасетов AWS) — это распределенная библиотека поверх Apache Spark, вычисляющая метрики качества данных за один параллельный проход по распределенному датасету.

### 5.1. Архитектура PyDeequ

PyDeequ предоставляет 4 ключевых компонента:
1. **AnalysisRunner**: масштабируемое вычисление статистических профилей данных.
2. **VerificationSuite**: декларативная проверка правил качества (Quality Constraints).
3. **MetricsRepository**: долговременное хранение истории метрик качества (в файлах JSON или базе данных) для отслеживания деградации во времени.
4. **Constraint Suggestion**: автоматический статистический анализ датасета с выдачей рекомендаций по правилам валидации.

### 5.2. Практический пример: Аудит датасета клиентов на PySpark с PyDeequ

```python
from pyspark.sql import SparkSession
import pydeequ
from pydeequ.analyzers import AnalysisRunner, Size, Completeness, Compliance, ApproxCountDistinct
from pydeequ.checks import Check, CheckLevel, ConstrainableDataTypes
from pydeequ.verification import VerificationSuite, VerificationResult

# 1. Инициализация Spark с пакетом PyDeequ
spark = SparkSession.builder \
    .appName("DataQualityDeequ") \
    .config("spark.jars.packages", pydeequ.deequ_maven_coord) \
    .config("spark.jars.excludes", pydeequ.f2j_maven_coord) \
    .getOrCreate()

# 2. Загрузка распределенного датасета клиентов
df = spark.read.parquet("s3://company-lakehouse-silver/clients/")

# 3. Анализ статистических профилей (AnalysisRunner)
analysisResult = AnalysisRunner(spark) \
    .onData(df) \
    .addAnalyzer(Size()) \
    .addAnalyzer(Completeness("client_id")) \
    .addAnalyzer(Completeness("email")) \
    .addAnalyzer(ApproxCountDistinct("client_id")) \
    .addAnalyzer(Compliance("age_valid", "age >= 18 AND age <= 120")) \
    .run()

analysisResult_df = AnalyzerContext.successMetricsAsDataFrame(spark, analysisResult)
analysisResult_df.show(truncate=False)

# 4. Декларативная проверка правил качества (VerificationSuite)
check = Check(spark, CheckLevel.Error, "Client Integrity Checks")

checkResult = VerificationSuite(spark) \
    .onData(df) \
    .addCheck(
        check.hasSize(lambda size: size >= 10000) # Минимум 10 000 клиентов
             .isComplete("client_id")             # client_id не содержит NULL
             .isUnique("client_id")               # client_id строго уникален
             .hasCompleteness("email", lambda c: c >= 0.95) # Заполненность email >= 95%
             .isContainedIn("status", ["ACTIVE", "BLOCKED", "PENDING"])
             .isNonNegative("total_spent")
    ) \
    .run()

# 5. Оценка результатов и принятие решения
checkResult_df = VerificationResult.checkResultsAsDataFrame(spark, checkResult)
checkResult_df.show(truncate=False)

if checkResult.status != "Success":
    raise ValueError("Качество данных ниже допустимого порога! Запись в Gold слой заблокирована.")
```

## 6. Вопросы с собеседований

### Вопрос 1: В чем разница между Deequ и Great Expectations? Что выбрать для проекта?
**Ответ**:
- **Great Expectations (GX)** ориентирован на гибкость, генерацию красивой интерактивной документации (Data Docs) и интеграцию с широким спектром источников (SQL-базы, Pandas, Polars). Отлично подходит для этапа dbt/ELT и небольших/средних датасетов.
- **Deequ / PyDeequ** спроектирован специально для распределенной обработки петабайтов данных внутри ядра Apache Spark. Он транслирует все проверки качества в единый Spark Job и вычисляет метрики параллельно на кластере без выгрузки данных на Driver-ноду.

### Вопрос 2: Как выполнить требования "Права на забвение" (Right to be Forgotten по GDPR) в Data Lake на S3/HDFS с Parquet файлами?
**Ответ**:
В классическом Data Lake файлы Parquet неизменяемы (immutable). Удаление одного пользователя требовало бы полного переписывания терабайтных партиций.
Современное решение:
1. Использование транзакционных слоев **Apache Iceberg / Delta Lake**: операция `DELETE FROM lake.users WHERE user_id = ?` выполняет точечную перезапись только затронутых файлов (Copy-on-Write) или создает файлы позиционных удалений (Merge-on-Read).
2. Псевдонимизация / Криптографическое стирание (Crypto-Shredding): чувствительные данные пользователя шифруются его индивидуальным ключом шифрования. По запросу на удаление достаточно уничтожить ключ пользователя в Key Management Service (KMS). После этого исторические данные в Parquet превращаются в нерасшифровываемый мусор, удовлетворяя требования регулятора без физической перезаписи файлов.
