# Моделирование данных и архитектура DWH (Уровень Middle)

Размерное моделирование (Dimensional Modeling) по методологии Ральфа Кимбалла (Ralph Kimball) — ключевой навык для проектирования корпоративных хранилищ данных (DWH) и аналитических витрин. На собеседованиях уровня Middle этот блок проверяют глубже всего, так как ошибки в моделировании приводят к деградации производительности и неверным отчетам.

---

## 1. Четыре шага проектирования по Кимбаллу

При проектировании любой витрины или хранилища инженер данных проходит 4 строгих этапа:
1. **Выбор бизнес-процесса**: моделируется конкретная деятельность компании (продажи, доставка, регистрация пользователей, выдача кредитов).
2. **Определение зерна / гранулярности (Grain)**: точный уровень детализации одной строки в таблице фактов. *Правило*: «Одна строка таблицы фактов представляет собой отдельную позицию в кассовом чеке клиента».
3. **Определение измерений (Dimensions)**: контекст события — «кто, где, когда, какой товар» (`dim_customers`, `dim_stores`, `dim_products`, `dim_date`).
4. **Определение фактов (Facts)**: числовые измеримые показатели события (`quantity`, `sales_amount`, `discount`).

## 2. Схемы организации данных: «Звезда» против «Снежинки»

```text
       Схема "Звезда" (Star Schema)                 Схема "Снежинка" (Snowflake Schema)
       
       +---------------+                            +---------------+      +-------------------+
       | dim_customers |                            | dim_customers | ---> | dim_customer_city |
       +-------+-------+                            +-------+-------+      +-------------------+
               |                                            |
+--------------+-------------+               +--------------+-------------+
|        fact_sales          |               |        fact_sales          |
+--------------+-------------+               +--------------+-------------+
               |                                            |
       +-------+-------+                            +-------+-------+      +-------------------+
       | dim_products  |                            | dim_products  | ---> |   dim_categories  |
       +---------------+                            +---------------+      +-------------------+
```

### Сравнение схем:
| Критерий | Схема «Звезда» (Star Schema) | Схема «Снежинка» (Snowflake Schema) |
|---|---|---|
| **Уровень нормализации** | Таблицы измерений полностью денормализованы (1NF / 2NF) | Таблицы измерений нормализованы (3NF) и разбиты на подтаблицы |
| **Количество JOIN** | Минимальное (1 шаг соединения факта с каждым измерением) | Большое (каскадные соединения справочников) |
| **Скорость аналитики** | Максимальная (оптимизирована под колоночные СУБД) | Медленнее из-за множества операций `JOIN` |
| **Избыточность данных** | Выше (строковые названия категорий дублируются) | Минимальная (устранена избыточность) |
| **Сложность поддержки** | Простая структура, интуитивно понятная BI-аналитикам | Сложные графы связей |

## 3. Классификация фактов (Types of Facts)

1. **Аддитивные факты (Additive Facts)**:
   - Значения можно суммировать по всем измерениям модели (по времени, магазинам, клиентам, продуктам).
   - *Примеры*: `sales_amount` (выручка), `units_sold` (количество проданных единиц).
2. **Полуаддитивные факты (Semi-Additive Facts)**:
   - Значения можно суммировать по одним измерениям, но нельзя по другим (в частности, нельзя суммировать по измерению времени).
   - *Пример*: `account_balance` (баланс банковского счета на конец дня) или остаток товара на складе. Суммировать балансы по всем клиентам на одну дату имеет смысл, но сложение баланса за понедельник, вторник и среду дает бессмысленную цифру. Для измерения времени применяются функции `AVG()`, `FIRST()` или `LAST()`.
3. **Неаддитивные факты (Non-Additive Facts)**:
   - Значения, которые нельзя корректно складывать ни по одному измерению (обычно коэффициенты, проценты, удельные величины).
   - *Примеры*: `unit_price` (цена за единицу), `discount_percentage` (процент скидки), `margin_rate`.
   - *Правило*: Неаддитивные факты не сохраняют как агрегаты, а сохраняют в таблице фактов числитель и знаменатель (`total_discount_amount` и `total_price`), вычисляя средневзвешенный процент в момент запроса.
4. **Безфакторные таблицы фактов (Factless Fact Tables)**:
   - Таблицы фактов, не содержащие числовых метрик, а фиксирующие факт свершения события или срез условий.
   - *Примеры*: Таблица посещаемости студентами лекций (`student_id`, `course_id`, `date_id`), фиксация кликов или рекламных показов.

## 4. Специальные типы измерений (Types of Dimensions)

- **Согласованное измерение (Conformed Dimension)**: измерение, имеющее одинаковую структуру и смысловое значение во всей компании и связанное с несколькими разными таблицами фактов. Классический пример: `dim_date` и `dim_customer`, используемые одновременно в `fact_sales` и `fact_support_tickets`.
- **Вырожденное измерение (Degenerate Dimension)**: атрибут, являющийся измерением по смыслу, но не имеющий собственных описательных атрибутов и хранящийся непосредственно в таблице фактов. Типичный пример: номер счета (`invoice_number`), номер заказа (`order_id`), номер чека.
- **Мусорное измерение (Junk Dimension)**: объединение множества разрозненных булевых флагов, статусов и индикаторов (`is_promotional`, `payment_status`, `delivery_flag`) в одну справочную таблицу с суррогатным ключом для предотвращения раздувания количества внешних ключей в таблице фактов.
- **Ролевое измерение (Role-Playing Dimension)**: одна физическая таблица измерения, выступающая в таблице фактов в разных логических ролях через разные внешние ключи. Например, таблица `dim_date` соединяется с таблицей фактов трижды: как дата оформления заказа (`order_date_id`), дата оплаты (`payment_date_id`) и дата доставки (`delivery_date_id`).

## 5. Медленно меняющиеся измерения (SCD — Slowly Changing Dimensions)

На собеседовании обязательно спрашивают, как отслеживать изменения атрибутов сущностей (например, переезд клиента в другой город).

| Тип SCD | Механизм работы | Сохранение истории | Когда применять |
|---|---|---|---|
| **Type 0** | Данные фиксируются один раз и никогда не меняются | Нет | Дата рождения, дата первой регистрации |
| **Type 1** | Старое значение перезаписывается новым значением | Нет (история утеряна) | Исправление грамматических ошибок, опечаток в именах |
| **Type 2** | Добавляется новая строка с новой версией, суррогатным ключом, датами `valid_from`, `valid_to` и флагом `is_current` | Полная история | Смена адреса клиента, смена грейда сотрудника, изменение цены товара (основной стандарт DWH) |
| **Type 3** | В существующую таблицу добавляются колонки `previous_value` и `current_value` | Только предыдущее и текущее состояние | Анализ динамики предыдущего и текущего региона продаж |
| **Type 4** | Основная таблица хранит только текущие данные, а все исторические изменения записываются в отдельную таблицу аудита/истории | Да (в отдельной таблице) | Высоконагруженные системы, где важно иметь компактную основную таблицу |
| **Type 6** | Гибрид типов 1, 2 и 3 ($1 + 2 + 3 = 6$): в строке Type 2 дополнительно хранится колонка с текущим актуальным значением | Полная история + быстрый доступ к актуальному значению | Сложная корпоративная аналитика |

### Пример структуры таблицы SCD Type 2
```sql
CREATE TABLE dim_customers_scd2 (
    customer_sk BIGINT PRIMARY KEY,       -- Суррогатный ключ версии
    customer_id INT NOT NULL,             -- Естественный бизнес-ключ клиента
    full_name VARCHAR(255),
    city VARCHAR(100),
    valid_from TIMESTAMP NOT NULL,        -- Начало действия версии
    valid_to TIMESTAMP,                   -- Конец действия версии (NULL или 9999-12-31)
    is_current BOOLEAN NOT NULL           -- Флаг актуальности
);

-- Выборка фактов с исторически точным состоянием клиента на момент совершения продажи:
SELECT 
    f.sale_id,
    f.amount,
    c.city AS customer_city_at_sale_time
FROM fact_sales f
JOIN dim_customers_scd2 c 
  ON f.customer_id = c.customer_id
 AND f.sale_timestamp >= c.valid_from 
 AND (f.sale_timestamp < c.valid_to OR c.valid_to IS NULL);
```
