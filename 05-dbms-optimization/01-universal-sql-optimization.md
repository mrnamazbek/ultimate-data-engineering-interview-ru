# Универсальные паттерны и правила оптимизации SQL-запросов

Данный модуль содержит общие фундаментальные правила оптимизации SQL, применимые к любой реляционной и аналитической СУБД. Следование этим принципам позволяет ускорить выполнение медленных запросов в десятки и сотни раз еще до настройки параметров серверов.

---

## 1. Анализ планов выполнения запросов (EXPLAIN)

Оптимизация без анализа плана выполнения — это работа вслепую. План показывает, какие физические алгоритмы выбрал оптимизатор СУБД для извлечения данных.

### Базовые типы сканирования таблиц:
- **Seq Scan / Full Table Scan (Последовательное сканирование)**: СУБД читает абсолютно все страницы таблицы с диска. Оправдано, если требуется выбрать более 15–20% строк таблицы, но катастрофически медленно для точечных выборок на миллионах записей.
- **Index Scan (Сканирование по индексу)**: СУБД находит адреса нужных строк в дереве индекса, а затем обращается к страницам таблицы за значениями остальных колонок (Random I/O).
- **Index Only Scan / Covering Index Scan**: Все запрошенные колонки уже содержатся в самом индексе. СУБД вообще не читает саму таблицу. Это самый быстрый сценарий чтения.
- **Bitmap Index Scan (в PostgreSQL)**: Сначала собирается битовая карта страниц, содержащих совпадения, а затем страницы читаются последовательно (Sequential I/O), что быстрее случайных чтений.

### Базовые типы соединений (JOIN):
1. **Nested Loop (Вложенные циклы)**: Для каждой строки внешней таблицы ищется совпадение во внутренней (обычно по индексу). Идеально для небольших наборов данных ($< 10\,000$ строк).
2. **Hash Join**: СУБД строит хэш-таблицу в оперативной памяти по меньшей таблице, а затем сканирует большую таблицу и ищет совпадения в хэш-таблице. Стандарт для соединений средних и больших таблиц по условию равенства (`=`).
3. **Merge Join**: Обе таблицы предварительно сортируются по ключу соединения, после чего происходит параллельное слияние. Эффективно, если данные уже физически отсортированы на диске (например, по первичному ключу или кластерному индексу).

## 2. Принцип SARGable-предикатов (Search Argument Able)

Предикат называется **SARGable**, если движок базы данных может напрямую применить индекс для фильтрации строк. Если колонка обернута в функцию или участвует в математической операции, индекс **отключается**, и СУБД переходит к полному сканированию всей таблицы (`Seq Scan`).

### Антипаттерны и их исправление:

#### Пример 1: Использование функций над колонками в WHERE
```sql
-- ПЛОХО (Non-SARGable): функция LOWER() вызывается для каждой строки таблицы, индекс idx_email не используется!
SELECT id, name FROM users WHERE LOWER(email) = 'ivan@example.com';

-- ХОРОШО (SARGable): ищем по чистому значению или создаем функциональный индекс CREATE INDEX idx_lower_email ON users(LOWER(email))
SELECT id, name FROM users WHERE email = 'ivan@example.com';
```

#### Пример 2: Работа с датами и усечениями
```sql
-- ПЛОХО: функция DATE_TRUNC или YEAR отключает B-Tree индекс по created_at
SELECT * FROM orders WHERE DATE_TRUNC('year', created_at) = '2026-01-01';

-- ХОРОШО: замена на диапазон значений (Range Scan по индексу)
SELECT * FROM orders 
WHERE created_at >= '2026-01-01' 
  AND created_at < '2027-01-01';
```

#### Пример 3: Поиск по маске (LIKE)
```sql
-- ПЛОХО: ведущий процент '%text' делает невозможным использование B-Tree индекса (Seq Scan)
SELECT * FROM products WHERE sku LIKE '%9912';

-- ХОРОШО: поиск по префиксу эффективно использует B-Tree индекс
SELECT * FROM products WHERE sku LIKE '9912%';
-- Для поиска по любой части строки используйте триграммные индексы (GIN / pg_trgm).
```

#### Пример 4: Неявное приведение типов (Implicit Casting)
Если колонка имеет тип `VARCHAR`, а в запросе передано число без кавычек (`phone = 79991234567`), СУБД неявно оборачивает колонку в функцию приведения типа `CAST(phone AS BIGINT)`, что полностью отключает индекс по номеру телефона.

## 3. Оптимизация пагинации: OFFSET против Keyset Pagination

### Почему пагинация через `LIMIT ... OFFSET` убивает производительность:
```sql
-- Медленный запрос: на странице 10 000
SELECT id, title, created_at
FROM articles
ORDER BY id ASC
LIMIT 20 OFFSET 200000;
```
*Что делает СУБД под капотом*: база вынуждена прочитать с диска и отсортировать **200 020 строк**, затем отбросить первые 200 000 и вернуть только последние 20. На высоких номерах страниц время ответа возрастает от миллисекунд до десятков секунд.

### Решение: Курсорная пагинация (Keyset Pagination)
Мы запоминаем максимальный `id` с предыдущей страницы и используем условие `WHERE`:
```sql
-- Быстрый запрос: O(1) время ответа независимо от глубины страниц
SELECT id, title, created_at
FROM articles
WHERE id > 200000  -- прямой прыжок в дерево индекса B-Tree
ORDER BY id ASC
LIMIT 20;
```

## 4. Антипаттерн N+1 запросов

### В чем суть проблемы:
Типичная ошибка при использовании ORM (Hibernate, SQLAlchemy, Django ORM). 
1. Сначала приложение делает 1 запрос на получение 100 заказов:
   `SELECT * FROM orders LIMIT 100;`
2. Затем в цикле для каждого заказа делает отдельный запрос за данными клиента:
   `SELECT * FROM customers WHERE id = 1;`
   `SELECT * FROM customers WHERE id = 2;`
   ... (всего 101 сетевой запрос к базе данных).

### Как исправить:
Использовать явное объединение (`JOIN`) или пакетную загрузку связанных сущностей (`IN (...)`):
```sql
SELECT 
    o.id AS order_id,
    o.amount,
    c.id AS customer_id,
    c.name AS customer_name
FROM orders o
JOIN customers c ON o.customer_id = c.id
LIMIT 100;
```

## 5. Чек-лист оптимизации любого SQL-запроса

1. Замените `SELECT *` на конкретный список необходимых полей.
2. Проверьте план запроса через `EXPLAIN ANALYZE` и найдите шаги с наибольшей стоимостью (`Cost`) и фактическим временем (`Actual Time`).
3. Убедитесь, что все предикаты в `WHERE` и `ON` являются SARGable (нет функций над колонками).
4. Проверьте кардинальность (число уникальных значений) полей для составного индекса: наиболее селективная колонка (с максимальным разнообразием значений) должна стоять **первой** в индексе.
5. Для подзапросов с проверкой существования используйте `EXISTS` вместо `IN`.
6. Используйте `UNION ALL` вместо `UNION`, если дубликаты допустимы или гарантированно отсутствуют.
