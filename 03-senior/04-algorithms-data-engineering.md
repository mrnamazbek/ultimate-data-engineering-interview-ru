## 1. Фильтр Блума (Bloom Filter)

### Назначение и проблема
Определить, принадлежит ли элемент множеству (например, был ли уже обработан данный `transaction_id`), расходуя минимум памяти (биты вместо мегабайт).

### Принцип работы
1. Создается битовый массив длиной $m$, изначально заполненный нулями.
2. При добавлении элемента вычисляются $k$ различных хэш-функций от ключа.
3. Биты по полученным индексам устанавливаются в 1.
4. При проверке элемента: если хотя бы один из $k$ битов равен 0 — элемент **гарантированно отсутствует** в множестве. Если все биты равны 1 — элемент **вероятно присутствует**.

```text
Добавление ключа "user_101":
hash1("user_101") = 2  ───┐
hash2("user_101") = 5  ───┼─►  Битовый массив: [0, 0, 1, 0, 0, 1, 0, 0]
                                Индексы:         0  1  2  3  4  5  6  7
```

### Свойства фильтра Блума:
- **Ложноотрицательные срабатывания (False Negative) невозможны для корректно поддерживаемого множества фильтра** без неподдерживаемых удалений. Синхронизацию фильтра с актуальной БД нужно обеспечивать отдельно.
- **Ложноположительные срабатывания (False Positive) возможны**: из-за коллизий хэшей биты могут быть выставлены другими ключами.
- **Удаление элементов невозможно** (в базовом варианте), так как сброс бита может повредить другие ключи.

### Применение в реальных системах:
- **Apache Parquet / ORC**: каждый блок файлов содержит встроенный фильтр Блума. Если при запросе `WHERE user_uuid = '...'` фильтр возвращает «нет», блок данных даже не считывается с диска S3.
- **LSM-хранилища (RocksDB, Cassandra)**: фильтр Блума может проверяться перед чтением SSTable, экономя I/O. В ClickHouse Bloom применяется также как data skipping index по блокам MergeTree; это другая организация хранения.

### Наглядно: ложное совпадение и точная проверка

```text
Добавили A → выставили bits 2,5
Не добавляли B, но hashes(B) тоже 2,5 → possibly present
Проверка B в точном хранилище → отсутствует → B нельзя отбросить
```

Bloom положительный ответ — только кандидат. Отсутствие false negatives требует корректно поддерживаемого фильтра и отсутствия неподдерживаемых удалений; результат фильтра не доказывает наличие строки в текущей БД.

## 2. HyperLogLog (HLL) — Оценка мощности множеств

### Проблема точного `COUNT(DISTINCT user_id)`
Точный COUNT(DISTINCT) должен различать все уникальные ключи. Хеш-агрегация в памяти требует большого состояния; sort-based или внешняя обработка могут использовать диск. При большом числе групп состояние, shuffle и spill становятся дорогими.

### Математическая идея HyperLogLog:
Алгоритм наблюдает за максимальным количеством ведущих нулей в двоичном представлении хэша каждого элемента. 
- Вероятность встретить последовательность, начинающуюся с одного нуля (`0...`) — $1/2$.
- Вероятность встретить 10 нулей подряд (`00000000001...`) — $1/2^{10} = 1/1024$.
- HyperLogLog хранит максимальный ранг в каждом из m регистров и строит оценку с поправками. Типичная стандартная ошибка — около **1.04 / sqrt(m)**; расход памяти зависит от числа и кодирования регистров, разрядности хеша и реализации. Выбранная точность задаёт размер состояния, а не число поступивших событий.

```sql
-- Пример синтаксиса Spark SQL; имена функций и точность зависят от движка
-- Вместо тяжелого COUNT(DISTINCT):
SELECT APPROX_COUNT_DISTINCT(user_id) AS approx_monthly_active_users
FROM event_logs;
```

### Наглядно: регистры и слияние HyperLogLog

```text
hash → часть бит выбирает register; оставшийся suffix задаёт ранг
Suffix 00101 → 2 ведущих нуля → ранг 3
Register хранит максимум рангов наблюдений
Merge HLL A/B: покомпонентный MAX, а не сумма оценок distinct
```

Оценка строится по множеству регистров с поправками, а не по одному самому редкому хешу. Типичная стандартная ошибка порядка 1.04/√m; это статистическая характеристика, не жёсткая гарантия процента.

## 3. Консистентное хеширование (Consistent Hashing)

### Проблема наивного шардирования
При наивном распределении данных по нодам кластера через формулу `node_index = hash(key) % N` (где $N$ — число серверов):
Если число узлов меняется ($N \to N+1$), меняется modulo и значительная доля ключей получает другое назначение. Это может вызвать большой объём перемещения данных или промахов кэша; точная доля зависит от N и распределения.

### Принцип консистентного хеширования:
1. Хэш-пространство замыкается в кольцо от $0$ до $2^{32}-1$.
2. Как сами узлы кластера (серверы), так и ключи данных проецируются на это кольцо с помощью единой хэш-функции.
3. Ключ сохраняется на ближайшем по часовой стрелке узле.
4. Меняются владельцы затронутых диапазонов кольца. При равномерном распределении добавление одного узла перемещает в среднем примерно **$K/(N+1)$**, удаление — **$K/N$** ключей; фактическая доля зависит от токенов и virtual nodes.

```text
                 Сервер А (0)
                 /          \
                /   Ключ 1   \
      Сервер В (240)        Сервер Б (120)
                \            /
                 \  Ключ 2  /
                  ----------
```

*Виртуальные ноды (Virtual Nodes)*: Чтобы исключить неравномерную нагрузку при небольшом числе серверов, каждый физический сервер отображается на кольцо в виде сотен виртуальных точек (`Node_A_1`, `Node_A_2` и т.д.).

### Наглядно: какие ключи переместятся после добавления узла

```text
Кольцо 0..99: узлы A=20, B=60, C=90
Ключи 10→A, 30→B, 70→C, 95→A
Добавили D=40 → ключ 30 переместился B→D; остальные прежние
```

Virtual nodes сглаживают распределение долей узлов, но не устраняют горячий реальный ключ. При равномерности добавление узла перемещает в среднем около 1/(N+1) ключей; удаление — около 1/N.

## 4. LSM-деревья (Log-Structured Merge-Tree) против B+ Деревьев

| Характеристика | B+ Tree (PostgreSQL, MySQL InnoDB) | LSM-Tree (Cassandra, RocksDB) |
|---|---|---|
| **Принцип записи** | Случайная запись в существующие блоки на диске (Random I/O) | Строго последовательная запись в конец файла (Append-only / Sequential I/O) |
| **Скорость записи** | Ограничена скоростью случайного позиционирования головок диска | **Экстремально высокая** |
| **Скорость чтения** | Высокая (сбалансированное дерево) | Медленнее (нужно проверить MemTable и несколько файлов SSTable на диске) |
| **Применение** | OLTP-базы данных со сбалансированным чтением и записью | Аналитические и NoSQL системы с гигантским потоком входящих логов |

### Компоненты LSM-Tree:
1. **MemTable**: оперативная структура для записей; например, skip list или дерево, в зависимости от реализации.
2. **CommitLog / WAL**: журнал упреждающей записи на диске для защиты от сбоев питания.
3. **SSTables (Sorted String Tables)**: неизменяемые файлы на диске, отсортированные по ключу. Когда MemTable заполняется, она целиком сбрасывается на диск в виде новой SSTable.
4. **Compaction (Компактизация)**: процесс слияния SSTables и разрешения версий по правилам движка. Удаление tombstones требует выполнения условий восстановления/согласования реплик.

### Наглядно: write path LSM и цена compaction

```text
Write → WAL + MemTable → flush → SSTable1
Следующие write → SSTable2
Read → память + нужные SSTables + разрешение версий
Compaction → объединение файлов, дополнительное чтение/запись
```

LSM обменивает характер записи на read/write/space amplification. B+ tree обновляет страницы и удобен для диапазонов; конкретная производительность зависит от workload и storage. MergeTree ClickHouse имеет похожие фоновые слияния, но не тождествен классическому key-value LSM.
