## 1. Архитектура Feature Store (Хранилища признаков)

Традиционная проблема ML в продакшне: дата-сайентист пишет SQL-запрос для обучения модели на исторических данных, а бэкенд-разработчик переписывает этот расчет на Go/Java для выдачи рекомендаций в реальном времени. Логика расчета неизбежно расходится — возникает **Train-Serving Skew** (перекос между обучением и эксплуатацией), и точность модели катастрофически падает.

```text
               Источники данных (Batch & Stream)
                               |
              +----------------v----------------+
              |     Feature Processing Engine   |
              |     (Apache Spark / Flink)      |
              +----------------+----------------+
                               |
            +------------------+------------------+
            |                                     |
    +-------v-------+                     +-------v-------+
    | Offline Store |                     | Online Store  |
    | (S3, BigQuery,|                     | (Redis,       |
    |  Snowflake)   |                     |  DynamoDB)    |
    +-------+-------+                     +-------+-------+
            |                                     |
            v Пакетное обучение                   v Инференс модели (< 10 мс)
    +---------------+                     +---------------+
    | Model Training|                     | Real-time API |
    +---------------+                     +---------------+
```

### Двухуровневое хранилище (Dual-layer storage):
1. **Offline Feature Store (Холодный слой)**: хранит терабайты полной истории значений признаков за годы (Parquet, Iceberg, Snowflake). Оптимизирован под тяжелые пакетные выгрузки обучающих выборок.
2. **Online Feature Store (Горячий слой)**: хранит только самое последнее актуальное значение каждого признака по ключу сущности (`user_id`). Построен на базе In-Memory баз данных (Redis, Cassandra). Гарантирует отдачу вектора признаков за $1-5$ миллисекунд в момент онлайн-запроса пользователя.

## 2. Корректность на момент времени (Point-in-Time Correctness)

Главный риск при подготовке данных для ML — **Data Leakage (Утечка из будущего)**.

*Пример*: Мы обучаем модель предсказывать дефолт по кредиту. Кредит был взят `2025-05-01`, а через 2 месяца (`2025-07-01`) у клиента упал кредитный рейтинг. Если при формировании обучающей выборки взять рейтинг на сегодняшний день, модель «увидит будущее» и покажет идеальную точность на тестах, но будет бесполезна в реальной жизни.

### Механизм Time-Travel Join:
Feature Store (например, **Feast** или **Tecton**) автоматически выполняет соединение таблицы фактов с историей изменений признаков на точный момент свершения события:
```sql
-- Логика Point-in-Time соединения:
SELECT 
    e.event_id,
    e.user_id,
    e.event_timestamp,
    f.credit_score
FROM credit_applications e
ASOF JOIN user_credit_history f
  ON e.user_id = f.user_id
 AND f.updated_at <= e.event_timestamp;
```

## 3. Конвейеры данных для Generative AI и Vector Databases

Инженеры данных строят конвейеры для Retrieval-Augmented Generation (RAG) и семантического поиска.

### Архитектура конвейера эмбеддингов (Embedding Pipeline):
1. **Забор документов (Ingestion)**: чтение сырых PDF, текстовых логов или статей из хранилища.
2. **Нарезка на фрагменты (Chunking Strategy)**: разбиение текстов на смысловые блоки с перекрытием (например, 512 токенов с overlap 50 токенов), чтобы не разрывать контекст предложений.
3. **Генерация эмбеддингов**: батчевый прогон чанков через нейросетевую модель (например, OpenAI text-embedding-3 или BERT) и получение векторов размерности 1536.
4. **Загрузка в векторную базу данных (Vector DB)**: сохранение векторов и метаданных в Milvus, Qdrant, Pinecone или PostgreSQL с расширением `pgvector`.

### Векторные индексы в СУБД:
- **IVFFlat (Inverted File Flat)**: делит векторное пространство на кластеры по алгоритму K-Means. Поиск выполняется только по ближайшим центроидам кластеров. Быстро строится, требует мало памяти, но уступает по точности.
- **HNSW (Hierarchical Navigable Small World)**: многоуровневый граф, позволяющий выполнять приближенный поиск ближайших соседей (Approximate Nearest Neighbors, ANN) с логарифмической сложностью. Обеспечивает высочайшую скорость поиска при минимальной погрешности, но требует значительного объема RAM под хранение графа.

## 4. Мониторинг качества данных в ML: Data Drift

После вывода модели в прод распределение входных данных неизбежно начинает меняться (**Data Drift**): меняется поведение пользователей, появляются новые версии мобильного приложения, обновляются браузеры.

### Методы детекции дрейфа:
- **Статистические тесты**: тест Колмогорова-Смирнова (KS-test) для непрерывных величин или критерий Хи-квадрат ($\chi^2$) для категориальных признаков.
- **Метрика PSI (Population Stability Index)**:
  - $PSI < 0.1$ — распределение стабильно.
  - $0.1 \le PSI < 0.2$ — умеренное смещение, требуется обратить внимание.
  - $PSI \ge 0.2$ — критический дрейф данных, конвейер автоматически триггерит переобучение модели.
