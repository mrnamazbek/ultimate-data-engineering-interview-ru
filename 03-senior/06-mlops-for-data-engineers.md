## 1. Архитектура Feature Store (Хранилища признаков)

Традиционная проблема ML в продакшне: дата-сайентист пишет SQL-запрос для обучения модели на исторических данных, а бэкенд-разработчик переписывает этот расчет на Go/Java для выдачи рекомендаций в реальном времени. Логика расчета неизбежно расходится — возникает **Train-Serving Skew** (перекос между обучением и эксплуатацией), и точность модели катастрофически падает.

```text
               Источники данных (Batch & Stream)
                               |
              +----------------v----------------+
              |     Feature Processing Engine   |
              |     (Apache Spark / Flink)      |
              +----------------+----------------+
                               |
            +------------------+------------------+
            |                                     |
    +-------v-------+                     +-------v-------+
    | Offline Store |                     | Online Store  |
    | (S3, BigQuery,|                     | (Redis,       |
    |  Snowflake)   |                     |  DynamoDB)    |
    +-------+-------+                     +-------+-------+
            |                                     |
            v Пакетное обучение                   v Инференс модели (< 10 мс)
    +---------------+                     +---------------+
    | Model Training|                     | Real-time API |
    +---------------+                     +---------------+
```

### Двухуровневое хранилище (Dual-layer storage):
1. **Offline Feature Store (Холодный слой)**: хранит терабайты полной истории значений признаков за годы (Parquet, Iceberg, Snowflake). Оптимизирован под тяжелые пакетные выгрузки обучающих выборок.
2. **Online Feature Store (Горячий слой)**: хранит только самое последнее актуальное значение каждого признака по ключу сущности (`user_id`). Построен на базе In-Memory баз данных (Redis, Cassandra). Гарантирует отдачу вектора признаков за $1-5$ миллисекунд в момент онлайн-запроса пользователя.

## 2. Корректность на момент времени (Point-in-Time Correctness)

Главный риск при подготовке данных для ML — **Data Leakage (Утечка из будущего)**.

*Пример*: Мы обучаем модель предсказывать дефолт по кредиту. Кредит был взят `2025-05-01`, а через 2 месяца (`2025-07-01`) у клиента упал кредитный рейтинг. Если при формировании обучающей выборки взять рейтинг на сегодняшний день, модель «увидит будущее» и покажет идеальную точность на тестах, но будет бесполезна в реальной жизни.

### Механизм Time-Travel Join:
Feature Store (например, **Feast** или **Tecton**) автоматически выполняет соединение таблицы фактов с историей изменений признаков на точный момент свершения события:
```sql
-- Логика Point-in-Time соединения:
SELECT 
    e.event_id,
    e.user_id,
    e.event_timestamp,
    f.credit_score
FROM credit_applications e
ASOF JOIN user_credit_history f
  ON e.user_id = f.user_id
 AND f.updated_at <= e.event_timestamp;
```

## 3. Конвейеры данных для Generative AI и Vector Databases

Инженеры данных строят конвейеры для Retrieval-Augmented Generation (RAG) и семантического поиска.

### Архитектура конвейера эмбеддингов (Embedding Pipeline):
1. **Забор документов (Ingestion)**: чтение сырых PDF, текстовых логов или статей из хранилища.
2. **Нарезка на фрагменты (Chunking Strategy)**: разбиение текстов на смысловые блоки с перекрытием (например, 512 токенов с overlap 50 токенов), чтобы не разрывать контекст предложений.
3. **Генерация эмбеддингов**: батчевый прогон чанков через нейросетевую модель (например, OpenAI text-embedding-3 или BERT) и получение векторов размерности 1536.
4. **Загрузка в векторную базу данных (Vector DB)**: сохранение векторов и метаданных в Milvus, Qdrant, Pinecone или PostgreSQL с расширением `pgvector`.

### Векторные индексы в СУБД:
- **IVFFlat (Inverted File Flat)**: делит векторное пространство на кластеры по алгоритму K-Means. Поиск выполняется только по ближайшим центроидам кластеров. Быстро строится, требует мало памяти, но уступает по точности.
- **HNSW (Hierarchical Navigable Small World)**: многоуровневый граф, позволяющий выполнять приближенный поиск ближайших соседей (Approximate Nearest Neighbors, ANN) с логарифмической сложностью. Обеспечивает высочайшую скорость поиска при минимальной погрешности, но требует значительного объема RAM под хранение графа.

## 4. Мониторинг качества данных в ML: Data Drift

После вывода модели в прод распределение входных данных неизбежно начинает меняться (**Data Drift**): меняется поведение пользователей, появляются новые версии мобильного приложения, обновляются браузеры.

### Методы детекции дрейфа:
- **Статистические тесты**: тест Колмогорова-Смирнова (KS-test) для непрерывных величин или критерий Хи-квадрат ($\chi^2$) для категориальных признаков.
- **Метрика PSI (Population Stability Index)**:
  - $PSI < 0.1$ — распределение стабильно.
  - $0.1 \le PSI < 0.2$ — умеренное смещение, требуется обратить внимание.
  - $PSI \ge 0.2$ — критический дрейф данных, конвейер автоматически триггерит переобучение модели.

## 5. Версионирование данных: DVC (Data Version Control)

Git отлично версионирует исходный код, но не способен хранить тяжелые файлы данных (датасеты на десятки гигабайт, веса нейросетей, файлы Parquet). Попытка коммитить большие файлы в Git приводит к разрастанию репозитория и падению `git clone`.

**DVC (Data Version Control)** решает проблему воспроизводимости данных для инженера:
1. Физические тяжелые файлы хранятся во внешнем удаленном хранилище (**DVC Remote**): S3, Google Cloud Storage, MinIO, SSH.
2. В Git коммитятся только легковесные указатели — текстовые файлы с расширением `.dvc` (содержащие md5-хеш файла и его размер в байтах).
3. Команды DVC повторяют привычный синтаксис Git:
   ```bash
   # Инициализация и привязка S3-хранилища
   dvc init
   dvc remote add -d myremote s3://ml-datasets-production/feature_store/

   # Добавление тяжелого датасета под версионирование
   dvc add data/train_dataset_2026.parquet
   # Генерируется файл data/train_dataset_2026.parquet.dvc

   # Отправка тяжелых данных в S3, а указателя — в Git
   dvc push
   git add data/train_dataset_2026.parquet.dvc .gitignore
   git commit -m "feat: добавлена обучающая выборка за сентябрь 2026"
   ```

### Пайплайны DVC (`dvc.yaml`):
DVC позволяет связывать код, входные данные и выходные модели в единый воспроизводимый граф (DAG). Если входной файл `train.parquet` не изменился, команда `dvc repro` пропустит повторный расчет и переобучение модели, сэкономив часы вычислений.

## 6. Учет и трекинг моделей: Архитектура MLflow

В продакшн-конвейерах инженеры данных настраивают централизованную платформу учета артефактов и моделей **MLflow**.

```
[ ETL Pipeline / Spark ] ──► [ Model Training Worker ]
                                     │
                 ┌───────────────────┴───────────────────┐
                 ▼                                       ▼
    [ MLflow Tracking Server ]               [ MLflow Artifact Store ]
    (PostgreSQL: параметры, метрики)         (S3 / MinIO: веса моделей, графики)
                 │
                 ▼
    [ MLflow Model Registry ]
    (Этапы: Staging -> Production -> Archived)
                 │
                 ▼
    [ Model Serving API (KubeFlow / Triton / FastAPI) ]
```

### 4 ключевых компонента MLflow:
1. **MLflow Tracking**: библиотека логирования параметров (`mlflow.log_param`), метрик качества (`mlflow.log_metric`) и артефактов (`mlflow.log_artifact`) при каждом запуске (Run). Позволяет сравнивать качество сотен экспериментов на интерактивном дашборде.
2. **MLflow Projects**: стандартизированный формат упаковки ML-кода (окружение `conda.yaml` или `Dockerfile`) для воспроизводимого запуска на любом сервере.
3. **MLflow Models**: универсальный формат сохранения моделей (PyTorch, Scikit-learn, SparkML, ONNX). Позволяет вызывать `predict()` в виде REST API или пакетной трансформации в PySpark.
4. **MLflow Model Registry**: централизованный каталог версий моделей с жизненным циклом (Stage transitions: `None` -> `Staging` -> `Production` -> `Archived`). При переходе модели в `Production` срабатывает Webhook, запускающий автоматический деплой в Kubernetes.

## 7. Вопросы с Senior собеседований

### Вопрос 1: В чем разница между Feast (Feature Store) и обычным кэшем в Redis?
**Ответ**:
Redis — это просто база данных ключ-значение. Feature Store (например, Feast):
1. Обеспечивает строгую схему и валидацию типов признаков (Feature View).
2. Поддерживает двойную запись: синхронно в Online Store (Redis) для минимальной задержки инференса и асинхронно в Offline Store (Parquet/Iceberg) для исторического обучения.
3. Решает проблему Time-Travel Join: формирует исторические обучающие выборки с гарантией отсутствия утечек из будущего (Data Leakage) на момент свершения событий.

### Вопрос 2: Как организовать непрерывное дообучение (Continual Learning) модели при обнаружении Data Drift?
**Ответ**:
1. Потоковый конвейер (Kafka + Flink/Spark) логирует входные векторы и предсказания модели в слой Bronze.
2. Ежесуточный DAG в Airflow запускает расчет метрики стабильности популяции (PSI) между текущим окном данных и референсным обучающим датасетом.
3. Если $PSI \ge 0.2$, Airflow триггерит запуск задачи переобучения на свежих данных.
4. Новая версия модели автоматически валидируется на отложенной выборке (Champion-Challenger validation).
5. При подтверждении превосходства метрик качества новая версия регистрируется в MLflow Model Registry как `Staging`, и запускается канареечный деплой (Canary Deployment) в Kubernetes на 5% пользователей.
