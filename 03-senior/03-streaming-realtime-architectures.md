# Потоковая обработка и архитектуры реального времени (Уровень Senior)

Потоковая обработка данных (Stream Processing) требует принципиально иного инженерного мышления по сравнению с пакетной. На уровне Senior интервьюеры уделяют внимание гарантиям доставки сообщений, семантике Exactly-Once, обработке времени событий (Event Time vs Processing Time) и выбору архитектурного паттерна (Lambda против Kappa).

## 1. Архитектурные паттерны: Lambda против Kappa

```text
       Архитектура Lambda                              Архитектура Kappa
       
       +------------------+                            +------------------+
       |   События (Logs) |                            |   События (Logs) |
       +--------+---------+                            +--------+---------+
                |                                               |
        +-------+-------+                               +-------v-------+
        |               |                               |  Потоковый    | (Apache Kafka /
+-------v-------+ +-----v---------+                     |  лог событий  |  Pulsar)
|  Speed Layer  | |  Batch Layer  |                     +-------+-------+
| (Storm/Flink) | | (Spark/Hadoop)|                             |
+-------+-------+ +-----+---------+                     +-------v-------+
        |               |                               | Движок потока | (Apache Flink /
+-------v-------+-------v---------+                     | (Stream Engine|  Spark Streaming)
|         Serving Layer           |                     +-------+-------+
|  (Слияние двух результатов)     |                             |
+---------------------------------+                     +-------v-------+
                                                        |  Витрина DWH  | (ClickHouse /
                                                        +---------------+  Pinot / Redis)
```

### Сравнение архитектур:
| Критерий | Lambda Architecture | Kappa Architecture |
|---|---|---|
| **Количество конвейеров** | Два независимых конвейера: быстрый (Speed) и точный (Batch) | Один универсальный потоковый конвейер |
| **Кодовая база** | Двойная (одна логика на Java/Flink для потока, вторая на SQL/Spark для батча) | Единая кодовая база для всех вычислений |
| **Сложность поддержки** | Высокая (постоянный рассинхрон бизнес-логики и результатов) | Значительно ниже |
| **Исторический пересчет** | Батчевый слой автоматически пересчитывает историю | Пересчет запускается сдвигом оффсетов чтения из топика Kafka с сохранением в новую витрину |

Выбор Lambda/Kappa зависит от доступности журнала для replay, сложности расчётов, требований к задержке и стоимости поддержки. Kappa упрощает повторное использование потокового расчёта, но требует сохранённой истории и подходящего протокола пересчёта.

### Наглядно: исторический пересчёт двумя путями

```text
Lambda: batch история + speed последние события → согласование serving
Kappa: сохранённый event log → тот же stream код → новая версия результата
```

Kappa требует достаточного retention или архива для replay; Lambda требует согласования двух расчётов. Выбор зависит от источников, обновлений и SLA, а не всеобщего превосходства одного подхода.

## 2. Гарантии доставки: At-Most-Once, At-Least-Once, Exactly-Once

1. **At-Most-Once (Не более одного раза)**:
   - В выбранной границе обработка допускает потерю при сбое и не повторяется автоматически. Например, consumer фиксирует offset до записи результата. `acks=0` описывает отсутствие подтверждения producer-записи, но не задаёт весь протокол обработки.
2. **At-Least-Once (Хотя бы один раз)**:
   - При выполнении условий хранения и восстановления событие обрабатывается как минимум один раз, возможны повторы. Consumer подтверждает прогресс после результата. Producer acknowledgements и retries настраивают отдельно; один `acks=all` не доказывает end-to-end гарантию.
3. **Exactly-Once (Строго один раз)**:
   - Каждая входная запись влияет на результат ровно один раз в явно определённой границе протокола. Два входных сообщения одного бизнес-события требуют отдельного договора дедупликации.

### Как физически достигается Exactly-Once в продакшне:
Используются разные протоколы; перечисленные механизмы не обязаны применяться все одновременно:
1. **Идемпотентный producer Kafka** предотвращает дубли определённых повторных отправок в рамках producer-протокола. Он не устраняет произвольные дубли входного бизнес-события.
2. **Kafka transactions** могут атомарно связать выходные записи Kafka и consumer offsets; потребители используют подходящую изоляцию, например `read_committed`.
3. **Checkpoint + транзакционный sink** или поддерживаемый **2PC** согласуют состояние вычисления и внешнюю запись при условиях конкретного коннектора.
4. **Идемпотентный sink / реестр батчей** может предотвратить повторный эффект при повторном чтении. Нужны стабильный ключ, транзакция и защита от конкуренции; одного слова `UPSERT` недостаточно.

Границы подтверждаются документацией выбранных компонентов и failure-тестом, например сбоем после записи перед подтверждением. [Kafka design](https://kafka.apache.org/41/design/design/), [Spark Structured Streaming](https://spark.apache.org/docs/latest/streaming/apis-on-dataframes-and-datasets.html).

### Наглядно: порядок результата и подтверждения

```text
Commit offset → сбой до записи → возможная потеря эффекта
Запись → сбой до commit offset → повтор чтения
Повтор + идемпотентный sink/транзакционный протокол → один эффект в заданной границе
```

Разделяйте гарантии producer→broker, обработки и внешнего sink. acks=all само по себе не даёт end-to-end exactly-once; idempotent producer не дедуплицирует произвольные бизнес-дубли.

## 3. Обработка времени: Event Time, Ingestion Time, Processing Time

- **Event Time (Время события)**: время бизнес-события из payload; оно подходит для анализа времени события, если источник, timezone и качество timestamp соответствуют договору.
- **Ingestion Time (Время поступления)**: момент, когда брокер сообщений (Kafka) записал событие в свой топик.
- **Processing Time (Время обработки)**: текущие системные часы сервера, на котором в данный момент работает Spark или Flink воркер.

### Проблема задержки и рассинхрона времени:
Пользователь совершил покупку в поезде без связи в 12:00 (Event Time). Телефон отправил событие на сервер только в 15:00 (Processing Time). Если аналитика сгруппирована по `Processing Time`, покупка неверно попадет в дневной пик продаж вместо полуденного.

### Наглядно: одно событие и три времени

```text
Покупка произошла: event_time=12:00
Брокер принял: ingestion_time=15:00
Worker обработал: processing_time=15:02
```

Группировка по event time показывает время покупки, по processing time — нагрузку обработки. Event timestamp может быть ошибочным; проверяйте timezone, часы устройства и договор времени.

## 4. Водяные знаки (Watermarking) и поздние данные

Когда мы группируем поток по окнам на основе **Event Time**, мы не знаем, сколько времени ждать опаздывающие события из-за сетевых задержек.

### Что такое Watermark:
Watermark — граница продвижения event time, применяемая по правилам движка для завершения результатов и ограничения состояния. Она не доказывает, что все более ранние события получены. В Spark ориентир связан с максимальным наблюдённым event time и заданной задержкой, а фактическое применение зависит от micro-batches, оператора и output mode.

```python
# events — уже прочитанный и распарсенный streaming DataFrame;
# event_timestamp имеет TimestampType, device_id извлечён из payload.
from pyspark.sql.functions import window

# Задержка 10 минут относительно event-time прогресса.
# Более поздние события могут быть отброшены; это не wall-clock TTL.
streaming_df = events \
    .withWatermark("event_timestamp", "10 minutes") \
    .groupBy(
        window("event_timestamp", "5 minutes"), # окно 5 минут
        "device_id"
    ) \
    .count()
```

### Наглядно: watermark и очистка состояния окна

```text
Max event time observed=12:20; delay=10 минут → ориентир watermark=12:10
Окно [12:00,12:05) может завершаться/очищаться по правилам оператора
Пришло event_time=12:03 позже → возможное late event → согласованная политика
```

Это иллюстрация event-time горизонта, а не wall-clock timeout и не доказательство полноты. В Spark watermark обновляется по micro-batches; точное отбрасывание и очистка зависят от оператора/output mode.

## 5. Типы окон (Windowing Strategies)

1. **Tumbling Windows (Перекатывающиеся / Фиксированные окна)**:
   - Непересекающиеся окна фиксированного размера (например, 00:00–00:05, 00:05–00:10). Каждое событие принадлежит ровно одному окну.
2. **Sliding Windows (Скользящие окна)**:
   - Окна фиксированной длины, сдвигающиеся с заданным шагом (например, окно 10 минут с шагом сдвига 1 минута). Окна перекрываются, одно событие может учитываться в нескольких окнах.
3. **Session Windows (Сессионные окна)**:
   - Окна переменной длины, динамически формируемые по периодам активности пользователя. Если в течение заданного интервала неактивности (gap duration, например, 30 минут) новых событий нет — сессия закрывается.

### Наглядно: в какие окна попадёт событие

```text
Event at 12:07
Tumbling 5 min → [12:05,12:10)
Sliding 10 min, step 5 min → [12:00,12:10) и [12:05,12:15)
Session gap 5 min: события 12:00,12:03,12:12 → две сессии
```

Sliding учитывает одно событие в нескольких окнах. Session объединяется при активности с допустимым gap; позднее событие может связать ранее разделённые сессии в поддерживающем это режиме.
