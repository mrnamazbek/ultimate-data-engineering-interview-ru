# 12. Классическая экосистема Big Data: Hadoop HDFS, YARN, MapReduce и Apache Hive

## 1. Введение: Почему появился Apache Hadoop

В начале 2000-х годов с бурным ростом веб-сервисов (Google, Yahoo!) объем генерируемых данных превысил физические возможности одиночных серверов. 

Существовало два пути масштабирования:
1. **Вертикальное масштабирование (Scale-Up)**: покупка сверхдорогих серверов с десятками терабайт RAM и сотнями ядер. Ограничение: экспоненциальная стоимость и физический предел оборудования.
2. **Горизонтальное масштабирование (Scale-Out)**: объединение сотен и тысяч дешевых стандартных серверов (Commodity Hardware) в единый распределенный кластер.

**Apache Hadoop** (создан Дагом Каттингом на базе статей Google GFS и MapReduce) стал стандартом распределенного хранения и вычислений для Big Data.

## 2. Распределенная файловая система HDFS (Hadoop Distributed File System)

HDFS спроектирована для надежного хранения файлов огромного размера (гигабайты и терабайты) с потоковым доступом на чтение (Streaming Data Access) по принципу **"Write once, read many times"**.

```
                           [ Active NameNode ]  ◄──(ZKFC/ZooKeeper)──► [ Standby NameNode ]
                                    │
                       (Служебные метаданные: RAM)
                                    │
         ┌──────────────────────────┼──────────────────────────┐
         ▼                          ▼                          ▼
   [ DataNode 1 ]            [ DataNode 2 ]             [ DataNode 3 ]
   (Стойка Rack 1)           (Стойка Rack 1)            (Стойка Rack 2)
   ├── Блок A (копия 1)      ├── Блок B (копия 1)       ├── Блок A (копия 3)
   └── Блок B (копия 2)      └── Блок A (копия 2)       └── Блок C (копия 1)
```

### 2.1. Компоненты архитектуры HDFS

1. **NameNode (Мастер)**:
   - Управляет пространством имен файловой системы (дерево директорий, права доступа, маппинг файлов на блоки).
   - **Хранит все метаданные исключительно в оперативной памяти (RAM)** для максимальной скорости ответа. 1 миллион файлов/блоков занимает около 150 МБ в памяти NameNode.
   - Долговечность метаданных обеспечивается двумя файлами на диске:
     - `FSImage` — полный снимок метаданных на определенный момент времени.
     - `EditLog` — журнал транзакций (WAL), куда последовательно дописывается каждое изменение.

2. **DataNodes (Воркеры)**:
   - Физические серверы, на обычных дисках которых хранятся блоки данных.
   - Отправляют на NameNode сигналы жизнедеятельности (Heartbeats каждые 3 секунды) и отчеты о состоянии блоков (Block Reports).

3. **Secondary NameNode (Не является горячей заменой!)**:
   - Частая ошибка на собеседованиях — считать Secondary NameNode резервным сервером.
   - **Его единственная задача — Checkpoint**: периодически скачивать с активного NameNode файлы `FSImage` и `EditLog`, объединять их в новый `FSImage` и отправлять обратно, чтобы журнал изменений `EditLog` не разрастался до гигантских размеров.

### 2.2. Физическое устройство блоков и репликация

- **Размер блока (Block Size)**: по умолчанию **128 МБ** (или 256 МБ). В обычных ОС размер блока 4 КБ. Большой размер блока в HDFS необходим, чтобы:
  - Минимизировать объем метаданных в RAM NameNode.
  - Амортизировать время механического позиционирования головки диска (Seek Time): время поиска дорожки составляет ~10 мс, а последующее чтение 128 МБ непрерывного блока происходит на линейной скорости диска.
- **Фактор репликации (Replication Factor = 3)** и топология стоек (**Rack Awareness**):
  - 1-я копия блока пишется на локальный узел клиента (или случайный узел).
  - 2-я копия кладется на другой узел в той же стойке (Rack 1).
  - 3-я копия кладется на узел в **другой физической стойке (Rack 2)**.
  - Это защищает данные даже при полном выходе из строя коммутатора или питания всей серверной стойки.

### 2.3. Режим высокой доступности (HDFS High Availability)

В продакшне NameNode не может быть единой точкой отказа (SPOF). Используется схема **Active/Standby NameNode**:
- Общий журнал изменений через кворум узлов **JournalNodes (QJM)**.
- Автоматическое переключение при сбое с помощью **ZooKeeper** и демона **ZKFC (ZooKeeper Failover Controller)**.

## 3. Менеджер ресурсов YARN (Yet Another Resource Negotiator)

YARN отвечает за распределение вычислительных ресурсов кластера (CPU и оперативной памяти) между конкурирующими приложениями (Spark, Flink, MapReduce, Hive).

```
                            [ YARN ResourceManager ]
                            (Scheduler + AppsManager)
                                       │
         ┌─────────────────────────────┼─────────────────────────────┐
         ▼                             ▼                             ▼
   [ NodeManager 1 ]            [ NodeManager 2 ]             [ NodeManager 3 ]
   ├── [ ApplicationMaster ]    ├── [ Container (Spark Exec)] ├── [ Container (Hive Task) ]
   └── [ Container ]            └── [ Container ]             └── [ Container ]
```

### 3.1. Компоненты YARN

1. **ResourceManager (RM)**: центральный арбитр кластера.
   - *Scheduler*: распределяет ресурсы строго по запросам согласно политикам (CPU, RAM).
   - *ApplicationsManager*: принимает отправленные задачи и перезапускает ApplicationMaster при сбоях.
2. **NodeManager (NM)**: агент на каждом физическом сервере. Мониторит утилизацию ресурсов и запускает изолированные **Контейнеры (Containers)**.
3. **ApplicationMaster (AM)**: создается индивидуально под каждое запущенное приложение (например, для каждого Spark-приложения создается свой Spark ApplicationMaster). Ведет переговоры с ResourceManager о выделении контейнеров и координирует воркеры.

### 3.2. Политики планирования (Schedulers)

- **FIFO Scheduler**: задачи выполняются строго в порядке очереди. Большой ночной расчет блокирует короткие аналитические запросы.
- **Capacity Scheduler (по умолчанию в Hadoop)**: ресурсы делятся на фиксированные очереди (например, `prod_etl` = 70%, `analytics` = 30%). Гарантирует изоляцию ресурсов между отделами.
- **Fair Scheduler**: динамически перераспределяет ресурсы поровну между всеми активными пользователями.

## 4. Парадигма MapReduce

MapReduce — это распределенная модель вычислений, разбитая на два основных шага:
1. **Map (Отображение)**: параллельная фильтрация и трансформация входных данных. На входе пара `(K1, V1)`, на выходе список пар `(K2, V2)`.
2. **Shuffle and Sort**: автоматическая фаза экосистемы Hadoop. Данные с одинаковыми ключами $K2$ со всех серверов кластера группируются, сортируются и по сети передаются на один узел Reducer.
3. **Reduce (Свертка)**: агрегация значений по ключу. На входе `(K2, list(V2))`, на выходе итоговый результат `(K3, V3)`.

### Вспомогательные элементы:
- **InputSplit**: логическое разбиение файла на порции данных (обычно равно 1 блоку HDFS = 128 МБ). На каждый InputSplit запускается ровно один Map Task.
- **Combiner (Mini-Reducer)**: локальная агрегация на ноде маппера до отправки в сеть. Например, при подсчете суммы чисел комбинатор предварительно суммирует значения на месте, сокращая сетевой трафик (Shuffle) в десятки раз.
- **Partitioner**: определяет, на какой именно Reducer отправить конкретный ключ (обычно `hash(key) % num_reducers`).

> **Почему MapReduce устарел**: MapReduce после каждого шага обязан материализовать (сбросить) промежуточные данные на локальный диск и записать их копии. В многошаговых конвейерах 80% времени уходило на дисковый ввод-вывод (I/O). Apache Spark перенес вычисления в оперативную память (In-Memory DAG), ускорив обработку в 10–100 раз.

## 5. Apache Hive: SQL поверх Big Data

Apache Hive транслирует привычные аналитикам декларативные SQL-запросы (HiveQL) в направленный ациклический граф задач (на движках Tez или Spark).

### 5.1. Управляемые (Managed) против Внешних (External) таблиц

| Характеристика | Managed / Internal Table | External Table |
| :--- | :--- | :--- |
| **Создание** | `CREATE TABLE table_name (...)` | `CREATE EXTERNAL TABLE table_name (...) LOCATION 'hdfs://...'` |
| **Владение данными** | Hive полностью контролирует данные в директории `/user/hive/warehouse/` | Данные могут принадлежать другим системам (Kafka, Spark, raw files) |
| **Операция `DROP TABLE`** | **Удаляет и метаданные, и физические файлы с диска HDFS!** | **Удаляет только метаданные из Hive Metastore.** Физические файлы на HDFS остаются нетронутыми. |

> **Золотое правило Enterprise Data Engineering**: Все сырые слои (Raw/Bronze) и разделяемые таблицы обязаны создаваться как **EXTERNAL**, чтобы ошибка инженера в скрипте не привела к физической потере терабайт сырых данных.

### 5.2. Оптимизация хранения: Партиционирование и Бакетирование

```sql
CREATE EXTERNAL TABLE sales_orders (
    order_id bigint,
    customer_id bigint,
    amount decimal(12,2)
)
PARTITIONED BY (order_date string)
CLUSTERED BY (customer_id) INTO 16 BUCKETS
STORED AS ORC
LOCATION '/data/sales/orders';
```

1. **Партиционирование (Partitioning)**:
   - Физически создает директорию на HDFS под каждое значение (`order_date=2026-09-24/`).
   - Исключает сканирование лишних файлов при фильтре `WHERE order_date = '2026-09-24'`.
   - **Опасность**: Оверпартиционирование (создание миллионов мелких папок по часам или клиентам) перегружает память NameNode.
2. **Бакетирование (Bucketing)**:
   - Внутри папки данные делятся на строго фиксированное количество файлов ($N$ файлов-бакетов) по хеш-функции: `hash(customer_id) % 16`.
   - Позволяет выполнять **Bucket Map Join**: если две таблицы сбакетированы по одному ключу на одинаковое число бакетов, СУБД объединяет их без дорогостоящего сетевого Shuffle.

### 5.3. Формат ORC (Optimized Row Columnar)
Стандарт хранения данных в экосистеме Hive:
- Колоночный формат с разделением на полосы (Stripes по 64–256 МБ).
- Встроенные индексы (Min/Max значения, Bloom Filters) для пропуска ненужных блоков строк (Row Groups).
- Векторизованное исполнение запросов (Vectorized Query Execution): процессор считывает сразу по 1024 строки в векторный буфер.

## 6. Вопросы с собеседований

### Вопрос 1: Что произойдет, если NameNode упадет, а High Availability не настроен?
**Ответ**:
Кластер станет полностью недоступным. Даже если все терабайты данных физически лежат на DataNodes, без NameNode невозможно определить, какие блоки какому файлу принадлежат. Поэтому в продакшне обязательна настройка HA NameNode с автоматическим переключением через ZooKeeper.

### Вопрос 2: В чем разница между `ORC` и `Parquet`?
**Ответ**:
Оба формата являются колоночными и поддерживают предикатное сжатие. `ORC` исторически разрабатывался под Apache Hive и экосистему Hortonworks, обладает лучшей поддержкой ACID-транзакций в Hive и легковесных индексов. `Parquet` проектировался совместно Twitter и Cloudera для универсальной экосистемы (Apache Spark, Arrow, Impala, Presto/Trino, DuckDB) и сегодня является индустриальным стандартом для облачных хранилищ и Lakehouse.
