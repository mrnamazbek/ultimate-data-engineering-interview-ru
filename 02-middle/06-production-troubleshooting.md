# Производственные инциденты и отладка (Уровень Middle)

На собеседованиях для уровня Middle вопросы из серии *«Расскажите о самом сложном баге в продакшне»* или *«Что вы будете делать, если ночной пайплайн упал с OutOfMemory?»* являются решающими. Они показывают реальный боевой опыт кандидата и его способность поддерживать стабильность систем данных под нагрузкой.

---

## 1. Падение заданий с ошибкой Out Of Memory (OOM) в Spark

Ошибка `java.lang.OutOfMemoryError` — самый частый инцидент в распределенных вычислениях.

### 1.1. Driver OOM (Память управляющего узла)
- **Причина**: разработчик вызвал действие `df.collect()`, `df.toPandas()` или `take(1000000)` на огромном датасете. Все данные со всех воркеров передаются по сети на одну машину Driver-а, мгновенно переполняя его JVM Heap.
- **Решение**:
  - Категорически избегать вызова `collect()` на неагрегированных данных в продакшне.
  - Сохранять результат напрямую в файл или таблицу (`df.write.parquet(...)`).
  - При необходимости увеличить память драйвера в конфиге: `--driver-memory 8g`.

### 1.2. Executor OOM (Память рабочих узлов)
- **Причина 1: Перекос данных (Data Skew)**. Из 200 задач (tasks) 199 завершаются за 5 секунд, а 1 задача зависает на 40 минут и падает с OOM. Это означает, что 90% данных имеют один и тот же ключ группировки/соединения (например, `user_id = NULL` или бот), и вся эта масса свалилась на один-единственный воркер.
- **Причина 2: Слишком большие партиции**. Размер одной партиции превышает объем свободной памяти исполнителя.
- **Причина 3: Нехватка памяти вне кучи (Off-heap / Memory Overhead)**. Ошибка `Container killed by YARN for exceeding memory limits`. Воркер потребил больше системной памяти на сериализацию PySpark, чем выделено контейнеру.

#### Алгоритм решения Executor OOM:
1. Открыть **Spark UI**, перейти во вкладку **Stages** и посмотреть распределение времени выполнения задач (Summary Metrics: Min, Median, 75th percentile, Max). Огромный разрыв между Median и Max подтверждает Data Skew.
2. Если обычные партиции слишком велики, подобрать число shuffle partitions по объёму и доступной памяти. Увеличение числа не разбивает один горячий ключ автоматически.
3. Применить технику **Salting** для размазывания тяжелого ключа.
4. Выделить дополнительную память на системные накладные расходы контейнера:
   `spark.executor.memoryOverhead = 2g` (или 15–20% от `spark.executor.memory`).

### Наглядно: две причины памяти и одна проверка гипотезы

```text
Driver: collect 100 ГБ → одна машина → OOM
Executor: один task читает 90% данных → OOM/долгий хвост
Подтверждение: размер входа, max/median tasks, spill, GC, container metrics
```

Большой разрыв max/median — сигнал, а не доказательство skew: возможны медленный узел и I/O. Увеличение shuffle partitions не разбивает один горячий ключ само по себе.

## 2. Идемпотентность пайплайнов (Idempotency)

### Что такое идемпотентность
Конвейер данных называется **идемпотентным**, если повторный запуск задания с теми же входными параметрами (например, запуск за одну и ту же дату `2026-09-18`) приводит к абсолютно одинаковому результату в целевой таблице, не создавая дубликатов и не искажая метрики.

### Антипаттерн (Неидемпотентный пайплайн):
```python
# ОПАСНО: при каждом перезапуске после сбоя данные вставляются повторно!
df.write.mode("append").saveAsTable("analytics.fact_orders")
```

### Правильные подходы:
1. **Атомарная перезапись партиции (Partition Overwrite)**:
   ```python
   # Пример Delta Lake: API replaceWhere зависит от формата и версии
   df.write \
       .format("delta") \
       .mode("overwrite") \
       .option("replaceWhere", "order_date = '2026-09-18'") \
       .saveAsTable("analytics.fact_orders")
   ```
2. **Паттерн Staging -> Delete -> Insert (или MERGE)**:
   ```sql
   BEGIN TRANSACTION;
   DELETE FROM fact_orders WHERE order_date = '2026-09-18';
   INSERT INTO fact_orders SELECT * FROM staging_orders WHERE order_date = '2026-09-18';
   COMMIT;
   ```

### Наглядно: сбой между удалением и вставкой

```text
Без транзакции: DELETE дня → сбой → опубликован пустой день
В транзакции поддерживающей БД: DELETE + INSERT → COMMIT вместе
Повтор одного батча → тот же итог, если вход и правила фиксированы
```

Overwrite должен соответствовать API выбранного формата; replaceWhere — не универсальная опция всех таблиц. Обеспечьте защиту от конкурирующего live-запуска.

## 3. Сдвиг схемы данных (Schema Drift)

В производственных конвейерах системы-источники регулярно вносят несанкционированные изменения в структуру данных: добавляют новые поля, удаляют существующие или меняют типы (`INT` на `VARCHAR`).

### Стратегии обработки:
1. **Строгие контракты данных (Data Contracts)**: валидация схемы на этапе Ingestion (например, с помощью Great Expectations или Pydantic). Записи с некорректной схемой отсекаются в карантинный бакет (Dead Letter Queue, DLQ), а инженеру отправляется алерт.
2. **Автоматическая эволюция схемы (Schema Evolution)**: современные табличные форматы (Delta Lake, Iceberg) поддерживают автоматическое расширение схемы при сохранении совместимости:
   ```python
   df.write \
       .format("delta") \
       .mode("append") \
       .option("mergeSchema", "true") \
       .save("/mnt/lakehouse/silver/events")
   ```

### Наглядно: совместимость и семантика

```text
Добавили nullable note → проверить реальные consumers
amount numeric→string → несовместимость для расчёта
amount всё ещё numeric, но другая валюта → семантическая ошибка
```

Автоматическая schema evolution не проверяет бизнес-смысл. Изолируйте плохие записи или блокируйте публикацию по договору и храните причину отклонения.

## 4. Проблема мелких файлов (Small Files Problem)

### Суть проблемы
Когда потоковый конвейер или частые батчи пишут в HDFS или S3 данные каждые 5 минут, в хранилище образуются миллионы файлов размером по 10–50 КБ.
- В HDFS каждый файл занимает память NameNode (~150 байт на метаданные), что приводит к падению NameNode при миллионах файлов.
- При чтении в Spark запуск отдельной задачи (Task) на каждый крошечный файл тратит 99% времени на накладные расходы создания задач и HTTP-запросы `LIST`/`GET` к S3.

### Решения:
1. **Консолидация перед записью**: вызов `df.coalesce(N)` перед сохранением, где $N$ рассчитано так, чтобы размер каждого файла составлял 128–512 МБ.
2. **Периодическая компактизация (Compaction Job)**: фоновый ночной Airflow DAG читает директорию за прошедший день, выполняет `repartition` и перезаписывает данные крупными блоками.
3. **Использование встроенных механизмов**:
   - В Delta Lake: команда `OPTIMIZE table_name;` сжатия мелких файлов в блоки по 1 ГБ.
   - В Apache Iceberg: вызов процедуры `system.rewrite_data_files`.

### Наглядно: стоимость мелких файлов

```text
1 ГБ: 100 000 файлов по ~10 КБ → множество операций и метаданных
Тот же объём: несколько крупных файлов → меньше накладных расходов
Compaction → новый набор файлов → безопасная публикация
```

Spark может объединять несколько файлов в одну task; проблема не сводится к правилу «один файл — одна task». Целевой размер выбирают по формату, параллелизму и нагрузке.

## 5. Сверка данных (Data Reconciliation)

Как обнаружить расхождения между источником и хранилищем?
Каждый надежный конвейер включает шаг аудита:
```sql
-- Автоматизированная проверка контрольных сумм и количества строк
WITH SourceStats AS (
    SELECT 
        'source_crm' AS system,
        COUNT(*) AS row_cnt,
        COALESCE(SUM(amount), 0) AS total_sum
    FROM crm_orders_export
    WHERE order_date = '2026-09-18'
),
TargetStats AS (
    SELECT 
        'dwh_fact' AS system,
        COUNT(*) AS row_cnt,
        COALESCE(SUM(amount), 0) AS total_sum
    FROM fact_orders
    WHERE order_date = '2026-09-18'
)
SELECT 
    s.row_cnt - t.row_cnt AS row_count_diff,
    s.total_sum - t.total_sum AS amount_diff
FROM SourceStats s
CROSS JOIN TargetStats t;
```
Если `row_count_diff != 0` или `ABS(amount_diff) > 0.01`, проверка фиксирует расхождение. Допуск, политика блокировки и действия задаются договором; проверяйте обе стороны отклонения и тип decimal. Совпавшие агрегаты требуют дополнительных проверок ключей и значений.

### Наглядно: одинаковая сумма скрывает расхождение

```text
Источник: id1=100, id2=200 → count=2, SUM=300
Приёмник: id1=150, id2=150 → count=2, SUM=300
Сравнение по ключу → две changed rows
```

Count/SUM — первый уровень сверки. Затем ищут missing/extra/changed ключи на одинаковом snapshot/cutoff. Денежную разницу сравнивают по ABS с согласованной точностью.
