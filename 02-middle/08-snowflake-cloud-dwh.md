# Архитектура и разработка в Snowflake Cloud DWH (Уровень Middle)

Snowflake — ведущее облачное корпоративное аналитическое хранилище данных. Его уникальная трехуровневая архитектура (Multi-Cluster Shared Data) полностью разделяет вычисления и хранение, кардинально меняя подходы к проектированию конвейеров данных, клонированию сред и управлению расходами.

---

## 1. Трехуровневая архитектура Snowflake

```text
               +-------------------------------------------+
               |           Слой Cloud Services             |
               | (Аутентификация, метаданные, транзакции,  |
               |  оптимизатор CBO, контроль доступа RBAC)  |
               +---------------------+---------------------+
                                     |
    +--------------------------------+--------------------------------+
    |                                |                                |
+---v------------------------+  +----v-----------------------+  +-----v-----------------------+
|  Virtual Warehouse: ETL    |  | Virtual Warehouse: BI      |  | Virtual Warehouse: ML Data  |
|  (Кластер Compute: Large)  |  | (Кластер Compute: Small)   |  | (Кластер Compute: X-Large)  |
+----------------------------+  +----------------------------+  +-----------------------------+
    |                                |                                |
    +--------------------------------+--------------------------------+
                                     | Доступ к общему хранилищу по сети
               +---------------------v---------------------+
               |         Слой Database Storage             |
               | (Amazon S3 / GCS / Azure Blob)            |
               | - Неизменяемые микропартиции              |
               | - Колоночный формат, компрессия Zstandard |
               +-------------------------------------------+
```

### 1. Database Storage (Хранилище)
- Физические данные лежат в блочном объектном хранилище (AWS S3, Azure Blob, GCS) в проприетарном колоночном формате.
- Все данные автоматически разбиваются на **микропартиции** (Micro-partitions) размером 50–500 МБ несжатых данных. Микропартиции **неизменяемы (Immutable)**: любое обновление (`UPDATE`) создает новые микропартиции, а старые остаются для версионирования.

### 2. Query Processing / Virtual Warehouses (Вычислительный слой)
- Виртуальные склады — это независимые кластеры виртуальных машин (размеры от X-Small: 1 нода до 6X-Large: 512 нод).
- **Полная изоляция нагрузок**: тяжелый ночной ETL-пайплайн никогда не замедлит BI-дэшборды генерального директора, так как они работают на физически изолированных складах.
- **Экономия ресурсов**: виртуальный склад запускается за 1–2 секунды и автоматически засыпает при отсутствии запросов (`AUTO_SUSPEND = 60, AUTO_RESUME = TRUE`).

### 3. Cloud Services (Управляющий мозг)
- Координирует всю систему: хранит метаданные микропартиций (min/max значения каждой колонки), обрабатывает транзакции ACID, управляет кэшированием результатов запросов.

## 2. Микропартиционирование и ключи кластеризации (Clustering Keys)

В отличие от традиционных СУБД, в Snowflake **нет индексов** и ручного партиционирования по директориям.

### Как работает отсечение партиций (Partition Pruning):
При записи строк Snowflake автоматически формирует микропартиции и сохраняет их метаданные в Cloud Services (минимальное и максимальное значение каждой колонки внутри микропартиции). 
При выполнении запроса:
```sql
SELECT * FROM fact_sales 
WHERE order_date BETWEEN '2026-09-01' AND '2026-09-15';
```
Cloud Services мгновенно сравнивает предикат `WHERE` с метаданными и дает виртуальному складу команду прочитать только 3 микропартиции из 10 000. Это происходит без чтения самих данных с диска.

### Ключи кластеризации (Clustering Keys):
Если на таблице размером в несколько терабайт запросы регулярно фильтруют по двум полям (`WHERE customer_id = 101 AND status = 'PAID'`), микропартиции со временем могут фрагментироваться. Инженер может задать ключ кластеризации:
```sql
ALTER TABLE fact_sales CLUSTER BY (customer_id, status);
```
*Важное правило*: Ручная кластеризация стоит денег (фоновый сервис Automatic Clustering потребляет кредиты). Ее имеет смысл включать **только для таблиц размером более 1–2 ТБ**, где естественное время запроса превышает десятки секунд.

## 3. Уникальные возможности Snowflake

### 1. Бесплатное мгновенное клонирование (Zero-Copy Cloning)
Позволяет создать мгновенную изолированную копию всей боевой базы данных или таблицы для тестирования или отладки, **не копируя ни одного байта физических данных**:
```sql
-- Мгновенно создается тестовая схема для экспериментов без дублирования расходов на диск!
CREATE OR REPLACE SCHEMA analytics_dev CLONE analytics_prod;
```
Копируются только указатели на метаданные. Плата за хранение начнет начисляться только тогда, когда в `analytics_dev` будут внесены изменения (за счет архитектуры Copy-on-Write).

### 2. Путешествие во времени (Time Travel)
Позволяет прочитать состояние таблицы на любой момент в прошлом (до 90 дней на тарифе Enterprise) или восстановить случайно удаленную таблицу:
```sql
-- Запрос данных по состоянию на 2 часа назад:
SELECT * FROM fact_orders AT(OFFSET => -60*120);

-- Восстановление ошибочно удаленной таблицы:
UNDROP TABLE fact_orders;
```

## 4. Конвейеры данных: Streams, Tasks и Dynamic Tables

### 1. Декларативные динамические таблицы (Dynamic Tables — Рекомендуемый подход)
Современный стандарт для построения витрин данных в Snowflake:
```sql
CREATE OR REPLACE DYNAMIC TABLE mart_daily_sales
    TARGET_LAG = '15 minutes'
    WAREHOUSE = transform_wh
    AS
    SELECT 
        order_date,
        store_id,
        SUM(amount) AS total_revenue
    FROM raw_orders
    GROUP BY 1, 2;
```
Snowflake сам отслеживает появление свежих данных в `raw_orders` и автоматически запускает инкрементальное обновление с заданным допустимым отставанием (`TARGET_LAG`).

### 2. Императивный подход: Streams и Tasks
Используется для сложного Change Data Capture (CDC):
- **Stream**: объект, фиксирующий изменения таблицы (INSERT, UPDATE, DELETE) с помощью внутренних дельт.
- **Task**: расписание запуска SQL-команд по крону с условием `WHEN SYSTEM$STREAM_HAS_DATA('my_stream')`.

## 5. Полуструктурированные данные (JSON) и тип VARIANT

Snowflake оптимизирует хранение JSON на уровне колоночного формата:
```sql
-- Поле payload имеет тип VARIANT
SELECT 
    payload:user.id::BIGINT AS user_id,
    payload:user.name::STRING AS user_name,
    f.value:item_name::STRING AS item_name,
    f.value:price::NUMBER(10, 2) AS price
FROM raw_events,
LATERAL FLATTEN(input => payload:cart_items) f;
```
При загрузке JSON в колонку `VARIANT` Snowflake автоматически разбивает частые атрибуты по виртуальным колоночным под-микропартициям, обеспечивая скорость чтения аналитики по JSON со скоростью плоских реляционных таблиц.
