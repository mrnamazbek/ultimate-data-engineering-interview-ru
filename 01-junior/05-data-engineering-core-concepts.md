# Базовые концепции Data Engineering (Уровень Junior)

Этот раздел посвящен фундаментальным архитектурным понятиям, которые должен понимать каждый начинающий инженер данных: как устроены современные конвейеры данных, в чем разница между хранилищами и озерами данных, и какие парадигмы обработки существуют.

---

## 1. Парадигмы обработки данных: Batch, Stream и Real-Time

В современной индустрии данных выбор архитектуры определяется требованиями бизнеса к скорости получения инсайтов (SLA и Latency) и объему информации.

| Характеристика | Пакетная обработка (Batch) | Потоковая обработка (Stream) | Обработка в реальном времени (Real-Time) |
|---|---|---|---|
| **Суть метода** | Накопление порции данных за период (час, день, месяц) и запуск обработки всего батча | Непрерывная построчная обработка входящих событий по мере их поступления | Мгновенная реакция на событие с генерацией обратного действия |
| **Задержка (Latency)** | Минуты, часы, дни | От нескольких сотен миллисекунд до секунд | Микросекунды и миллисекунды |
| **Объем данных** | Высокий (гигабайты, терабайты, петабайты) | Непрерывный поток сообщений переменного объема | Отдельные транзакции и события |
| **Сложность отказоустойчивости** | Низкая (при сбое батч просто перезапускается) | Высокая (необходимо отслеживать смещения/offsets и состояние/state) | Критически высокая |
| **Технологии** | Apache Spark, dbt, Snowflake, Airflow | Apache Kafka, Apache Flink, Spark Streaming | Redis, In-Memory DB, Flink CEP |
| **Типичный бизнес-кейс** | Ежедневный расчет витрин выручки, закрытие финансового месяца | Мониторинг пользовательской активности, кликстрим, GPS-трекинг | Антифрод (блокировка карты при подозрительной транзакции) |

## 2. Конвейеры данных: ETL против ELT

### ETL (Extract, Transform, Load)
- **Традиционный подход**:
  1. Данные извлекаются из источника (**Extract**).
  2. Трансформируются на выделенном сервере/кластере обработки (например, на Spark-кластере или сервере информатики) до сохранения (**Transform**).
  3. Очищенный и агрегированный результат загружается в целевое аналитическое хранилище (**Load**).
- **Плюсы**: В хранилище попадают только проверенные, очищенные и обезличенные данные (соответствие GDPR/ФЗ-152).
- **Минусы**: Жесткая зависимость от структуры: если аналитикам потребуется сырое историческое поле, которое было отброшено на этапе трансформации, его придется загружать заново.

### ELT (Extract, Load, Transform)
- **Современный облачный подход**:
  1. Данные извлекаются из источника (**Extract**).
  2. В сыром виде как есть загружаются в озеро данных или облачное хранилище (**Load**).
  3. Трансформация выполняется внутри самого хранилища силами его распределенного движка (BigQuery, Snowflake, ClickHouse, Databricks) с помощью SQL/dbt (**Transform**).
- **Плюсы**: Высокая скорость первой загрузки, сохранение полной истории сырых данных, максимальная гибкость для аналитиков.
- **Минусы**: Высокие требования к емкости хранилища и разграничению прав доступа к чувствительным сырым данным.

## 3. Эволюция архитектуры хранения: RDBMS, DWH, Data Lake, Lakehouse

### 1. Реляционные СУБД (RDBMS: PostgreSQL, MySQL, Oracle)
- Оптимизированы для OLTP: короткие быстрые транзакции, строгая нормализация, построчное хранение (Row-oriented). Не справляются с аналитическими агрегациями по миллиардам строк.

### 2. Корпоративные хранилища данных (Data Warehouse / DWH: Snowflake, Greenplum, BigQuery)
- Оптимизированы для OLAP: колоночное хранение (Columnar storage), высокая степень сжатия данных, векторное выполнение запросов.
- Хранят только структурированные, очищенные и согласованные данные бизнеса.

### 3. Озера данных (Data Lake: HDFS, AWS S3, Azure Blob / ADLS Gen2, MinIO)
- Хранилища неструктурированных, полуструктурированных и сырых файлов (Parquet, ORC, JSON, CSV, аудио, логи).
- Дешевое масштабируемое дисковое пространство, но без встроенной транзакционности, контроля схемы и индексов («болото данных» / Data Swamp).

### 4. Озера-хранилища (Data Lakehouse: Delta Lake, Apache Iceberg, Apache Hudi)
- Архитектурный гибрид: дешевизна и открытость файлов в Data Lake сочетается с транзакционными гарантиями (ACID), эволюцией схем данных и высокой скоростью DWH.

## 4. Суррогатные ключи против естественных ключей

На собеседованиях регулярно спрашивают: *«Почему в аналитических таблицах фактов и измерений используют суррогатные ключи (Surrogate Keys), а не естественные (Natural/Business Keys)?»*

### Определения
- **Естественный ключ (Natural / Business Key)**: Идентификатор, приходящий из системы-источника (например, ИИН/ИНН, номер паспорта, артикул `SKU-9921`, email).
- **Суррогатный ключ (Surrogate Key)**: Искусственно сгенерированный целочисленный идентификатор или хэш (BigInt, UUID, MD5/SHA256), создаваемый внутри хранилища данных и не имеющий бизнес-смысла.

### Почему суррогатные ключи обязательны в DWH:
1. **Независимость от изменений бизнес-систем**: Если источник изменит формат идентификатора (например, вместо числа станет строка `A-1234`), в DWH с суррогатными ключами архитектура не сломается.
2. **Поддержка медленно меняющихся измерений (SCD Type 2)**: Один и тот же клиент (с одним естественным ID) со временем меняет адрес или фамилию. В DWH для каждой исторической версии строки создается новый суррогатный ключ, в то время как естественный ключ остается одинаковым.
3. **Производительность соединений (JOIN)**: Соединение огромных таблиц фактов с таблицами измерений по компактным 4- или 8-байтным целым числам (`BIGINT`) в разы быстрее, чем по длинным строкам (`VARCHAR(64)`).
4. **Устранение коллизий при слиянии источников**: Если компания покупает другой сервис или объединяет две CRM-системы, в них могут совпадать идентификаторы пользователей (`user_id = 101`). Суррогатный ключ устраняет дублирование.

## 5. Надежность и отказоустойчивость: Паттерн Blue-Green для ETL

При обновлении логики тяжелых ETL-конвейеров нельзя допускать прерывания работы бизнес-отчетов и BI-дэшбордов.

### Как работает Blue-Green для данных:
1. Развертываются два параллельных окружения или две схемы в хранилище: **Blue** (текущая активная схема, откуда читают аналитики) и **Green** (пассивная копия).
2. Новая версия ETL-конвейера заливает и трансформирует данные в окружение **Green**.
3. На окружении Green автоматически прогоняются проверки качества данных (Data Quality Tests: проверка на `NULL`, дубликаты, сверка контрольных сумм).
4. Если тесты успешны, происходит мгновенное переключение (через обновление синонимов, View или табличных указателей). Теперь Green становится активным, а Blue уходит в резерв.
5. Если обнаружена ошибка, данные в Blue остаются нетронутыми, инцидент для пользователей не наступает.
