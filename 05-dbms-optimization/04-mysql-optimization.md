# Оптимизация MySQL и движка InnoDB (MySQL Performance Tuning)

MySQL с транзакционным движком **InnoDB** — одна из самых распространенных СУБД в веб-приложениях и микросервисах. В этом руководстве рассматривается специфика кластерной организации InnoDB, предотвращение фрагментации страниц диска, чтение планов `EXPLAIN` и тюнинг системных параметров.

---

## 1. Анатомия хранения InnoDB: Кластерный и вторичные индексы

Понимание того, как физически хранятся данные в InnoDB, определяет 90% успеха при оптимизации схемы.

```text
               Кластерный индекс (Primary Key)
               +-----------------------------+
               |  Листовой узел B+ Tree      |
               |  [PK] -> [ВСЯ СТРОКА ДАННЫХ]|
               +-----------------------------+
                              ^
                              | Поиск по PK (Double Lookup)
               +--------------+--------------+
               | Вторичный индекс (Secondary)|
               | [Индексный ключ] -> [PK]    |
               +-----------------------------+
```

### 1. Первичный ключ (Primary Key) — всегда кластерный
- Все строки таблицы физически упорядочены на диске по первичному ключу.
- Листовой узел дерева B+ Tree содержит **полную строку со всеми полями**.

### 2. Вторичные индексы (Secondary Indexes) и двойной поиск (Double Lookup)
- Листовые узлы любого вторичного индекса содержат значение индексного поля и **значение первичного ключа** (а не физический адрес строки на диске).
- Если запрос фильтрует по вторичному индексу, но запрашивает колонки, которых в нем нет:
  1. СУБД находит значение во вторичном индексе и извлекает `Primary Key`.
  2. Делает второй переход в дерево кластерного индекса по найденному `Primary Key` (**Bookmark / Double Lookup**), чтобы прочитать остальные поля.
- *Решение*: Использование **покрывающего индекса** (Covering Index), содержащего все поля запроса. В выводе `EXPLAIN` в колонке `Extra` появляется `Using index` — двойной поиск устранен.

### 3. Почему случайный UUID v4 губителен для Primary Key в MySQL:
Если сделать первичным ключом случайный UUID v4 (`36-символьная строка`):
- Новые записи вставляются не в конец таблицы, а в случайные середины страниц B+ Tree.
- Возникает постоянное **расщепление страниц (Page Split)**: страница данных заполняется, СУБД вынуждена делить ее пополам, выделять новый блок и перестраивать дерево.
- Размер таблицы раздувается в 2–3 раза из-за полупустых страниц, а скорость дисковой записи падает на 80%.
- *Правило*: В качестве Primary Key всегда используйте монотонно возрастающие целочисленные ключи (`BIGINT AUTO_INCREMENT`) или упорядоченные во времени UUID (ULID / UUID v7).

## 2. Анализ планов выполнения: `EXPLAIN` в MySQL

```sql
EXPLAIN FORMAT=TREE
SELECT o.id, o.order_date, c.name
FROM orders o
JOIN customers c ON o.customer_id = c.id
WHERE o.status = 'COMPLETED'
ORDER BY o.order_date DESC
LIMIT 10;
```

### Иерархия эффективности типов доступа (Колонка `type`):
От лучших к худшим:
1. `system` / `const`: выборка 1 строки по первичному ключу (мгновенно).
2. `eq_ref`: соединение, при котором для каждой строки извлекается ровно 1 строка из другой таблицы по первичному ключу (идеальный `JOIN`).
3. `ref`: поиск по некластерному индексу, возвращающий несколько строк.
4. `range`: сканирование диапазона строк по индексу (`BETWEEN`, `<`, `>`).
5. `index`: полное сканирование всего дерева индекса (лучше, чем таблицы, но все равно медленно).
6. `ALL`: **Full Table Scan** — полное последовательное сканирование всех страниц таблицы (сигнал отсутствия индекса).

### Критические маркеры в колонке `Extra`:
- `Using index`: **Отлично**. Запрос выполнен исключительно по индексу (Covering Index) без чтения данных таблицы.
- `Using where`: Фильтрация строк на уровне движка SQL после получения из хранилища.
- `Using temporary`: **Опасно**. СУБД создала временную таблицу в памяти или на диске для выполнения `GROUP BY` или `DISTINCT`.
- `Using filesort`: **Опасно**. СУБД не смогла использовать порядок индекса для `ORDER BY` и выполнила дополнительный проход сортировки в оперативной памяти или на диске.

## 3. Настройка параметров конфигурации (`my.cnf`)

| Параметр | Рекомендуемое значение | Зачем нужен |
|---|---|---|
| `innodb_buffer_pool_size` | 60–70% от всей RAM сервера | Главный буферный пул ОЗУ, в котором InnoDB держит кэш страниц данных и индексов. Увеличение этого параметра исключает дисковый I/O |
| `innodb_log_file_size` | 25% от размера Buffer Pool (например, 2G–4G) | Размер файлов журнала повтора (Redo Log). Большой размер сглаживает пики записи при массовых транзакциях |
| `innodb_flush_log_at_trx_commit` | `1` (строгий ACID) или `2` (для ETL) | При значении `1` Redo Log сбрасывается на диск при каждом коммите. Значение `2` сбрасывает лог в кэш ОС и пишет на диск раз в секунду, ускоряя массовую вставку данных в 5–10 раз |
| `innodb_file_per_table` | `ON` | Каждая таблица сохраняется в отдельном файле `.ibd`, а не в общей системной табличной области, что позволяет возвращать дисковое пространство ОС при `TRUNCATE` |

## 4. Поиск медленных запросов: Slow Query Log

Включение журнала медленных запросов в `my.cnf`:
```ini
slow_query_log = 1
slow_query_log_file = /var/log/mysql/mysql-slow.log
long_query_time = 1.0        # логировать запросы, длящиеся более 1 секунды
log_queries_not_using_indexes = 1 # фиксировать запросы без индексов
```

### Анализ лога через Percona Toolkit:
Анализировать миллион строк текстового лога вручную невозможно. Используйте отраслевой стандарт:
```bash
pt-query-digest /var/log/mysql/mysql-slow.log > slow_report.txt
```
Утилита сгруппирует запросы по сигнатурам и выведет Топ-10 запросов, генерирующих максимальную нагрузку на сервер (по параметрам Query Time, Lock Time, Rows Sent, Rows Examined).
