## 1. Архитектура памяти Executor (Unified Memory Manager)

Память каждого Spark Executor (JVM-процесса) жестко разделена на логические пулы:

```text
+-------------------------------------------------------------------------+
|                        Total Executor Memory                            |
+-------------------------------------------------------------------------+
| System Overhead | Reserved  |               Unified Memory Pool         |
| (off-heap / OS) |  Memory   |               (spark.memory.fraction)     |
|                 | (300 MB)  |  +-------------------+------------------+ |
|                 |           |  |  Storage Memory   | Execution Memory | |
|                 |           |  |  (кэш датасетов)  | (Shuffle / Joins)| |
|                 |           |  +-------------------+------------------+ |
|                 |           |      User Memory (структуры Python/UDF)   |
+-----------------+-----------+-------------------------------------------+
```

1. **Reserved Memory (300 МБ)**: фиксированная зарезервированная системная память под внутренние процессы самого Spark.
2. **User Memory (по умолчанию ~40%)**: `(1 - spark.memory.fraction)`. Служит для хранения собственных структур данных пользователя, метаданных и внутренних коллекций UDF.
3. **Spark Memory Pool (по умолчанию 60%)**: пул, регулируемый `spark.memory.fraction`. Он разделен между:
   - **Storage Memory**: кэшированные датасеты (`cache()`, `persist()`) и broadcast-переменные.
   - **Execution Memory**: рабочие буферы для операций Shuffle, Hash Join, агрегаций и сортировок.
4. **Динамическое вытеснение (Eviction Policy)**:
   - Если памяти для Execution не хватает, Spark может принудительно вытеснить данные из Storage Memory на диск.
   - Если данные заняты Execution Memory, Storage **не может** вытеснить их обратно, пока не завершится расчет задачи.

## 2. Глубокое погружение в Shuffle: Index File, Data File и Spill to Disk

### Как физически работает Shuffle:
1. **Shuffle Write (Фаза маппера)**:
   - Исполнитель берет строки, вычисляет партицию получателя (`hash(key) % numPartitions`) и складывает данные во внутренний буфер в оперативной памяти (AppendOnlyMap).
   - Когда буфер заполняется, данные сортируются и сбрасываются во временный spill-файл на локальный диск.
   - По завершении все промежуточные сбросы объединяются в единый **Data File**, и создается крошечный **Index File**, хранящий смещения (байтовые оффсеты) каждой партиции внутри файла данных.
2. **Shuffle Read (Фаза редьюсера)**:
   - Исполнители следующей стадии обращаются к Shuffle-сервису других нод через асинхронный сетевой протокол Netty и выкачивают свои блоки байтов по сети.

### Проблема Spill to Disk (Сброс на диск)
В Spark UI можно увидеть метрики:
- **Spill (Memory)**: объем данных в десериализованном виде, который не поместился в ОЗУ.
- **Spill (Disk)**: физический объем тех же данных после сериализации и сжатия, записанный на локальный SSD/HDD.

*Почему Spill опасен*: Запись на диск и последующее повторное чтение увеличивают время выполнения задачи в 5–10 раз.
*Как устранить*:
- Увеличить `spark.executor.memory`.
- Увеличить количество партиций (`spark.sql.shuffle.partitions`), чтобы порции данных в каждом таске стали меньше.

## 3. Стратегии распределенных соединений (Join Strategies)

При планировании запроса физический оптимизатор выбирает одну из 5 стратегий:

| Стратегия | Сетевые накладные расходы | Требования к ресурсам | Сценарий применения |
|---|---|---|---|
| **Broadcast Hash Join (BHJ)** | Минимальные (нет Shuffle) | Одна из таблиц должна помещаться в память драйвера и каждого воркера | Одна маленькая таблица (< 10 МБ по умолчанию: `spark.sql.autoBroadcastJoinThreshold`) соединяется с большой |
| **Shuffle Hash Join (SHJ)** | Высокие (Shuffle обеих таблиц) | Меньшая из партиций должна помещаться в память воркера | Ключи нельзя отсортировать эффективно, таблицы среднего размера |
| **Sort Merge Join (SMJ)** | Высокие (Shuffle + сортировка) | Требует дискового пространства под сброс сортировки | Стандартное соединение двух огромных таблиц (миллиарды строк) |
| **Broadcast Nested Loop Join** | Умеренные | Высокая нагрузка на CPU ($O(N \times M)$) | Соединения без условий равенства (например, `t1.val > t2.val`) |
| **Cartesian Join** | Экстремальные ($N \times M$) | Огромные ресурсы | Явный `CROSS JOIN` |

### Пример явного хинта на Broadcast Join:
```python
from pyspark.sql.functions import broadcast

# Принудительный broadcast справочника, гарантирующий отсутствие тяжелого Shuffle
enriched_df = large_fact_df.join(broadcast(small_dim_df), "category_id", "inner")
```

## 4. Борьба с перекосом данных (Data Skew): Паттерн Salting

### Симптомы перекоса в продакшне:
Пайплайн висит на 99% (например, `Stage 4: 199/200 tasks completed`). Один таск обрабатывает 10 ГБ данных, в то время как остальные 199 обработали по 50 МБ.

### Техника засолки ключей (Key Salting):
Суть идеи: искусственно размазать строки с популярным ключом по случайным под-партициям.

```python
import pyspark.sql.functions as F

# 1. Добавляем случайную соль (от 0 до 9) к ключу в большой перекошенной таблице фактов
SALT_FACTOR = 10
skewed_fact = fact_df.withColumn(
    "salted_key", 
    F.concat(F.col("skewed_key"), F.lit("_"), F.floor(F.rand() * SALT_FACTOR))
)

# 2. Размножаем справочник (Replication / Explode), чтобы в нем были все варианты солей от 0 до 9
salt_array = F.array([F.lit(i) for i in range(SALT_FACTOR)])
replicated_dim = dim_df.withColumn("salt_val", F.explode(salt_array)) \
    .withColumn("salted_key", F.concat(F.col("key"), F.lit("_"), F.col("salt_val")))

# 3. Выполняем идеальный равномерный Join по засоленному ключу без перекоса!
joined_df = skewed_fact.join(replicated_dim, "salted_key", "inner") \
    .drop("salted_key", "salt_val")
```

## 5. Адаптивное выполнение запросов (Adaptive Query Execution — AQE)

Начиная со Spark 3.0, движок может перестраивать физический план прямо во время выполнения задач на основе фактической статистики после завершения стадий Shuffle.

### Ключевые возможности AQE:
1. **Динамическое слияние мелких партиций (`spark.sql.adaptive.coalescePartitions.enabled`)**:
   Если после выполнения фильтрации многие партиции стали весить по 10 КБ, Spark автоматически склеит их перед следующим шагом, предотвращая запуск тысяч лишних микро-тасок.
2. **Динамическое переключение на Broadcast Join (`spark.sql.adaptive.autoBroadcastJoinThreshold`)**:
   Если на этапе компиляции таблица казалась большой, но после фильтрации сжалась до 5 МБ, AQE на лету заменит медленный Sort Merge Join на быстрый Broadcast Hash Join.
3. **Автоматическая обработка Data Skew (`spark.sql.adaptive.skewJoin.enabled`)**:
   AQE автоматически детектирует аномально большие партиции на стадии Shuffle и делит их на более мелкие фрагменты без необходимости ручного кода с Salting.
