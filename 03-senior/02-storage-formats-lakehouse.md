## 1. Формат файлов против Формата таблиц (File Format vs Table Format)

На собеседовании кандидатов часто ловят на вопросе: *«Чем отличается Parquet от Iceberg?»*

- **Формат файлов (File Format: Parquet, ORC, Avro)**:
  Определяет, как байты конкретных строк и колонок физически упакованы и сжаты внутри одного изолированного файла. Parquet обеспечивает колоночное сжатие (Snappy/ZSTD) и min/max статистику на уровне Row Group.
- **Формат таблиц (Table Format: Apache Iceberg, Delta Lake, Apache Hudi)**:
  Определяет, как **сотни тысяч разрозненных файлов** объединяются в единую логическую таблицу с гарантиями транзакций (ACID), версионированием, эволюцией схемы и атомарными коммитами.

### Наглядно: Parquet внутри таблицы

```text
Parquet → как прочитать байты одного файла
Iceberg table → какие файлы относятся к согласованному snapshot
Новые Parquet-файлы сами по себе ещё не опубликованы в таблице
```

Табличный формат добавляет метаданные и протокол commit, не заменяя файловый формат. Движок и catalog должны поддерживать соответствующие операции.

## 2. Архитектура метаданных Apache Iceberg

В классическом Hive таблица — это просто папка на HDFS/S3, а список файлов получается медленной операцией листинга директорий (`LIST`). В Apache Iceberg состояние таблицы полностью определяется древовидным графом файлов метаданных:

```text
               +-----------------------------+
               |       Iceberg Catalog       |
               | (Nessie, Glue, REST, Hive)  |
               +--------------+--------------+
                              | указывает на текущую версию
               +--------------v--------------+
               |     Metadata JSON File      |  (v2.metadata.json)
               | - Schema, Partition Spec    |
               | - Current Snapshot Pointer  |
               +--------------+--------------+
                              |
               +--------------v--------------+
               |     Manifest List File      |  (snap-101.avro)
               | - Список манифестов         |
               | - Min/Max границы разделов  |
               +--------------+--------------+
                              |
               +--------------v--------------+
               |     Manifest Files (.avro)  |  (m-0.avro, m-1.avro)
               | - Список файлов данных      |
               | - Статистика колонок (null) |
               +--------------+--------------+
                              |
            +-----------------+-----------------+
            |                                   |
+-----------v-----------+           +-----------v-----------+
|    Data File (.parquet)|           |    Data File (.parquet)|
+-----------------------+           +-----------------------+
```

### Преимущества такой трехуровневой архитектуры:
1. **Атомарная публикация**: согласованный протокол catalog меняет текущую версию metadata. Подготовка файлов, валидация конфликтов и размер commit могут требовать работы, зависящей от объёма изменения.
2. **Pruning файлов по метаданным**: движок читает метаданные и может исключить неподходящие data files до чтения их содержимого. Доля зависит от layout, статистики и предикатов.
3. **Time Travel**: чтение сохранённого snapshot по ID или подходящему времени. Expiration и удаление файлов ограничивают доступную историю.
4. **Скрытое партиционирование (Hidden Partitioning)**: пользователю не нужно явно передавать в запрос технические поля партиций. Если партиционирование настроено по `days(event_timestamp)`, запрос `WHERE event_timestamp >= '2026-09-01'` автоматически превратится в фильтрацию нужных партиций без риска ошибок аналитика.

### Наглядно: читатели и конкурирующие commit

```text
Reader R1 закрепил snapshot S1 → читает его файлы
Writer создаёт новые data/metadata → пытается commit S2
Catalog атомарно меняет текущую версию → новый Reader R2 видит S2
Конфликт writer → проверка и retry; неподключённые файлы не видны как строки
```

Атомарный переход не означает O(1) полной подготовки commit. Time Travel работает только для сохранённых snapshots/файлов; hidden partitioning преобразует бизнес-фильтр согласно partition spec.

## 3. Практический кейс: Миграция 40 ТБ исторических данных из RDBMS в Iceberg

Реальная задача с собеседования: *«Вам необходимо выгрузить и заархивировать 40 ТБ исторических данных из стареющей СУБД (Oracle / MS SQL) в Iceberg на объектное хранилище (Google Cloud Storage / AWS S3). Как построить процесс надежно и дешево?»*

### Пошаговый план реализации:
1. **Фаза 1: Срез данных и параллельная выгрузка (Ingestion)**:
   - Нельзя выгружать 40 ТБ одним запросом (вызовет блокировку таблиц СУБД и переполнение журналов redo/undo log).
   - Разбить выгрузку на батчи по историческим диапазонам (по месяцам или дням через первичный ключ).
   - Использовать распределенный конвейер (Spark на пуле виртуальных машин) с параллельным чтением через JDBC с настройками `partitionColumn`, `lowerBound`, `upperBound`, `numPartitions`.
2. **Фаза 2: Запись в Iceberg на Cloud Storage**:
   ```python
   # Запись выгруженных батчей в формат Iceberg с колоночным сжатием ZSTD
   spark.conf.set("spark.sql.catalog.iceberg_catalog", "org.apache.iceberg.spark.SparkCatalog")
   spark.conf.set("spark.sql.catalog.iceberg_catalog.type", "rest")

   df_historical.write \
       .format("iceberg") \
       .mode("append") \
       .partitionBy("years(order_date)") \
       .save("iceberg_catalog.archive.fact_orders_legacy")
   ```
3. **Фаза 3: Оптимизация расходов на облако (Cost Optimization)**:
   - Использовать **прерываемые (Preemptible / Spot) виртуальные машины** для вычислительного кластера (Dataproc / EMR). Это снижает стоимость CPU/RAM на 70–80%. При отключении отдельной ноды Spark автоматически перезапустит упавшие таски на оставшихся узлах.
   - Настроить правила жизненного цикла (Object Lifecycle Rules) в хранилище: через 90 дней после архивации переводить данные в архивный холодный класс хранения (GCS Archive / AWS Glacier Deep Archive).
4. **Фаза 4: Верификация и компактизация**:
   - Сверка контрольных сумм и количества строк между источником и архивом.
   - Запуск ночной процедуры компактизации мелких файлов:
     ```sql
     CALL iceberg_catalog.system.rewrite_data_files(
         table => 'archive.fact_orders_legacy',
         strategy => 'binpack',
         options => map('target-file-size-bytes', '536870912') -- 512 МБ
     );
     ```
   - Удаление устаревших снимков метаданных для экономии дискового пространства:
     ```sql
     CALL iceberg_catalog.system.expire_snapshots(
         table => 'archive.fact_orders_legacy',
         older_than => TIMESTAMP '2026-09-01 00:00:00'
     );
     ```

### Наглядно: выгрузка без разрыва между snapshot и изменениями

```text
Согласованный cutoff T → historical export до T
Изменения после T → захват/дочитывание по выбранному протоколу
Сверка ключей и значений → публикация → контроль потребителей
```

Сам watermark по дате не обеспечивает согласованность изменяемого источника. Для 40 ТБ считайте пропускную способность, нагрузку на источник, повторяемость чанков, стоимость и время восстановления.
