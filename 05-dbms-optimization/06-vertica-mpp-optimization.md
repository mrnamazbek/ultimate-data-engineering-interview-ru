# Оптимизация OpenText Vertica (HP Vertica MPP)

OpenText Vertica (ранее HP Vertica) — высокопроизводительная колоночная аналитическая СУБД с архитектурой Shared-Nothing. В Vertica **отсутствуют традиционные индексы** (B-Tree): скорость выборки достигается за счет проекций (Projections), предсортировки данных на диске и алгоритмов специализированного кодирования колонок.

---

## 1. Архитектура проекций (Projections)

В Vertica логическая таблица (`TABLE`) — это лишь определение схемы. Физически данные хранятся в **проекциях** (Projections).

```text
Логическая таблица: FACT_ORDERS (id, customer_id, order_date, amount, status)
                               |
            +------------------+------------------+
            |                                     |
+-----------v-----------+             +-----------v-----------+
|    Суперпроекция      |             | Аналитическая проекция|
| (Все 5 колонок)       |             | (customer_id, amount, |
| ORDER BY order_date   |             |  order_date)          |
| SEGMENTED BY customer |             | ORDER BY customer_id  |
+-----------------------+             +-----------------------+
```

### 1. Суперпроекции (Superprojections)
- Проекция, содержащая **все колонки** таблицы.
- Создается автоматически при первой загрузке данных, если не была определена вручную. Гарантирует возможность выполнить `SELECT *`.

### 2. Специализированные проекции (Query-Specific Projections)
- Содержат только подмножество колонок, необходимых для конкретной группы тяжелых отчетов, с индивидуальным порядком сортировки `ORDER BY`.

### 3. Сегментация (Segmentation):
- `SEGMENTED BY HASH(customer_id) ALL NODES`: данные таблицы равномерно нарезаются по всем узлам кластера по хэшу ключа. Применяется для больших таблиц фактов.
- `UNSEGMENTED ALL NODES`: полная копия проекции сохраняется на каждом узле кластера. Применяется для небольших справочников измерений до 1 млн строк для устранения сетевого пересыла при `JOIN`.

## 2. Кодирование данных (Column Encodings)

В Vertica правильный выбор алгоритма кодирования колонки важнее аппаратных ресурсов. Кодирование определяет не только степень сжатия диска, но и позволяет Vertica выполнять предикаты `WHERE` **напрямую над сжатыми данными** без их декомпрессии в памяти.

| Тип кодирования | Принцип работы | Идеальный сценарий |
|---|---|---|
| **RLE (Run-Length Encoding)** | Заменяет последовательности одинаковых значений парами `(значение, счетчик)` | Первая колонка в `ORDER BY` проекции с низкой или средней кардинальностью (например, `status`, `country`) |
| **DELTAVAL** | Сохраняет разницу (дельту) между последовательными значениями | Монотонно возрастающие целочисленные идентификаторы или даты/метки времени |
| **BLOCKDICT** | Словарное кодирование блоков | Строковые колонки средней кардинальности (`VARCHAR` категории, марки машин) |
| **AUTO** | Vertica автоматически подбирает алгоритм на основе выборки | Значения по умолчанию |

### Пример проектирования сверхбыстрой проекции:
```sql
CREATE PROJECTION analytics.fact_orders_opt
(
    order_date ENCODING RLE,           -- отсортированная дата идеально сжимается в RLE
    customer_id ENCODING DELTAVAL,     -- дельты по идентификаторам
    status ENCODING RLE,               -- статусы (3-5 уникальных значений)
    amount ENCODING AUTO
)
AS SELECT order_date, customer_id, status, amount
FROM analytics.fact_orders
ORDER BY order_date, status, customer_id -- порядок сортировки на диске!
SEGMENTED BY HASH(customer_id) ALL NODES;
```

## 3. Механизм Tuple Mover: WOS, ROS и ROS Pushback

Под капотом Vertica разделяет запись на два слоя:
1. **WOS (Write Optimized Store)**: буфер в оперативной памяти без сжатия для быстрого приема мелких транзакций.
2. **ROS (Read Optimized Store)**: постоянное дисковое хранилище, где данные отсортированы, закодированы и сжаты в отдельные контейнеры.

### Фоновые процессы Tuple Mover:
- **Moveout**: фоновый процесс перемещения данных из памяти WOS в новые ROS-контейнеры на диске.
- **Mergeout**: фоновый процесс слияния множества мелких ROS-контейнеров в крупные (аналог Compaction в LSM).

### Проблема ROS Pushback (Отказ в записи):
По умолчанию Vertica разрешает не более 1024 ROS-контейнеров на проекцию. Если загружать данные частыми мелкими батчами (например, по 10 строк каждые 5 секунд), Tuple Mover не успевает выполнять слияние. Vertica выбрасывает фатальную ошибку **`Too many ROS containers (ROS pushback)`** и полностью блокирует запись в таблицу.

#### Решение: Прямая загрузка в ROS (DIRECT)
При любых пакетных загрузках в DWH обходите буфер WOS с помощью директивы `DIRECT`:
```sql
-- Прямая запись сразу в постоянные дисковые ROS-контейнеры минуя память WOS
COPY analytics.fact_orders 
FROM 's3://bucket/orders_2026.csv' 
DELIMITER ',' 
DIRECT;
```

## 4. Автоматическая оптимизация: Database Designer (DBD)

Вместо ручного подбора проекций для сотен таблиц в Vertica встроен инструмент **Database Designer (DBD)**. 
- Инженер подает в DBD файл со списком репрезентативных медленных запросов (`queries.sql`) и статистику объемов данных.
- DBD прогоняет оптимизационный алгоритм, генерирует DDL-скрипт с набором идеальных проекций, кодировок и ключей сортировки, а затем автоматически перестраивает физическое хранение.
