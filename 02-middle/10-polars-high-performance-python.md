# 10. Высокопроизводительный Python: Polars и Apache Arrow

## 1. Введение: Когда выбирать Pandas, Polars или распределённый движок

Pandas остаётся полезен для локального анализа и совместимости с Python-экосистемой. При выборе учитывайте свойства конкретного workload:
1. **Параллелизм**: обычный Pandas API не является распределённым движком; нативные операции могут освобождать GIL, но степень параллелизма зависит от реализации.
2. **Память**: `object`-строки имеют значительный overhead; NumPy- и Arrow-backed типы хранят данные иначе. Размер файла после сжатия не равен требованию к RAM, универсального коэффициента нет.
3. **Eager execution**: многие операции вычисляются сразу; расходы промежуточных результатов зависят от операций и версии. Lazy API Polars позволяет оптимизировать цепочку до исполнения.
4. **Оптимизация плана**: LazyFrame может применять pushdown и pruning. В Pandas часть отбора тоже можно задать при чтении; сравнивайте реальные пути загрузки и расчёта.

**Polars** — это современная колоночная библиотека для работы с табличными данными, написанная на языке Rust с нуля поверх стандарта **Apache Arrow**. Она спроектирована для максимальной утилизации современных многоядерных процессоров и векторных инструкций (SIMD).

### Наглядно: выбор движка по задаче

```text
Небольшой набор и существующая экосистема → Pandas может быть достаточен
Локальные табличные расчёты с lazy plan → кандидат Polars
Распределённые объёмы и кластер → кандидат Spark
```

Сравнивайте время, peak RAM и удобство нужных операций. Pandas поддерживает NumPy- и Arrow-backed типы; нельзя описывать все его данные как Python-объекты или объявлять его всегда устаревшим.

## 2. Архитектурный фундамент Polars

### 2.1. Стандарт Apache Arrow в памяти
В отличие от Pandas, где строковые данные хранятся как массив ссылок на Python-объекты, Polars использует спецификацию Apache Arrow:
- **Колоночное представление (Columnar In-Memory Format)**: Все значения одного столбца хранятся в непрерывном блоке оперативной памяти. Это обеспечивает максимальное попадание в L1/L2/L3 кэш процессора.
- **Векторизация (SIMD - Single Instruction, Multiple Data)**: Процессор за один машинный такт выполняет операцию сразу над 4, 8 или 16 элементами столбца.
- **Zero-Copy**: для совместимых типов и layout обмен с Arrow-инструментами может переиспользовать буферы. Преобразования типов и несовместимые структуры требуют копирований.

### 2.2. Многопоточный параллелизм на Rust
Нативные операции Polars могут использовать несколько потоков вне Python GIL. Не каждая операция распараллеливается одинаково; число потоков, зависимости плана и Python UDF влияют на результат.

### Наглядно: колоночные буферы и Arrow

```text
Строки: (id1,amount1),(id2,amount2)
Колонки: id=[1,2]; amount=[10,20]; NULL mask=[valid,valid]
Нативный оператор → работает с массивами значений
```

Это помогает векторизации и уменьшает расходы Python. Zero-copy возможен для совместимых типов и операций, но не универсален: преобразование типа и layout может потребовать копирования.

## 3. Выражения (Expressions API): Философия декларативных вычислений

В Pandas для сложных вычислений часто используют `df.apply(lambda row: ...)` или циклы `for`, что уничтожает производительность.

В Polars табличные операции удобно описывать через **Expressions** — декларативные узлы расчёта. Движок планирует их и исполняет подходящими нативными операторами; это не означает обязательную отдельную JIT-компиляцию каждого выражения.

```python
import polars as pl

df = pl.DataFrame({
    "user_id": [1, 2, 3, 4],
    "category": ["electronics", "books", "electronics", "fashion"],
    "amount": [1200.0, 450.0, 3200.0, 150.0],
    "quantity": [1, 3, 2, 1]
})

# Декларативная трансформация без единого Python-цикла
result = df.select([
    pl.col("user_id"),
    (pl.col("amount") / pl.col("quantity")).alias("price_per_item"),
    pl.when(pl.col("amount") > 1000)
      .then(pl.lit("VIP"))
      .otherwise(pl.lit("Standard"))
      .alias("client_tier")
])
```

Ключевые контексты выполнения выражений:
- `select()`: проекция и трансформация столбцов.
- `with_columns()`: добавление новых или модификация существующих столбцов без пересоздания таблицы.
- `filter()`: отбор строк по булеву условию (в Pandas: булева индексация).
- `group_by().agg()`: группировка с параллельным вычислением множества агрегатов.

### Наглядно: выражение описывает расчёт

```text
amount=[100,50], quantity=[2,1]
col(amount)/col(quantity) → [50,50]
when amount>80 then VIP else Standard → [VIP,Standard]
```

Контекст определяет длину результата: select выбирает, with_columns добавляет, group_by().agg() сворачивает. Встроенное выражение обычно удобнее Python-функции на каждой строке.

## 4. Ленивые вычисления (Lazy Execution) и Оптимизатор запросов

Основная сила Polars раскрывается при использовании **LazyFrame**.

### 4.1. Разница между Eager и Lazy

- **Eager (`pl.DataFrame`, `pl.read_parquet`)**: чтение и операции выполняются сразу; методы часто возвращают новый результат, а не мутируют исходный DataFrame.
- **Lazy (`pl.LazyFrame`, `pl.scan_parquet`)**: Polars строит логический граф вычислений (Logical Plan). Реальное чтение и расчет начинаются только при вызове метода `.collect()`.

```python
import polars as pl

# 1. scan_parquet НЕ читает весь файл в память, а только считывает метаданные
lazy_query = (
    pl.scan_parquet("s3://lakehouse/gold/orders/*.parquet")
    .filter(pl.col("order_date") >= pl.date(2026, 1, 1))
    .filter(pl.col("status") == "COMPLETED")
    .group_by("customer_id")
    .agg([
        pl.col("total_amount").sum().alias("lifetime_value"),
        pl.col("order_id").count().alias("total_orders")
    ])
    .filter(pl.col("lifetime_value") > 10000)
    .select(["customer_id", "lifetime_value", "total_orders"])
)

# 2. Посмотреть оптимизированный план запроса
print(lazy_query.explain())

# 3. Запуск выполнения
final_df = lazy_query.collect()
```

### 4.2. Встроенные оптимизации физического плана

Перед запуском вычислений оптимизатор Polars автоматически применяет:
1. **Predicate Pushdown (Проталкивание предикатов)**: Условия фильтрации (`order_date >= '2026-01-01'`) спускаются на уровень чтения Parquet. Polars отбрасывает группы строк (Row Groups) еще до их загрузки с диска.
2. **Projection Pushdown (Проталкивание проекций)**: чтение ограничивается колонками, нужными результату и промежуточным операциям, включая фильтры и группировки.
3. **Slice Pushdown**: движок может протолкнуть ограничение строк к источнику, если это сохраняет смысл. После глобальной агрегации или сортировки `limit(100)` не обязательно позволяет прекратить чтение рано.
4. **Common Subplan Elimination**: Повторяющиеся подвыражения рассчитываются один раз и переиспользуются.

### Наглядно: проталкивание чтения

```text
План пользователя: scan 50 колонок → filter → select 3
Оптимизированный план: scan нужных колонок и блоков → filter → результат
```

Для фильтра нужны и его колонки, даже если их нет в финальном select. Pushdown ограничен операторами и источником; смотрите explain, не предполагая, что любой limit остановит чтение сразу.

## 5. Обработка данных больше объема RAM (Streaming Engine)

Если полная материализация превышает доступную RAM, она может привести к OOM. Проекция, чтение чанками или отбор данных уменьшают расходы, если задача это допускает; сравнивайте несжатый working set и размер результата.

Polars имеет встроенный **Streaming Engine**. Он обрабатывает данные порциями (чанками/батчами) через конвейер, сбрасывая промежуточные результаты:

```python
# Потоковая агрегация большого объема данных
result = (
    pl.scan_parquet("large_clickstream_dataset/*.parquet")
    .filter(pl.col("event_type") == "purchase")
    .group_by("product_id")
    .agg(pl.col("price").sum())
    .collect(engine="streaming")  # Текущий API streaming engine
)
```

### Наглядно: streaming и размер состояния

```text
Источник → batch 1 → оператор → следующий batch
Простой filter/select → небольшое состояние
Высококардинальная group_by → состояние всех групп может быть большим
Финальный collect → результат всё равно материализуется
```

Streaming уменьшает память поддерживаемых операций, но не гарантирует обработку любого набора в фиксированной RAM. Используйте подходящий sink для огромного выхода; текущий API — collect(engine="streaming").

## 6. Сравнительная матрица: Pandas vs Polars vs PySpark

| Характеристика | Pandas | Polars | Apache Spark / PySpark |
| :--- | :--- | :--- | :--- |
| **Язык ядра** | C / Python | Rust | Scala / JVM |
| **Формат памяти** | NumPy массивы / Python objects | Apache Arrow (колоночный) | JVM Heap / Tungsten (Off-Heap) |
| **Параллелизм** | 1 ядро (ограничен GIL) | Все ядра CPU локальной машины | Кластер из сотен серверов |
| **Оптимизатор запросов** | Отсутствует | Catalyst-подобный (в Lazy режиме) | Catalyst Optimizer |
| **Обработка данных порциями** | Чтение chunks для поддерживаемых источников | Streaming engine для поддержанных операций | Распределённое batch execution; Structured Streaming для потоков |
| **Накладные расходы запуска** | Минимальные | Минимальные (< 10 мс) | Высокие (старт JVM, координация нод) |
| **Идеальный размер данных** | < 1 ГБ | 1 ГБ – 100 ГБ (Single-Node) | > 100 ГБ – Петабайты (Distributed) |

> **Практический совет для собеседования**: Разворачивание кластера Spark на датасетах размером 5-50 ГБ является антипаттерном из-за высоких инфраструктурных затрат и сетевого оверхеда на shuffle. Polars на одном 16-ядерном сервере обработает такой объем в 3-5 раз быстрее и в 10 раз дешевле.

### Наглядно: одна машина и кластер

```text
Pandas/Polars → ресурсы одной машины
Spark → Driver + Executors на нескольких машинах
Малые данные → overhead кластера может перевесить выгоду
```

Выбирайте по объёму, операциям, отказоустойчивости и эксплуатации, а не только по benchmark одной функции.

## 7. Практические примеры и паттерны Polars

### Паттерн 1: Оконные функции (Window Functions)

В Polars оконные функции записываются лаконично через модификатор `.over()`:

```python
import polars as pl

df = pl.DataFrame({
    "department": ["IT", "IT", "HR", "HR", "IT"],
    "employee": ["Alice", "Bob", "Charlie", "David", "Eve"],
    "salary": [100000, 120000, 70000, 85000, 95000]
})

# Расчет средней зарплаты по отделу и отклонения сотрудника от нее
result = df.with_columns([
    pl.col("salary").mean().over("department").alias("dept_avg_salary"),
    (pl.col("salary") - pl.col("salary").mean().over("department")).alias("diff_from_avg"),
    pl.col("salary").rank("dense", descending=True).over("department").alias("rank_in_dept")
])
```

### Паттерн 2: Быстрое чтение нескольких файлов и объединение

```python
# Сканирование целой директории с сотнями файлов Parquet
lf = pl.scan_parquet("data/year=2026/month=*/*.parquet")

# Присоединение справочника (Join)
dim_users = pl.scan_parquet("data/dim_users.parquet")

joined = lf.join(dim_users, on="user_id", how="left")
```

### Наглядно: join меняет зерно и NULL влияет на агрегат

```text
Orders: customer=1, amount=100
Customers: две строки customer=1 → после join две строки amount=100
SUM после join=200 вместо 100
```

Перед join проверяйте ожидаемую кардинальность и правила NULL. Для len/count уточняйте, считаете ли строки или ненулевые значения.

## 8. Типичные ошибки при работе с Polars

1. **Использование `df.to_pandas()` в середине конвейера**: Это разрушает ленивый план, копирует данные в медленный формат и может вызвать падение по OOM.
2. **Итерация по строкам через `for row in df.iter_rows()`**: Замедляет обработку в тысячи раз. Любая логика условий должна формулироваться через `pl.when().then().otherwise()`.
3. **Вызов `.collect()` слишком рано**: Вызывайте `.collect()` только в самом конце пайплайна, когда уже применены все фильтры, проекции и агрегации.
4. **Неправильный выбор джойна**: Для слияния по времени (Time Series) Polars предоставляет высокоскоростной `join_asof()`, который заменяет громоздкие оконные функции поиска ближайшего события.

### Наглядно: обход оптимизатора через Python

```text
map_elements(Python function) → вызов по элементам и ограничения плана
Встроенное выражение → нативный путь и доступные оптимизации
```

Проверяйте типы литералов, return dtype UDF и порядок операций. API библиотек меняется: фиксируйте версию, вместо механического переноса старого примера.
