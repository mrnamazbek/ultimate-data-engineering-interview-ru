# 11. Современные парадигмы моделирования DWH: Data Vault 2.0 и Anchor Modeling

## 1. Введение: Почему классических подходов (Inmon и Kimball) стало недостаточно

В классической теории проектирования хранилищ данных (DWH) долгое время доминировали две школы:
1. **Подход Билла Инмона (Corporate Information Factory, CIF)**: централизованное нормализованное хранилище в 3-й нормальной форме (3NF), из которого строятся предметные витрины (Data Marts).
2. **Подход Ральфа Кимбалла (Dimensional Modeling)**: прямое построение хранилища в виде совокупности размерных витрин (схемы «Звезда» и «Снежинка») с таблицами фактов и общими измерениями (Conformed Dimensions).

### Проблемы классических подходов при росте компании
По мере масштабирования бизнеса, увеличения числа источников данных и перехода к Agile-разработке выявились критические архитектурные ограничения:

1. **Экспоненциальный рост трудоемкости в модели Кимбалла**:
   Каждая новая витрина данных строится напрямую из исходных систем. Отсутствует единый центральный слой нормализованной исторической правды. При изменении логики в источнике инженеры вынуждены переписывать десятки изолированных витрин.
2. **Хрупкость модели Инмона к изменениям кардинальности связей**:
   Если связь между сущностями в 3NF меняется с «один-ко-многим» (1:M) на «многие-ко-многим» (M:N) (например: раньше заказ такси оформлял строго один пассажир, а затем бизнес внедрил функцию совместных поездок), в 3NF требуется кардинальная перестройка схемы, пересоздание внешних ключей и миграция исторических данных с простоем сервиса.
3. **Проблема дублирования данных в SCD Type 2**:
   Если у сущности 50 атрибутов, и раз в день меняется всего один несущественный атрибут (например, статус подписки на рассылку), классический SCD-2 дублирует всю широкую строку целиком, расходуя дисковое пространство и создавая миллионы версий.

Для решения этих проблем были разработаны ансамблевые и высоконормализованные методологии: **Data Vault 2.0** и **Anchor Modeling**.

## 2. Архитектура Data Vault: Базовые сущности

Методология Data Vault (создана Дэном Линдстедтом) разделяет хранение **бизнес-ключей**, **связей между ними** и **описательных атрибутов (контекста)** на три независимых типа таблиц:

```
    [ Satellite: SAT_CUSTOMER ]
                 │
                 ▼
          [ Hub: HUB_CUSTOMER ]
                 │
                 ├───► [ Link: LINK_ORDER_CUSTOMER ] ◄─── [ Hub: HUB_ORDER ]
                 │                                                ▲
                 ▼                                                │
    [ Satellite: SAT_CUSTOMER_ADDR ]                  [ Satellite: SAT_ORDER ]
```

### 2.1. Хаб (Hub)
Хаб представляет собой ядро бизнес-сущности (Клиент, Товар, Договор, Заказ). Хаб хранит только неизменяемый уникальный бизнес-ключ сущности.

**Структура таблицы Hub:**
- `HUB_CUSTOMER_HASH_KEY` (CHAR(32) / BINARY(16)) — суррогатный хеш-ключ бизнес-ключа (в DV 2.0).
- `CUSTOMER_ID` (VARCHAR) — реальный бизнес-ключ из системы-источника.
- `LOAD_DATE` (TIMESTAMPTZ) — дата и время первой загрузки ключа в DWH.
- `RECORD_SOURCE` (VARCHAR) — наименование системы-источника (например, `CRM_POSTGRES`).

Хаб **никогда не изменяется и не обновляется (Insert-Only)**. Если бизнес-ключ уже есть в хабе, повторная вставка игнорируется.

### 2.2. Связь (Link)
Линк представляет собой физическую реализацию связи «многие-ко-многим» (M:N) между двумя или более Хабами. Линк транзакционно фиксирует факт взаимодействия сущностей (событие покупки, оформление договора, регистрация устройства).

**Структура таблицы Link:**
- `LINK_ORDER_CUSTOMER_HASH_KEY` — хеш от конкатенации бизнес-ключей всех связанных хабов.
- `HUB_ORDER_HASH_KEY` — внешний ключ на хаб заказов.
- `HUB_CUSTOMER_HASH_KEY` — внешний ключ на хаб клиентов.
- `LOAD_DATE` — дата и время первой фиксации связи.
- `RECORD_SOURCE` — источник события.

> **Главное преимущество Линка**: Изменение кардинальности отношений (1:1 -> 1:M -> M:N) не требует изменения схемы базы данных. Линк изначально спроектирован как M:N.

### 2.3. Сателлит (Satellite)
Сателлит содержит описательный контекст (атрибуты) сущности или связи, а также полную историю их изменений во времени.

**Структура таблицы Satellite:**
- `HUB_CUSTOMER_HASH_KEY` — ссылка на родительский Хаб (или Линк).
- `LOAD_DATE` — момент загрузки данной версии атрибутов.
- `HASH_DIFF` — хеш от конкатенации всех описательных атрибутов (для мгновенного определения факта изменения строки без поколоночного сравнения).
- `FIRST_NAME`, `LAST_NAME`, `EMAIL`, `PHONE` — бизнес-атрибуты.
- `RECORD_SOURCE` — система-источник.

Сателлиты также являются **Insert-Only**: новая строка вставляется только тогда, когда `HASH_DIFF` новой порции данных не совпадает с последним известным `HASH_DIFF` в сателлите.

## 3. Эволюция к Data Vault 2.0: Революция хеш-ключей

В первой версии Data Vault (DV 1.0) суррогатные ключи генерировались через стандартные счетчики СУБД (`SEQUENCE`, `IDENTITY`, `AUTO_INCREMENT`). Это создавало узкое горлышко:
- Чтобы загрузить Линк или Сателлит, требовалось сначала дождаться окончания загрузки Хаба и получить сгенерированные целочисленные ID.
- Параллельная загрузка была невозможна.

### Ключевые нововведения Data Vault 2.0:
1. **Детерминированные хеш-ключи (MD5 / SHA-256)**:
   Ключ вычисляется как математический хеш от бизнес-ключа прямо в ETL-конвейере на клиенте (в Spark, dbt, Airflow):
   ```python
   # Расчет ключа на стороне ETL без обращения к СУБД
   hub_customer_hash_key = md5(upper(trim(customer_id)).encode('utf-8')).hexdigest()
   ```
   **Результат**: Хабы, Линки и Сателлиты могут загружаться **полностью параллельно и независимо друг от друга**.

2. **Мульти-активные сателлиты (Multi-Active Satellites)**:
   Применяются, когда у одной сущности на один момент времени может существовать несколько активных состояний (например, несколько телефонных номеров с разными типами: «рабочий», «домашний»).

3. **Служебные структуры ускорения чтения (Point-In-Time и Bridge)**:
   Поскольку Data Vault состоит из сотен узких таблиц, сборка аналитической витрины требует десятков соединений (`JOIN`). Для устранения оверхеда в DV 2.0 вводятся таблицы ускорения:
   - **PIT (Point-In-Time) таблицы**: предварительно рассчитанные срезы ключей сателлитов на определенные моменты времени (например, на каждый день в 00:00). Исключают тяжелые неравенства `WHERE load_date <= snapshot_date`.
   - **Bridge таблицы**: материализованные пути обхода сложных графов линков (Link-to-Link) для плоских выборок.

## 4. Якорное моделирование (Anchor Modeling)

**Anchor Modeling** (разработано Ларсом Рённбэком и Олле Регнером) доводит идею декомпозиции до абсолюта и переводит базу данных в **Шестую нормальную форму (6NF)**.

### Философия 6NF
В 6-й нормальной форме таблица содержит первичный ключ и **не более одного** описательного атрибута.

### 4 базовых строительных блока Anchor Modeling:

| Элемент | Название в методологии | Описание | Пример |
| :--- | :--- | :--- | :--- |
| **Якорь (Anchor)** | Сущность | Хранит только идентификатор объекта без каких-либо атрибутов. | `ANC_CUSTOMER (CU_ID)` |
| **Атрибут (Attribute)** | Свойство якоря | Хранит ровно один атрибут, ссылку на якорь и временную метку (если историчен). | `CU_NAM_Customer_Name (CU_ID, CU_NAM_Value, ChangedAt)` |
| **Связь (Tie)** | Связь якорей | Связывает два или более якоря. Может быть исторической. | `CU_owns_AC (CU_ID, AC_ID, ChangedAt)` |
| **Узел (Knot)** | Справочник | Таблица общих справочных значений с высокой повторяемостью (аналог ENUM). | `GEN_Gender (GEN_ID, Description)` |

### Ключевые преимущества Anchor Modeling:
1. **Zero-Lock Schema Evolution (Нулевая блокировка при эволюции)**:
   Если бизнесу потребовалось добавить новое поле (например, `Telegram_ID`), в классической СУБД выполняется `ALTER TABLE ADD COLUMN`, что блокирует таблицу на миллионы строк. В Anchor Modeling просто создается **новая независимая таблица** для атрибута:
   ```sql
   CREATE TABLE CU_TEL_Customer_Telegram (
       CU_ID bigint REFERENCES ANC_CUSTOMER(CU_ID),
       Telegram_Username varchar(64),
       ChangedAt timestamptz,
       PRIMARY KEY (CU_ID, ChangedAt)
   );
   ```
   Старые запросы и существующие таблицы вообще не затрагиваются.
2. **Отсутствие пустых значений (Sparse Data Optimization)**:
   Если у 95% пользователей не заполнен загранпаспорт, в 3NF/Star Schema под него выделяются пустые колонки (NULL). В Anchor Modeling для незаполненных полей строки просто физически не создаются.

## 5. Сравнительная матрица методологий DWH

| Критерий | Inmon (3NF CIF) | Kimball (Star Schema) | Data Vault 2.0 | Anchor Modeling (6NF) |
| :--- | :--- | :--- | :--- | :--- |
| **Уровень нормализации** | 3NF | Денормализация | 3NF / 4NF (ансамбль) | 6NF |
| **Основное назначение** | Центральное DWH | Витрины отчетности (BI) | Масштабируемое корпоративное ядро DWH | Гибкое ядро DWH при частых изменениях требований |
| **Сложность добавления источника** | Высокая (рефакторинг 3NF) | Средняя (пересчет измерений) | Низкая (создание новых сателлитов/линков) | Минимальная (создание новых атрибутов/якорей) |
| **Параллельная загрузка** | Ограничена блокировками PK/FK | Зависит от генерации surrogate keys | Полная (за счет хеш-ключей) | Полная (независимые таблицы атрибутов) |
| **Производительность чтения (BI)** | Низкая (много JOIN) | Максимальная (быстрый Star Join) | Средняя (требует PIT/Bridge или слоя витрин) | Низкая в чистом виде (требует генерации представлений) |
| **Хранилище/СУБД** | Традиционные RDBMS | Любые СУБД, OLAP | MPP (Greenplum, Snowflake), Cloud Lakehouse | Колоночные MPP с хорошим предикатным pushdown |

## 6. Практический пример: Моделирование предметной области такси

### Бизнес-кейс:
Сервис такси фиксирует поездки. Изначально: Пассажир заказывает поездку у Водителя. Затем бизнес вводит возможность совместных поездок (несколько пассажиров в одной машине) и промокоды.

### Реализация на Data Vault 2.0 (DDL SQL):

```sql
-- 1. Хабы сущностей (Insert-Only)
CREATE TABLE hub_passenger (
    hub_passenger_pk CHAR(32) PRIMARY KEY, -- MD5(passenger_phone)
    passenger_phone VARCHAR(32) NOT NULL,
    load_date TIMESTAMPTZ NOT NULL,
    record_source VARCHAR(64) NOT NULL
);

CREATE TABLE hub_driver (
    hub_driver_pk CHAR(32) PRIMARY KEY, -- MD5(license_number)
    license_number VARCHAR(64) NOT NULL,
    load_date TIMESTAMPTZ NOT NULL,
    record_source VARCHAR(64) NOT NULL
);

CREATE TABLE hub_ride (
    hub_ride_pk CHAR(32) PRIMARY KEY, -- MD5(ride_uuid)
    ride_uuid VARCHAR(64) NOT NULL,
    load_date TIMESTAMPTZ NOT NULL,
    record_source VARCHAR(64) NOT NULL
);

-- 2. Линк связи поездки, водителя и пассажиров (M:N)
CREATE TABLE link_ride_participation (
    link_ride_participation_pk CHAR(32) PRIMARY KEY,
    hub_ride_pk CHAR(32) NOT NULL REFERENCES hub_ride(hub_ride_pk),
    hub_driver_pk CHAR(32) NOT NULL REFERENCES hub_driver(hub_driver_pk),
    hub_passenger_pk CHAR(32) NOT NULL REFERENCES hub_passenger(hub_passenger_pk),
    load_date TIMESTAMPTZ NOT NULL,
    record_source VARCHAR(64) NOT NULL
);

-- 3. Сателлит с изменяемыми атрибутами пассажира
CREATE TABLE sat_passenger_details (
    hub_passenger_pk CHAR(32) NOT NULL REFERENCES hub_passenger(hub_passenger_pk),
    load_date TIMESTAMPTZ NOT NULL,
    hash_diff CHAR(32) NOT NULL, -- MD5(first_name + '|' + email)
    first_name VARCHAR(128),
    email VARCHAR(256),
    record_source VARCHAR(64) NOT NULL,
    PRIMARY KEY (hub_passenger_pk, load_date)
);
```

Если завтра в поездку добавится второй пассажир, схема базы данных **не изменится ни на один символ**: в таблицу `link_ride_participation` просто добавится еще одна строка с тем же `hub_ride_pk`, но другим `hub_passenger_pk`.

## 7. Вопросы с собеседований

### Вопрос 1: Зачем в Data Vault 2.0 перешли с автоинкрементных ключей на хеши?
**Ответ**:
Автоинкрементные ключи создают централизованное бутылочное горлышко: при загрузке сателлита или линка поток обязан обратиться к таблице хаба, заблокировать счетчик sequence и дождаться выдачи ID. Переход на хеш-ключи (MD5/SHA) позволяет вычислять ключи на этапе распределенной обработки (в Spark/dbt) до начала записи в хранилище. Это дает возможность загружать сотни хабов, линков и сателлитов абсолютно параллельно без взаимных блокировок.

### Вопрос 2: Что такое таблица PIT (Point-In-Time) и какую проблему она решает?
**Ответ**:
В Data Vault сущность окружена множеством сателлитов, каждый из которых обновляется со своей частотой (асинхронно). Чтобы собрать срез данных на конкретную дату, классический SQL-запрос должен выполнять сложные подзапросы с поиском максимальной даты загрузки (`MAX(load_date) WHERE load_date <= target_date`) для каждого сателлита, что приводит к многократным сканированиям больших таблиц. PIT-таблица предварительно материализует связку: `(hub_key, target_snapshot_date, sat1_load_date, sat2_load_date)`. Запрос к витрине превращается в простой и быстрый экви-джойн (`INNER JOIN on load_date`).
