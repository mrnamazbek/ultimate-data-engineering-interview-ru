# Хеширование, коллизии и дедупликация в Data Engineering

Модуль соединяет устройство `dict`/`set`, алгоритмы JOIN, ключи DWH и надёжность загрузки. Сначала определите, для чего нужен хеш: поиск, распределение, контроль изменений или идентификация. Эти задачи требуют разных гарантий.

## 1. Вопрос: что такое коллизия хеша?

**Ответ:** разные входы дают один результат хеш-функции: `x != y`, но `h(x) = h(y)`. Если множество входов больше конечного пространства хешей, коллизии неизбежны. Увеличение разрядности снижает вероятность случайной коллизии, но не даёт математической уникальности.

```python
def toy_hash(key: int) -> int:
    return key % 4

print(toy_hash(2), toy_hash(6))  # 2 2: разные ключи, одинаковый хеш
print(hash(-1) == hash(-2))     # True: пример коллизии Python int
print(len({-1, -2}))           # 2: set различает исходные ключи
```

**Наглядно:** `2 → h → 2 ← h ← 6`. Хеш — кандидат для поиска совпадения; окончательное решение может требовать сравнения исходных значений.

## 2. Вопрос: коллизия хеша и попадание в один bucket — одно и то же?

**Ответ:** нет. Разные полные хеши могут попасть в один bucket после сокращения диапазона, например через `% capacity`. Это конфликт размещения, даже когда полные хеши отличаются.

```text
Полный hash(A)=10 → 10 % 8 = 2 ┐
Полный hash(B)=18 → 18 % 8 = 2 ┴→ один bucket, разные полные хеши
Полный hash(C)=10 ──────────────→ совпадает полный хеш A и C
```

**Ловушка:** увеличить таблицу можно для уменьшения конфликтов размещения, но это не делает полные хеши уникальными.

## 3. Вопрос: как хеш-таблицы разрешают коллизии?

**Ответ:** chaining хранит несколько записей в bucket; open addressing ищет другую свободную позицию по правилу probing. CPython `dict` использует открытую адресацию, но его устройство нельзя описывать как универсальный массив связанных списков.

```text
Chaining: bucket 2 → (A, value) → (B, value)
Open addressing: bucket 2 занят A → probe → bucket 5 свободен → записать B
Поиск B: повторить probing → проверить хеш и равенство ключа
```

**Follow-up:** удаление в открытой адресации должно сохранять путь поиска, например специальным маркером, а не просто обрывать его. Конкретные детали зависят от реализации.

## 4. Вопрос: почему поиск в `dict` в среднем O(1), а не всегда?

**Ответ:** при хорошем распределении и контролируемой заполненности нужно мало проверок. Много конфликтов ухудшают поиск, в худшем случае до O(n); обработка n таких ключей может потребовать O(n²). Расширение таблицы стоит O(n), но стоимость вставки амортизируется. Длинный ключ тоже не хешируется бесплатно.

| Условия | Иллюстрация поиска |
|---|---|
| Хорошее распределение | Несколько проверок независимо от числа записей |
| Все n ключей имеют один хеш | До n сравнений равенства |
| Resize | Перестройка таблицы, затем снова короткий поиск |

**DE-кейс:** `set` ускоряет проверку ID, но требует памяти под все ID. При миллиардах ключей рассмотрите JOIN в движке, внешний sort/merge или предварительный Bloom filter с точной проверкой.

## 5. Вопрос: каков договор `__eq__` и `__hash__`?

**Ответ:** равные ключи обязаны иметь одинаковый хеш; одинаковый хеш не доказывает равенство. Нельзя менять поля, определяющие хеш ключа, пока он находится в коллекции.

```text
Вставили key(id=42): hash=H42 → позиция P
Поменяли id на 43: hash=H43 → поиск идёт к Q → запись может не находиться
```

**Пример:** используйте неизменяемый `(source, event_id)`, а не изменяемый словарь события. Кортеж с вложенным списком тоже нехешируем. Код корректного ключа есть в [ООП, вопрос 11](../01-junior/06-oop-for-data-engineers.md).

## 6. Вопрос: можно ли использовать Python `hash()` как постоянный ключ DWH?

**Ответ:** нет. Хеши строк и bytes рандомизируются между процессами; алгоритм и разрядность зависят от среды. Это локальный механизм коллекций, а не межсистемный договор. Для воспроизводимого ключа задают алгоритм, сериализацию, кодировку, нормализацию и версию правил.

```python
import hashlib
import json

def business_key(source: str, customer_id: str) -> str:
    payload = json.dumps(
        [source, customer_id], ensure_ascii=False, separators=(",", ":")
    ).encode("utf-8")
    return hashlib.sha256(payload).hexdigest()

print(business_key("crm", "42") == business_key("crm", "42"))  # True
print(business_key("crm", "42") == business_key("erp", "42"))  # False
```

**Наглядно:** `договор полей → однозначные байты UTF-8 → SHA-256 → ключ`. Этот JSON-пример задаёт простой договор для списка строк, а не универсальную канонизацию любых JSON-документов.

## 7. Вопрос: зачем канонизация, если используется SHA-256?

**Ответ:** сильный хеш не исправляет неоднозначный вход. Простая конкатенация может дать одинаковые байты для разных составных ключей; это ошибка сериализации, а не криптографическая коллизия.

```text
("ab", "c") → "abc" ← ("a", "bc")
("a|b", "c") → "a|b|c" ← ("a", "b|c")
JSON-массив: ["ab","c"] != ["a","bc"]
NULL должен отличаться от пустой строки и буквального текста "NULL"
```

**Follow-up:** задайте порядок полей, escape/length prefix, decimal scale, timezone и Unicode-нормализацию. `upper(trim(id))` допустим только если бизнес считает такие ID равными; иначе вы склеите разные сущности ещё до хеширования.

## 8. Вопрос: как оценить вероятность случайной коллизии?

**Ответ:** при равномерном независимом b-битном хеше и n различных входах приближение birthday bound:

$$p \approx 1 - e^{-n(n-1)/(2 \cdot 2^b)}.$$

Когда показатель мал, `p ≈ n(n−1)/(2·2^b)`.

| Размер хеша | n = 1 миллиард различных ключей | Вывод |
|---|---|---|
| 64 бит | p ≈ 2,67% | Недостаточно для необратимой склейки ключей без проверки |
| 128 бит | p ≈ 1,47 × 10⁻²¹ | Очень малая случайная вероятность при указанных предпосылках |
| 256 бит | p ≈ 4,32 × 10⁻⁶⁰ | Ещё ниже, но ошибки договора входа всё равно возможны |

**Наглядно:** число потенциальных пар растёт примерно как n², а не n. Это оценка случайных совпадений; атаки на MD5 и ошибки нормализации нельзя оценивать этой таблицей.

## 9. Вопрос: чем отличаются криптографический хеш, быстрый хеш и checksum?

| Инструмент | Подходящая задача | Что не гарантирует |
|---|---|---|
| CRC/checksum | Обнаружение случайной порчи | Защиту от намеренного изменения |
| Быстрый некриптографический хеш | Bucket, shuffle, hash table | Уникальность или стойкость к атакующему |
| SHA-256 | Устойчивый digest, контроль содержимого по доверенному эталону | Уникальность, авторство, шифрование |
| HMAC с секретом | Проверку целостности и подлинности для обладателей секрета | Конфиденциальность |

**Наглядно:** `открытый файл → digest`; если атакующий заменил и файл, и недоверенный digest, сравнение ничего не докажет. Нужен доверенный канал для эталона или соответствующий механизм аутентификации. MD5 имеет известные криптографические слабости; его историческое применение в DWH не делает его подходящим для защиты от атак.

## 10. Вопрос: как hash join сохраняет корректность при коллизиях?

**Ответ:** сначала строит структуру по хешу ключа одной стороны, затем ищет кандидатов для другой стороны и проверяет реальное условие соединения. Совпавший bucket сам по себе не основание выдавать строку результата.

```text
Build: A(key=2), B(key=6) → toy_hash=2 → один bucket
Probe: key=2 → кандидаты [A, B] → 2=2: да; 2=6: нет → только A
```

**Follow-up:** два разных ключа с одним хешем — коллизия; миллион строк с одинаковым ключом — data skew. Хороший хеш не распределит один и тот же ключ по разным партициям без дополнительной техники. Дубли совпадающего ключа с обеих сторон размножают результат JOIN.

## 11. Вопрос: достаточно ли хеша строки для дедупликации и сверки?

**Ответ:** сначала выберите определение дубля: повтор события, одинаковый payload или новая версия сущности. При критичной точности сравнивайте исходные ключи/поля после совпадения digest. Сумма хешей или сумм денежных значений сама по себе не доказывает равенство наборов.

```text
event_id=42, v1, amount=100 → повтор v1: транспортный дубль
event_id=42, v2, amount=120 → изменение: нельзя удалить как дубль v1
Набор A: [100, 200]; набор B: [150, 150] → SUM=300 в обоих, строки различаются
```

**Кейс Data Vault:** `hash key` представляет бизнес-ключ, `hashdiff` — контролируемый набор описательных атрибутов. Храните исходный бизнес-ключ, версию канонизации и проверяйте конфликт «один hash key, разные бизнес-ключи». Несовпавшие hashdiff указывают на разные байты; совпавшие не являются математическим доказательством равенства.

## 12. Вопрос: коллизии, Bloom filter и consistent hashing решают одну задачу?

**Ответ:** нет. Bloom filter быстро отсеивает точно отсутствующие элементы и может дать false positive. Consistent hashing распределяет ключи и сокращает их перемещение при смене состава узлов. Ни один не делает идентификатор уникальным.

```text
Bloom «точно нет» → точный поиск можно пропустить
Bloom «возможно есть» → проверить исходный ключ в точном хранилище
Consistent hashing → выбрать узел → хранить и сравнивать реальные ключи
```

**Ловушка:** отбросить событие как дубль только по положительному Bloom — значит потерять часть новых событий. Отсутствие false negative предполагает корректно поддерживаемый фильтр без неподдерживаемых удалений. Подробнее: [вероятностные структуры и LSM](../03-senior/04-algorithms-data-engineering.md).
