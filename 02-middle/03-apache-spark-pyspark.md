# Apache Spark и PySpark (Уровень Middle)

Apache Spark — главный распределенный вычислительный фреймворк в современном Big Data стеке. На собеседованиях уровня Middle от кандидата требуют глубокого понимания архитектуры Spark, оптимизатора Catalyst, правильного управления партициями и оптимизации работы с памятью.

---

## 1. Архитектура Spark: Driver, Cluster Manager, Executors

Spark работает в распределенной парадигме Master-Worker:

```text
               +-----------------------------------+
               |        Driver Program             |
               |  (SparkSession, DAGScheduler)     |
               +-----------------+-----------------+
                                 |
                     +-----------v-----------+
                     |    Cluster Manager    |
                     | (YARN, K8s, Mesos)    |
                     +-----+-----------+-----+
                           |           |
            +--------------+           +--------------+
            |                                         |
+-----------v-----------+                 +-----------v-----------+
|    Worker Node 1      |                 |    Worker Node 2      |
| +-------------------+ |                 | +-------------------+ |
| |     Executor      | |                 | |     Executor      | |
| | [Task] [Task]     | |                 | | [Task] [Task]     | |
| | (Executor Memory) | |                 | | (Executor Memory) | |
| +-------------------+ |                 | +-------------------+ |
+-----------------------+                 +-----------------------+
```

1. **Driver**:
   - Главный управляющий процесс. Создает `SparkSession`, компилирует пользовательский код в ориентированный ациклический граф задач (**DAG — Directed Acyclic Graph**), разбивает DAG на стадии (Stages) и задачи (Tasks), распределяет их по исполнителям.
2. **Cluster Manager**:
   - Выделяет физические ресурсы (память и ядра CPU). Поддерживает Standalone, Apache YARN, Kubernetes.
3. **Executors**:
   - Рабочие JVM-процессы на нодах кластера, выполняющие назначенные таски в отдельных потоках (Cores) и сохраняющие данные в оперативной памяти или на диске.

## 2. Ленивые вычисления (Lazy Evaluation), Трансформации и Действия

Spark не выполняет вычисления сразу после написания строки кода. Он лишь строит логический план выполнения. Физический расчет запускается только при вызове действия (**Action**).

### 1. Узкие трансформации (Narrow Transformations)
- Каждая входная партиция данных используется максимум одной выходной партицией.
- Данные не передаются по сети между нодами кластера (выполняются локально в памяти исполнителя).
- *Примеры*: `filter()`, `map()`, `select()`, `withColumn()`.

### 2. Широкие трансформации (Wide Transformations)
- Данные из одной входной партиции требуются множеству выходных партиций.
- Вызывают **Shuffle** — тяжелый процесс перераспределения данных по сети между всеми узлами кластера с записью промежуточных файлов на диск.
- *Примеры*: `groupBy()`, `join()`, `distinct()`, `repartition()`, `orderBy()`.

### 3. Действия (Actions)
- Триггерят физический запуск DAG-графа и возвращают результат в Driver или записывают данные на постоянный диск.
- *Примеры*: `count()`, `collect()`, `show()`, `write.save()`, `take()`.

## 3. Оптимизатор Catalyst и Project Tungsten

В основе PySpark DataFrame API лежит движок **Catalyst**, который превращает декларативный код в оптимизированный байт-код.

### Этапы работы Catalyst:
1. **Анализ (Analysis)**: Разрешение названий таблиц и колонок через внутренний метастор (Catalog).
2. **Логическая оптимизация (Logical Optimization)**:
   - **Predicate Pushdown**: проталкивание условий фильтрации (`WHERE`) непосредственно к источнику данных (в Parquet или СУБД), чтобы с диска читались только нужные строки.
   - **Column Pruning**: чтение только запрошенных колонок, отсечение неиспользуемых.
   - **Constant Folding**: вычисление статических выражений на этапе компиляции (например, `1 + 1` заменяется на `2`).
3. **Физическое планирование (Physical Planning)**: Создание нескольких физических планов исполнения и выбор плана с минимальной стоимостью (Cost-Based Optimizer, CBO).
4. **Генерация кода (Whole-Stage Code Generation)**: Движок **Tungsten** компилирует цепочку операций в единый байт-код Java на лету, убирая накладные расходы на виртуальные вызовы функций и размещая данные компактно вне кучи JVM (Off-heap binary memory).

## 4. Управление партициями: `repartition()` против `coalesce()`

| Критерий | `repartition(N)` | `coalesce(N)` |
|---|---|---|
| **Наличие Shuffle** | Всегда вызывает полный Shuffle по сети | Выполняется **без Shuffle** (слияние локальных партиций) |
| **Изменение числа партиций** | Может как уменьшать, так и увеличивать | Может **только уменьшать** |
| **Равномерность распределения** | Равномерно распределяет данные | Может создавать перекосы по объему партиций |
| **Когда использовать** | Увеличение параллелизма или балансировка после тяжелого фильтра | Уменьшение количества мелких файлов перед записью на диск (`df.coalesce(1).write.parquet(...)`) |

## 5. Кэширование: `cache()` против `persist()`

- `df.cache()` — это шорткат для `df.persist(StorageLevel.MEMORY_AND_DISK)`.
- `df.persist(storage_level)` — позволяет явно указать уровень хранения данных:
  - `MEMORY_ONLY`: только в ОЗУ в виде десериализованных Java-объектов.
  - `MEMORY_ONLY_SER`: в ОЗУ в компактном сериализованном виде (экономит память, но тратит CPU на десериализацию).
  - `MEMORY_AND_DISK`: если в ОЗУ не помещается, избыток сбрасывается на локальный диск executor-а.
  - `OFF_HEAP`: хранение во внекучевой памяти через Tungsten.

*Важное правило*: Если датасет больше не нужен в цепочке вычислений, необходимо явно вызвать `df.unpersist()`, чтобы освободить память кластера.

## 6. Задание схемы: `inferSchema` против явного `StructType`

### Почему `inferSchema=True` запрещен в продакшне:
1. **Лишний проход по данным**: Чтобы угадать типы колонок, Spark вынужден прочитать весь файл целиком перед созданием DataFrame. На терабайтных объемах это удваивает время работы пайплайна.
2. **Нестабильность типов**: Если в строковой колонке с числами случайно встретится символ или `NULL`, тип может определиться некорректно, сломав последующие шаги.

### Явное задание схемы:
```python
from pyspark.sql.types import StructType, StructField, StringType, IntegerType, DoubleType, TimestampType

schema = StructType([
    StructField("transaction_id", StringType(), False),
    StructField("user_id", IntegerType(), False),
    StructField("amount", DoubleType(), True),
    StructField("event_time", TimestampType(), True)
])

df = spark.read \
    .format("csv") \
    .option("header", "true") \
    .schema(schema) \
    .load("s3a://data-lake/raw/transactions/")
```

## 7. Пользовательские функции (UDF): подводные камни

### Почему стандартный Python UDF медленный:
При вызове `pyspark.sql.functions.udf` строки из JVM сериализуются через сокет в отдельный Python-процесс, там выполняется функция, и результат сериализуется обратно в JVM. Это приводит к колоссальным накладным расходам CPU и памяти (Py4J overhead).

### Решение: Использование Vectorized Pandas UDF
Векторизованные UDF используют Apache Arrow для передачи данных пакетами (батчами) без накладных расходов на сериализацию:

```python
import pandas as pd
from pyspark.sql.functions import pandas_udf

@pandas_udf("double")
def vectorized_discount(amounts: pd.Series) -> pd.Series:
    # Вычисление выполняется средствами высокооптимизированного C-кода библиотеки Pandas/Numpy
    return amounts * 0.9

df = df.withColumn("discounted_amount", vectorized_discount("amount"))
```
