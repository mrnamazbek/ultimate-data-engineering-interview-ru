# Фундаментальные основы баз данных и СУБД (Уровень Junior)

В данном модуле собраны фундаментальные вопросы о внутреннем устройстве реляционных баз данных: принципы транзакций, уровни изоляции, структуры индексов и теория нормализации. Эти темы формируют базовую инженерную грамотность Junior Data Engineer и Junior Database Developer.

---

## 1. Свойства транзакций: Принцип ACID

Транзакция — это неделимая последовательность операций над базой данных, которая переводит систему из одного согласованного состояния в другое.

### Расшифровка ACID:
1. **Atomicity (Атомарность)**:
   - Принцип «все или ничего». Транзакция не может выполниться частично. При сбое на любом шаге все предыдущие изменения откатываются (`ROLLBACK`).
   - *Пример*: Банковский перевод — деньги списались со счета А, но из-за сбоя сети не зачислились на счет Б. Атомарность гарантирует откат списания.

2. **Consistency (Согласованность)**:
   - База данных переходит только из одного валидного состояния в другое, не нарушая ограничений целостности (Primary Key, Foreign Key, Check, триггеры).

3. **Isolation (Изолированность)**:
   - Параллельно выполняющиеся транзакции не должны влиять на результаты друг друга так, будто они выполняются одновременно. Степень изолированности регулируется уровнями изоляции.

4. **Durability (Надежность / Долговечность)**:
   - Если транзакция зафиксирована (`COMMIT`), ее результаты сохраняются навсегда, даже если сервер немедленно перезагрузится или отключится питание. Это достигается записью в журнал упреждающей записи (WAL — Write-Ahead Logging).

## 2. Уровни изоляции транзакций и аномалии

Стандарт ANSI SQL определяет 4 уровня изоляции для баланса между строгой корректностью данных и скоростью параллельной работы:

| Уровень изоляции | Грязное чтение (Dirty Read) | Неповторяющееся чтение (Non-repeatable Read) | Фантомное чтение (Phantom Read) |
|---|---|---|---|
| **Read Uncommitted** | Возможно | Возможно | Возможно |
| **Read Committed** (по умолчанию в PG, Oracle) | Защищено | Возможно | Возможно |
| **Repeatable Read** (по умолчанию в MySQL InnoDB) | Защищено | Защищено | Возможно (в PG защищено через MVCC) |
| **Serializable** | Защищено | Защищено | Защищено |

### Описание аномалий:
- **Грязное чтение (Dirty Read)**: Транзакция 1 читает изменения, сделанные Транзакцией 2, которые Транзакция 2 еще не закоммитила (и может откатить).
- **Неповторяющееся чтение (Non-repeatable Read)**: Транзакция 1 читает одну и ту же строку дважды, но между чтениями Транзакция 2 изменяет эту строку и коммитит. В итоге значения отличаются.
- **Фантомное чтение (Phantom Read)**: Транзакция 1 выполняет запрос с фильтром (например, `WHERE salary > 50000`) дважды, но Транзакция 2 вставляет новую строку, удовлетворяющую условию. Во втором чтении появляется новая «строка-фантом».

## 3. Индексы: Кластерные и Некластерные (B-Tree)

Индекс — это специализированная структура данных (чаще всего сбалансированное дерево B-Tree), ускоряющая поиск и выборку строк ценой дополнительного дискового пространства и замедления операций записи (`INSERT`, `UPDATE`, `DELETE`).

### Кластерный индекс (Clustered Index)
- Физически упорядочивает хранение строк таблицы на диске в соответствии со значениями ключа индекса.
- Листовые узлы кластерного индекса содержат **сами данные** строки.
- В таблице может быть **только один** кластерный индекс (обычно создается на первичном ключе).
- В PostgreSQL аналогом является таблица-куча (Heap Table), а команда `CLUSTER` выполняет разовое физическое упорядочивание. В MySQL InnoDB таблица всегда организована как кластерный индекс по Primary Key.

### Некластерный индекс (Non-Clustered / Secondary Index)
- Хранится отдельно от данных таблицы.
- Листовые узлы содержат ключ индекса и **указатель** на физическое расположение строки (RowID или значение первичного ключа).
- В таблице может быть создано множество некластерных индексов под различные фильтры.

### Покрывающий индекс (Covering Index)
Индекс, содержащий все колонки, запрошенные в блоке `SELECT`. СУБД извлекает результат напрямую из дерева индекса, не обращаясь к страницам самой таблицы на диске (механизм **Index Only Scan**).

```sql
-- Создание составного покрывающего индекса
CREATE INDEX idx_users_city_email ON users(city, email);

-- Данный запрос выполнит Index Only Scan без чтения самой таблицы:
SELECT email FROM users WHERE city = 'Almaty';
```

## 4. Нормализация реляционных баз данных

Нормализация — это процесс проектирования структуры таблиц с целью устранения избыточности данных и предотвращения аномалий модификации.

### Аномалии денормализованных таблиц:
1. **Аномалия вставки (Insert Anomaly)**: Невозможно добавить информацию об одном объекте без создания фиктивной записи о другом (например, нельзя завести новый отдел, пока в него не нанят хотя бы один сотрудник).
2. **Аномалия обновления (Update Anomaly)**: При изменении атрибута (например, названия города клиента) требуется обновить сотни строк. При сбое данные станут несогласованными.
3. **Аномалия удаления (Delete Anomaly)**: Удаление одной сущности приводит к случайной потере сопутствующей важной информации (удаление последнего сотрудника удаляет сам отдел).

### Нормальные формы:

#### Первая нормальная форма (1NF)
- Все атрибуты должны быть **атомарными** (неделимыми: нельзя хранить список телефонов через запятую в одном поле).
- В таблице отсутствует повторяющаяся группа колонок (например, `phone_1`, `phone_2`, `phone_3`).
- Каждая строка уникальна (определен первичный ключ).

#### Вторая нормальная форма (2NF)
- Таблица находится в 1NF.
- Все неключевые атрибуты функционально полно зависят от **всего составного первичного ключа**, а не от его части.
- *Пример*: В таблице `OrderItems` ключ `(order_id, product_id)`. Поле `product_name` зависит только от `product_id`, а не от `order_id`. Для соблюдения 2NF `product_name` выносится в отдельную таблицу `Products`.

#### Третья нормальная форма (3NF)
- Таблица находится в 2NF.
- Отсутствуют **транзитивные зависимости**: неключевые атрибуты зависят только от первичного ключа и не зависят от других неключевых атрибутов ($A \to B \to C$).
- *Пример*: Таблица сотрудников имеет поля `emp_id` (PK), `department_id`, `department_name`. Здесь `department_name` зависит от `department_id`, который зависит от `emp_id`. Для 3NF `department_name` переносится в таблицу отделов.

#### Нормальная форма Бойса-Кодда (BCNF)
- Усиленная версия 3NF. Требует, чтобы для любой функциональной зависимости $X \to Y$ детерминант $X$ являлся суперключом таблицы.

## 5. Денормализация: когда и зачем она применяется

Денормализация — это осознанное внесение избыточности в схему базы данных для ускорения аналитических запросов на чтение.

### Сравнение подходов:
- **OLTP-системы (Online Transaction Processing)**: Применяют нормализацию до 3NF. Приоритет — быстрые и безопасные точечные вставки, обновления и удаление без аномалий.
- **OLAP-системы и DWH (Online Analytical Processing)**: Применяют денормализацию (схемы «Звезда» и «Снежинка»). Приоритет — минимизация тяжелых операций `JOIN` при агрегации миллиардов строк.

## 6. Представления (Views) против Материализованных представлений (Materialized Views)

| Характеристика | Обычное представление (View) | Материализованное представление (Materialized View) |
|---|---|---|
| Хранение данных | Данные не хранятся физически (только сохраненный SQL-запрос) | Физически сохраняет результат выборки на диске |
| Скорость чтения | Каждый раз выполняет базовый запрос заново | Мгновенно читает предрассчитанный результат, как из обычной таблицы |
| Индексация | Индексы строить нельзя | Можно создавать собственные индексы |
| Актуальность данных | Всегда актуальны (real-time) | Требует явного обновления (`REFRESH MATERIALIZED VIEW`) |

```sql
-- Создание материализованного представления для витрины отчетов
CREATE MATERIALIZED VIEW mv_monthly_sales AS
SELECT 
    date_trunc('month', order_date) AS sales_month,
    category_id,
    SUM(amount) AS total_revenue
FROM sales
GROUP BY 1, 2;

-- Создание индекса для ускорения выборки по месяцам
CREATE INDEX idx_mv_sales_month ON mv_monthly_sales(sales_month);

-- Обновление данных в витрине
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_monthly_sales;
```
